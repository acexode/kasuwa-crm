# ADR-0018 — The transactional outbox and the kasuwa_relay role

- **Status:** Accepted (D-L128, @acexode, 2026-10-13). Answers to Q1–Q5 are in D-L128.
  Approved in principle by D-P30 item 2 (2026-10-07); this ADR is the design that approval asked for.
- **Date:** 2026-10-13
- **Deciders:** Lead; @acexode
- **Amends:** ADR-0002 (runtime roles), the `apps/worker/src/main.ts` header ("there is no other connection in this process")

## Context
CLAUDE.md 2.6 says events go through an outbox, and 2.5 says one domain never calls into another. Neither has been possible
yet, because the outbox does not exist. Phase 2 now needs it. Notifications (P26: T-0098 to T-0101) are produced by the
contact, deal and activity domains and consumed by a notifications domain. Search sync and outbound webhooks come later
(ADR-0014 names the outbox as the only acceptable sync path). The M18 portal-invite send is also gated on "an outbox, not
inside the DB transaction" (D-L52).

The relay that drains the outbox has to see rows from every tenant. `kasuwa_app` cannot, by design: every policy reads the
session GUCs, and a worker has no ambient tenant. That is the same problem the auth sweep had, and ADR-0012 and ADR-0013 set
the precedent: a dead-narrow role whose reach is bounded by the catalogue, not by code review.

D-P29 fixes what an event may carry: a notification stores (kind, object type, object id, actor id) and nothing else. Its
title is built at read time, under the reader's scope and field security.

## Decision
1. **The table: `outbox_event`** (one migration, T-0098):
   - `id uuid` primary key, generated by the producer; `seq bigint GENERATED ALWAYS AS IDENTITY` for ordering;
   - `tenant_id uuid NOT NULL`, `programme_id uuid NOT NULL`, `actor_user_id uuid` (NULL only for a system event, see Q2);
   - `event_type text` (for example `deal.stage_changed`), `schema_version smallint`;
   - `aggregate_type text`, `aggregate_id uuid`;
   - `payload jsonb`: identifiers, enum codes, field api names and timestamps only. Never a name, subject, amount, phone or
     any other value (D-P29). Each event type has a strict Zod schema that admits no free-text string;
   - `created_at`, `published_at`, `attempts smallint DEFAULT 0`, `last_attempt_at`, `dead_at`.
   - Partial indexes on `(seq) WHERE published_at IS NULL AND dead_at IS NULL` and on `(aggregate_type, aggregate_id, seq)`
     with the same predicate.
   - `programme_id` is NOT NULL, as ADR-0004 already requires of every event. A tenant-level event waits for a case that
     justifies it (Q1).
2. **Writing an event.** `appendOutboxEvent(tx: TenantTx, event)` in `packages/db`. It takes the tenant from `tx.session`,
   refuses a `programme_id` outside `tx.session.programmeIds`, and parses the payload with the event's schema before the
   INSERT. Because it needs a `TenantTx`, it can only run inside the producer's own `withTenantTransaction`. The event
   commits with the change or not at all, and the ADR-0010 commit-time scope check covers it like any other write.
3. **RLS and grants on `outbox_event`.** ENABLED and FORCED.
   - `outbox_tenant` `FOR ALL TO kasuwa_app`, the usual tenant-and-programme predicate, WITH CHECK identical to USING.
   - `kasuwa_app` holds **INSERT and SELECT only**. The migration revokes the default UPDATE and DELETE, as 0024 did for the
     auth tables, so SQL inside a tenant cannot mark its own events published or erase them. SELECT is kept so a consumer
     can confirm an event exists in its tenant (point 8).
   - The relay's policies are named `TO kasuwa_relay` and the tenant policy `TO kasuwa_app`, so neither role evaluates the
     other's predicate and the relay needs no EXECUTE on the `app` accessors.
4. **The role: `kasuwa_relay`**, created in `bootstrap.sql` (lead-owned):
   - LOGIN, NOBYPASSRLS, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION;
   - a member of no role, and no role is a member of it. Unlike the sweeper, it is never granted to `kasuwa_app`, so no
     injected `SET ROLE` reaches it (the ADR-0013 reasoning);
   - CONNECT on the database, USAGE on `public`; no default privilege ever names it;
   - on `outbox_event` only: SELECT; UPDATE on (`published_at`, `attempts`, `last_attempt_at`, `dead_at`); DELETE.
     No INSERT, so it cannot forge an event. Nothing on any other table, sequence or function;
   - policies:

     | Policy | Predicate |
     |---|---|
     | `FOR SELECT` | (`published_at IS NULL AND dead_at IS NULL`) or past retention (point 7) |
     | `FOR UPDATE` | USING `published_at IS NULL AND dead_at IS NULL`; WITH CHECK `published_at IS NULL OR published_at <= now()` |
     | `FOR DELETE` | past retention only |

   - The migration asserts at migrate time that nothing beyond this plan is held and that the role is shaped as above,
     and it fails loudly if bootstrap has not created it (the 0020 and 0024 pattern).
5. **Why this and not the alternatives D-P30 also weighed.**
   - *BYPASSRLS on a role granted one table:* the column and table grants would bound it, but BYPASSRLS is a role attribute.
     Any later grant to that role, including a default privilege added carelessly, becomes a cross-tenant read with no policy
     in the way. A NOBYPASSRLS role fails closed when someone gets the grants wrong.
   - *A SECURITY DEFINER claim function:* a third RLS-free path (CLAUDE.md 2.7), and a writing one. ADR-0012 rejected it for
     the same reason.
   - *Per-tenant polling as `kasuwa_app` with set GUCs:* `withTenantTransaction` needs a user to resolve scope, so the relay
     would need a synthetic user in every tenant and programme. It costs one transaction per tenant per tick and grows with
     tenant count, not backlog.
6. **Claiming and publishing** (`apps/worker`, a new `DATABASE_RELAY_URL` pool, max 2 connections):
   - One transaction per batch: select up to 100 rows `ORDER BY seq FOR UPDATE SKIP LOCKED`, excluding any row with an earlier
     unpublished, undead event for the same aggregate (a `NOT EXISTS` subquery, which sees locked rows too). Concurrent
     relays therefore never publish two events of one aggregate out of order.
   - Enqueue to BullMQ with `addBulk`, `jobId` = event id. Then set `published_at = now()` and commit. The mark step uses no
     `RETURNING`, because the published row no longer passes the relay's SELECT policy.
   - A crash between enqueue and commit re-enqueues the batch. BullMQ drops the duplicate while the job is retained, and the
     consumer's idempotency key (point 8) catches the rest. **Delivery is at-least-once.**
   - A failed enqueue increments `attempts`. At 10 attempts the row gets `dead_at` and leaves the relay's view.
   - The job envelope is the outbox row, Zod-parsed by the relay before enqueue and again by the consumer on receipt.
   - Consumer jobs retry 5 times with exponential backoff; then they stay in BullMQ's failed set, which is the dead-letter
     queue. Re-driving one is an operator action.
   - The relay polls every second. A `NOTIFY` wake-up hint is a later optimisation, not a dependency.
   - One queue per consuming domain (`kasuwa.events.notifications`), so a slow consumer cannot stall another.
7. **Retention.** The relay's sweep deletes published rows after 7 days and dead rows after 30 days (Q3), in batches, with a
   transaction-scoped advisory lock, as `pruneAuthTables` does. The retention rule lives in both the policy and the DELETE's
   WHERE clause and must change in both. BullMQ keeps completed jobs at least as long as the published-row window.
8. **How a consumer re-enters a tenant.**
   - It opens its own `withTenantTransaction({ tenantId, userId: actor_user_id })` from the envelope. Scope comes from
     `user_programme` as for any request. An actor who has since been deactivated or removed fails to resolve, and the event
     is dropped and counted, never widened (CLAUDE.md 6.5).
   - Inside that transaction it re-reads the outbox row by id under RLS and checks that `programme_id`, aggregate and type
     match the envelope. A missing or mismatched row is a forged or corrupt job: drop it and count it. Redis is therefore not
     trusted for scope, only for transport.
   - It then re-reads the aggregate under RLS and acts on current state, never on the payload. That also makes a reordered
     delivery harmless.
   - Idempotency lives in the consumer's own table: for example, notifications are unique on (`source_event_id`,
     `recipient_user_id`), inserted `ON CONFLICT DO NOTHING` in the same transaction.
9. **Module boundaries.** A domain publishes the event types it owns. Their schemas are its published interface (ADR-0004),
   exported from the domain's public entry point. Another domain subscribes by registering a handler on its queue. No domain
   imports another's internals or calls it directly, and the boundary lint rule stays the enforcement.
10. **Observability without PII.** The relay and consumers log event id, event type, attempt and outcome. They never log the
    payload, a tenant name or anything resolved from the aggregate. Metrics are labelled by event type only: backlog,
    age of the oldest unpublished row, publish failures, dead rows, consumer drops (forged, actor gone, not visible).
11. **Config.** `DATABASE_RELAY_URL` is required by `workerEnv`, refused by presence by `apiEnv`, `webEnv`, `realtimeEnv`
    and `migratorEnv`, and covered by the D-L94 dev-password refusal. The worker refuses to boot unless that pool logs in
    as `kasuwa_relay` and `DATABASE_URL` as `kasuwa_app` (the ADR-0013 Decision 4 check). The outbox code is the only
    importer of the relay pool.

## Tests (T-0098's acceptance suite)
- **Catalogue:** `kasuwa_relay` is LOGIN, NOBYPASSRLS, in no membership either way; its only privileges are the ones in
  point 4. `outbox_event` is in `TENANT_SCOPED_TABLES`, ENABLED and FORCED, and passes the schema-hygiene suite.
- **The relay can touch nothing else:** as `kasuwa_relay`, SELECT on `contact`, `deal`, `user`, `audit_event` and one table per
  domain gets 42501. INSERT into `outbox_event` gets 42501. UPDATE of `payload`, `tenant_id` or `programme_id` gets 42501. It
  sees no published row inside the window and cannot delete one.
- **The app cannot tamper:** as `kasuwa_app`, UPDATE and DELETE on `outbox_event` get 42501; tenant A sees none of tenant B's
  events, and an INSERT naming another tenant or an out-of-scope programme fails WITH CHECK.
- **Atomicity:** a producer transaction that throws after `appendOutboxEvent` leaves no row; one that commits leaves exactly
  one, and a scope violation (ADR-0010) rolls the event back with the change.
- **Claim semantics:** two concurrent relays never publish the same row twice in one pass; a later event of an aggregate is
  not published while an earlier one is unpublished; a crash between enqueue and commit yields one consumer effect.
- **Tenancy (in `tests/acceptance/tenancy`):** a forged job naming tenant B's tenant id with tenant A's event id, or tenant A's
  actor with tenant B's aggregate, produces no write in either tenant and no error text naming either.
- **Payload hygiene:** every registered event schema rejects a free-text string, and no fixture carries PII.

## Consequences
- **Unblocks** T-0098 (table, role, relay), T-0099 (notification contract), T-0100 (API) and T-0101 (screen); later the
  M18 invite send, search sync to OpenSearch (ADR-0014's revisit), and outbound webhooks.
- **Blast radius.** SQL running as `kasuwa_relay` reaches undispatched and expired outbox rows in every tenant. Those rows
  hold identifiers only, so the worst read is "an id changed in tenant X". The worst write is marking events published early,
  which loses notifications but leaks nothing. That cross-tenant reach is accepted, as ADR-0012 accepted the sweeper's.
- **Invariants unchanged:** still exactly two SECURITY DEFINER functions; nothing reachable from `kasuwa_app` holds BYPASSRLS.
- **Cost.** The worker opens a second, small pool. A new LOGIN role needs a secrets-manager password before `bootstrap.sql`
  runs in a real environment, then the T-0098 migration.
- **Latency.** An event reaches a consumer within about a second plus queue time. Notifications are polled by the UI in
  Phase 2 (D-L87), so that is well inside budget.
- **Honest limits.** Ordering holds per aggregate at the relay. BullMQ concurrency can still reorder deliveries, and
  consumers must re-read state rather than replay payloads. A job whose actor has lost access is dropped, so an event can be
  lost by design rather than delivered under a wider scope.

## Alternatives rejected
- **LISTEN/NOTIFY only.** Not durable: a notification sent while no listener is connected is gone, and payloads cap at 8 kB.
  Kept only as a possible wake-up hint.
- **Logical decoding or CDC (Debezium).** It needs REPLICATION, a role that reads every table's WAL regardless of RLS. It
  also needs Kafka or a connector runtime that no cell runs. It is the widest reader in the system, not the narrowest.
- **Dual writes to Redis from the producer.** The write and the enqueue can disagree on commit or crash. That is the failure
  the outbox exists to prevent (ADR-0014 says so).
- **The relay as `kasuwa_migrator`.** It would put a BYPASSRLS, schema-owning credential in a long-running process (CLAUDE.md
  2.1, db invariant 6; ADR-0012 rejected the same).
- **A relay policy for `kasuwa_app`.** Every forgotten tenant context would become a cross-tenant read (ADR-0012's reasoning).

## Open questions for @acexode
- **Q1.** Is any Phase 2 event tenant-level (for example "you were added to a programme")? If so, `programme_id` becomes
  nullable with a tenant-admin-only predicate. Proposed: no, keep it NOT NULL until a case arrives.
- **Q2.** System events with no actor (imports, scheduled jobs): use the user who started the import, or add a per-tenant
  system principal? The latter is a new identity and a decision. Proposed: the initiating user for Phase 2.
- **Q3.** Retention: 7 days for published rows and 30 for dead rows, and dead-letter after 10 publish and 5 consumer attempts?
- **Q4.** Should a dead row or a failed-set job alert (page) or only show on a dashboard? Nothing alerts today.
- **Q5.** Should the relay's sweep also be the place where BullMQ's failed set is trimmed, or does that stay manual?
