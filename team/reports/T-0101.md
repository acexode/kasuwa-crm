## What changed

- **Flag.** `crm_notifications` is T-0100's entry, which is on main (merged at 02835a5). The first commit declared it word for word, and the merge left a single entry.
- **Harness.** `run-e2e.mjs` starts `webNotificationsUrl` only when the grep can select `@p26-notifications`, or when there is no grep at all. It is the records process's flags plus `crm_notifications`, on the same build. `stack.ts` types the field. The pattern follows `webSessionUrl`, and nothing was merged from T-0125.
- **Client** (`lib/notifications-api.ts`):
  - Zod-parsed, through `requestRecords`, so no-store and no scope argument.
  - An item of an unknown kind, or an unknown kind/type pair, or one that does not parse, is dropped; the rest is kept.
  - `objectId` is read as a string, so a malformed one is drawn without a link.
  - `headId` is the newest id the server served, drawn or not. A mark-all is bounded by it.
  - `requestRecords` now reads `Retry-After` into `error.retryAfterSeconds`, and a 429 with no envelope still carries it. This is the only change to shared code.
- **Pure, unit-tested modules** (`lib/`):
  - `notification-href.ts`: `notificationHref(item, live)`.
  - `notification-poller.ts`: interval, hidden pause, wake coalescing, back-off, Retry-After hold. It takes injected timers and is tested on a fake clock.
  - `notification-count.ts`: badge text, latest answer wins by epoch, `isRise`.
  - `notification-model.ts`: local-day grouping, the sentence splitter, list updates.
  - `notification-view.ts`: the view reducer, B2 versus an empty page with a cursor, the resend delays.
  - `notification-store.ts`: wires them to `document` and `window`, with one poller per page.
- **UI** (`components/notifications/`):
  - `bell.tsx`: `aria-haspopup`, `aria-expanded`, a name that carries the count, a badge that is `aria-hidden` and not a live region, and a polite region that exists before its first message.
  - `dropdown.tsx`: a lazy dialog with a focus trap and Escape returning focus to the bell. Closing aborts the read.
  - `centre.tsx`, `notification-list.tsx`, `use-notification-view.ts`, `message-ids.ts`: the centre and what it shares with the dropdown.
- **Routes, shells, flags.**
  - `/notifications` is a real 404 when the flag is off.
  - `crmLiveNav()` lists `notifications`, plus `notifications:<type>` for the object types whose route answers. A contact record needs two flags, so the server decides.
  - Both shells draw the bell. The admin one gets no record links, because `adminLiveNav()` only reports the bell.
  - `withShellMessages` (search plus bell) replaces `withSearchMessages` on every CRM page. The admin pages add the bell's strings from the menu's keys. The bell's words are bundled only where the flag is on.
- **i18n.** 38 `notifications.*` keys in all 8 catalogues:
  - One sentence per kind and object type, with an ICU `select` for which names were served (4 variants).
  - A withheld name gives a generic sentence, never a stand-in.
  - Arabic's six plural categories on the announcement.
  - Passthroughs declared: fr ×4 and pcm ×2.
  - Typographic apostrophes before no placeholder, so ICU quoting cannot bite.

  - The CRM header's app name is `sr-only` below `sm` where the bell is live. At 360 px the header was one 44 px target too wide, so the Lite-mode toggle overflowed by 29 px. It is only applied when the flag is on.

  - Row time is a time of day in a `<time>`, under a day heading that is itself a `<time>`. Relative "4m ago" would go stale on a screen that never polls the list.

## Decisions I made that you may want to overrule

1. **Cadence 45 s** (C1 allows 30–60). Back-off after n failures is `45 s × 2^n`, capped at 300 s, with no jitter. A 429 waits `max(Retry-After, cadence)`, capped at 15 min against a nonsense header, and does not grow the failure count. A wake cannot cut a 429's wait short.
2. **Wake coalescing is 5 s**, so ten focus events are one read. A wake while failing may read even inside the failure back-off (it only ever follows a real show or focus).
3. **Writes are drawn only when answered.** There is no optimistic UI, which the throttle and lost-answer journeys require.
4. **A lost write is resent with the same body**, at +1 s and +3 s (inside the 10 s the suite allows). If it still fails, the screen shows a translated failure and asks for a count re-read.
5. **A 429 on a write is not resent by itself.** The reader's click is the resend. The list retries by itself, with the same cursor.
6. **Mark-all is bounded by the newest id the server served**, including an item of a kind this client ignores. The mock demands it, and a hidden newer unread item would otherwise be left behind.
7. **`current="notifications"`** is passed to the CRM shell. It matches no nav item, so nothing is highlighted. That is correct, since there is no nav entry for the centre.
