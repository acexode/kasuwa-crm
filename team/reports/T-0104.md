## What changed

1. **The owner joins the contact value allow-list** (`apps/api/src/contacts/contact-audit.ts`, D-L71).
   - `ownerUserId` moved from "redacted when changed" into `CONTACT_AUDIT_VALUE_FIELDS`.
   - Its `before` and `after` are recorded through the same id canonicaliser that already decided "did it move". So the
     recorded value is the lower-case uuid whatever case the client sent, and an upper-case re-send of the current owner
     records nothing.
   - A create that sets an owner records `before: null` (D-L81).
   - Because `CONTACT_AUDIT_VALUE_FIELDS` feeds the admin audit API's allow-list, `/admin/audit` now judges `ownerUserId`
     by `owner_user_id`.
   - The timeline is unchanged. `ownerUserId` is still in `TIMELINE_REDACTED_FIELDS`, so a timeline never shows an owner
     id (T6, and former-owner's timeline pins).
   - `accountId` stays redacted.
2. **A convert that creates an account audits the account** (`apps/api/src/contacts/contact-convert.ts`, D-L82).
   - After the contact event, and only when `plan.link === 'create'`, the convert writes
     `accountAuditEvent('created', account, accountChanges({ name }, null))`. That is the accounts API's own shape: label
     the account id, the contact's programme, and `[{ field: 'name', redacted: true }]`. It runs in the same `tx`.
   - It is written only after `updateContactIfVersion` matched. So a losing racer (409) rolls back its account and the
     event together, and a repeat or a refusal never reaches it.
   - No escalation was needed: the second event shares the transaction trivially.
3. **Migration `0033_unassignment_audits_each_contact.sql`** replaces 0031's trigger function with CREATE OR REPLACE.
   - The oid is kept, so 0031's two triggers call the new body and there is no DDL on `user_programme`.
   - Steps 0 and (a) to (e) are verbatim: refusal, offboarding, READ COMMITTED, then every membership lock in ascending
     order before any contact row, then the same-key rewrite.
   - Step (f) is still one `UPDATE contact ... RETURNING`, now returning `c.id`. It feeds ONE `INSERT ... SELECT` over a
     `UNION ALL` of two parts:
     - the unchanged programme events;
     - one contact event per returned row: `updated`, `object_label` the contact id, the contact's programme, the remover as
       actor (`system` with no session user, P3), and `changes = [{ownerUserId, before: removed id, after: null,
       redacted: false}]`.
   - So per-contact events exist exactly where the programme event does and nowhere else.
   - The actor's role name is read once per tenant (a CTE) rather than per row.
   - SECURITY INVOKER, `search_path = pg_catalog`, EXECUTE revoked from PUBLIC. A DO block checks the triggers, invoker
     rights, the pinned path, the body's lock-before-UPDATE order, that no serving role can EXECUTE, and that the definer
     census is still 2.
4. **Contracts.**
   - `admin.openapi.yaml` `AuditChange`: the contact value allow-list now names `ownerUserId` (staff ids, lower case,
     judged by `owner_user_id`).
   - `records.openapi.yaml`, three descriptions:
     - createContact: the audit's value fields, `ownerUserId` included. The old text said every change was redacted,
       which had been stale since T-0061;
     - updateContact: the same, plus the no-op rule;
     - convertContact: one contact event, plus one account `created` event when it creates the account.
   - Only descriptions changed, with no schema shape or enum change. The timeline's `FieldChangeWithValues` enum
     deliberately does not gain `ownerUserId`.
   - D-L97: no e2e mock validates against a changed shape. I regenerated `admin-mock.generated.ts` and it was
     byte-identical apart from line endings, so I restored it. Nothing was re-pinned.
5. **Tests.**
   - Unit tests in `contact-audit.test.ts`: owner values, lower case, create and clear.
   - Unit tests in `audit-field-security.test.ts`: `ownerUserId` is a value field judged by `owner_user_id`. It is
     removed from the "never a value" list.
   - Integration test in `contact-convert.integration.test.ts`: exactly one account `created` event, names only, and none

the Testcontainers Postgres 16 under Docker Desktop: one DELETE of one membership owning 100,000 contacts, three runs of
each body in alternation, each rolled back.

|---|---|---|
| 0031 | 6.9 to 8.8 s | 63 to 65 MB |
| 0033 | 11.7 to 14.0 s | 161 to 308 MB |

308 MB figure includes full-page images after a checkpoint. This host is slower than 0031's review host (2.45 to 5 s), so
carry the ratio. 0031's rule for a future removal API (a cap, or an async batched job) applies with more force.
