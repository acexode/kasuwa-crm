# T-0161 report: D-L204 polish

## What changed
- **Studio settings menu with the docked editor.** `object-panel.tsx` marks its root `data-editor-docked` while the editor is docked (1280 and up). `admin-shell.tsx` sees it with CSS `:has()` (`xl:group-has-[[data-editor-docked]]/shell:...`): the 272px sidebar becomes the drawer it already is below 1280 (hidden, menu button back in the bar, over the content when opened). Closing the editor brings the sidebar back. No prop or context, so no admin route ships anything new. A browser without `:has()` keeps the old sidebar.
- **Deal breadcrumb.** `components/deal/use-programme-name.ts` reads `listMyProgrammes` once; the pipeline crumb is "Pipeline · Programme" through the existing `pipeline.select.qualified` message, which the deal bundle already carries. The detail never lists pipelines, so it cannot tell whether a namesake exists and always qualifies. While loading, on a failed read, or when the programme is not one of the caller's own, it is the pipeline name alone, never an id.
- **Search dropdown size literals** are tokens: `OVERLAY.searchDropdown` (600), `searchDropdownWide` (680), `searchDropdownMaxWidth`, `searchDropdownMaxHeight`, `searchDropdownMaxHeightWide`, and `searchScopeMenu` (340, the scope menu beside it). `min-[1280px]:` became `xl:` as in T-0151. `pnpm ui:tokens` regenerated `tokens.generated.css` and `tailwind-preset.cjs`.

## What was hard / decided
- The brief said "three literals"; the dropdown had these five (width, wide width, two max-heights, max-width) plus the scope menu's width. I tokenised all of them rather than leave two behind.
- `:has()` over a context: a context would put a provider in every admin route's chunk for a screen that needs it on one.
- The deal mock already declares `listMyProgrammes` (the file's own header lists it), so the extra read is not a violation and no pinned mock changed.

## Proposed to the lead (acceptance suites NOT edited)
1. **Command-palette scope pattern**, `tests/acceptance/records-ui/command-palette.acceptance.test.ts` line 757:
   ```
   /programmeIds?|ownerUserIds|(set|append)\(\s*['"`](programme|owner|scope)|['"`]x-[\w-]*(programme|tenant|scope)/i
   ```
   The bare `programmeIds?` and `ownerUserIds` alternatives also match response-schema fields a client parses. Narrowed, keeping the intent (nothing is SENT as scope):
   ```
   /(set|append)\(\s*['"`](programme|owner|scope)|['"`]x-[\w-]*(programme|tenant|scope)|\b(params|query|body|headers)\b[^;\n]*\b(programmeIds?|ownerUserIds)\b/i
   ```
2. **The attribute match**, `/(aria-label|aria-description|placeholder|title|alt)="[^"]*[A-Za-z][^"]*"/g`, in 17 suites (`contacts-list`, `command-palette`, `contact-record`, `activities-screen`, `deal-detail`, `accounts-screen`, `account-record`, `custom-values`, `duplicates-screen`, `leads-screen`, `notifications-screen`, `import-screen`, `pipeline-board`, `customisation-studio`, `p01-auth-screens`, `script-builder`, `script-agent`). `` matches after the hyphen, so `data-placeholder="x"` and `data-title="x"` are judged as user-facing attributes. T-0151 renamed the real ones, so this is a false positive waiting for the next one. Narrowed:
   ```
   /(?<![\w-])(aria-label|aria-description|placeholder|title|alt)="[^"]*[A-Za-z][^"]*"/g
   ```
