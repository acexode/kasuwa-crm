## The contract, and the mock generated from it

Agent 1 published `docs/api/auth.openapi.yaml` before implementing. Both files
are committed here so the branch is self-contained, including the **later
revision** in which `challengeId` stopped being a UUID and became the opaque
`<tenantUuid>.<challengeUuid>`.

> That change was harmless here, and deliberately so: `auth-api.ts` types the id
> as `z.string()` and the screens echo it back. There is no `.uuid()`, no regex
> and no branded type anywhere in `apps/web` — checked by grep after the
> message arrived.

`tests/e2e/support/auth-mock.generated.ts` is **generated** from the spec by
`tests/e2e/scripts/generate-auth-mock.mjs` (`pnpm --filter @kasuwa/e2e
generate-mock`). Every status code, every example body and the
`x-kasuwa-implemented` flag are read out of the YAML; nothing is retyped.

`tests/e2e/support/auth-mock.ts` holds only the part a set of examples cannot
express — the state machine: which attempt is the fifth, whether the code
matched, whether `sms` is still a 501. **One property is load-bearing in it:**
account existence is consulted in exactly one place, the password comparison.
Everything else — status, body, the lockout counter — is identical for a real
address and an invented one. A branch on "does this account exist" anywhere
else would be the enumeration oracle `P01/1a` was drawn to avoid.

Prism is still the right tool for poking at the contract by hand, and
`docs/api/README.md` explains it. It is not in the e2e run because it needs a
network fetch at test time and cannot express "this is the fifth attempt".

## Things the design got right that I did not simplify

- **`P01/1a` does not name the field.** The e2e test tagged `@enumeration`
  compares two separate browser contexts — unknown address versus wrong
  password — and asserts the message, the error code, the remaining-attempts
  counter **and** `aria-invalid` on both fields are identical. The last one
  matters: marking only the email invalid would re-introduce the distinction in
  the accessibility tree, where only a screen-reader user would meet it.
- **`P01/1b` names the timezone.** `lib/retry-time.ts` converts `retryAt` into
  the IANA zone the server sent and renders the abbreviation with it. Unit
  tests assert 13:47 UTC renders as 14:47 in Lagos and 16:47 in Nairobi, and
  that an unresolvable zone falls back to UTC **and says UTC** rather than
  quietly showing local time under a zone name we could not resolve. Per the
  coordinator's note, the screen renders what the API sends and derives nothing.
- **`P01/1d` is not a spinner.** Skeleton, a sentence at four seconds, then an
  offer of low-bandwidth mode. Exercised under the real 256 kbps / 300 ms
  profile. The timer runs on the request, not on a render, so it cannot fire on
  a fast connection.
- **`P01/2` takes a pasted code.** The e2e test dispatches a real
  `ClipboardEvent` with a `DataTransfer`, not six keystrokes — typing would pass
  even with no paste handler at all, which is precisely the bug. Paste fills
  from the focused box onward, digits only, and focus lands on the first empty
  box. Backspace on an empty box steps back and clears; arrows, Home and End
  work; each box announces "Digit 3 of 6" rather than "edit text".
- **`P01/2b` swaps the button.** An expired challenge turns "Verify" into "Send
  a new code". Leaving it as "Verify" invites the user to press it and be told
  again.
- **Lite mode drops the trust panel and the federated buttons**, and says so.

## Two deviations from the design, both forced

1. **The sign-in form has a Workspace field.** The design shows email and
   password only; the contract requires `tenantSlug`, and it is identity rather
   than scope, so the client has to supply it. Raising it here rather than
   inventing a lookup.
2. **The language menu offers two languages, not seven.** `SUPPORTED_LOCALES`
   is derived from catalogue completeness plus a named reviewer (D-P1). Six
   catalogues are structurally complete and held back. The menu shows what the
   gate offers, and the e2e test asserts the count is exactly what the gate
   returns rather than a number typed into the test.

## i18n

95 new ids, added to **every** catalogue: `en`, `fr`, `ha`, `ig`, `sw`, `pcm`,
`yo` and `ar`. Error strings follow `auth.error.<code>`, matching the contract's
convention, and the screens switch on `code` and never on `message`.

`pnpm i18n:validate` is clean: every menu language is structurally sound and the
six held-back ones are held back for attestation only.

**These are machine-drafted translations, not reviewed ones.** They are complete
and they parse; nobody who reads Hausa, Igbo, Yorùbá, Swahili, Pidgin or French
has read them. That is what D-P1 exists for and it is why none of them reach the
menu. They should not be treated as finished copy.

### One thing that cost time and will cost the next person time

The T-0009 acceptance suite extracts placeholder names with a regular
expression, `/\{\s*(\w+)/`, which also matches the **first word of a plural
branch body**. So `one {Encore # tentative}` is reported as an unknown
placeholder named `Encore`, and the French catalogue failed.

`completeness.ts` fixed this for itself by parsing the AST, and its comment says
at length why the regex is wrong — but the acceptance test still has the regex,
and acceptance tests may not be edited. It only bites Latin script (`\w` is
ASCII), which is why the Arabic and Yorùbá branches passed unchanged while
French, Hausa, Igbo and Swahili did not.

I complied: every plural branch in those catalogues now begins with `#`. That is
a real constraint on the wording — it forbids every plural form that does not
lead with the number, which is a normal way to write "a single attempt" in most
of these languages. **Worth fixing in the acceptance test** by reusing
`placeholderNames()` from `completeness.ts`, which already does it properly.

## The byte budget — measured, not asserted

Against a **production build** (`pnpm --filter @kasuwa/web build`, then
`next start`), a cold load of `P01/1`:

| | Transferred | FCP |
|---|---|---|
| Unthrottled | **256,948 bytes** | 216 ms |
| 256 kbps / 300 ms | **256,948 bytes** | 1,784 ms |

Breakdown: JavaScript 164,577 · fonts 78,598 · CSS 7,513 · HTML 6,260.

Re-measured after the session was interrupted, on a clean `next build` served
by `next start`, through the same Chrome DevTools Protocol instrumentation
`tests/e2e/support/metrics.ts` uses. Transferred bytes are stable to within
~40 between runs; FCP is not (216 ms against 452 ms unthrottled on an earlier
measurement), which is what you would expect of a wall-clock number on a
machine doing other work. **The byte count is the number to hold anyone to;
the paint time is an observation.**
Against PRD 2.13's 300 KB ceiling that is **about 16% of headroom**, which is
less than it sounds for the first screen in the product.

Two observations worth acting on before thirty screens exist:

- **JetBrains Mono costs 31 KB** and is on the critical path because the
  password field uses `font-mono`. That is a lot of bytes for one field.
- The two 45–55 KB shared chunks are React and the framework; `intl-messageformat`
  is in there too. The catalogues are **not** — the server-resolves /
  client-formats split (`bundleMessages` + `createBundleTranslator`, new in
  `@kasuwa/i18n`) keeps all nine on the server, and that saving grows with every
  screen.

The e2e assertion is written with the real number — `assertWithinByteBudget(...,
270336)`, pinned just above the measurement rather than at the NFR — and is
marked `test.fixme` with the reason. **The harness runs `next dev`**, where the
same page transfers 2.3 MB (D-L28). A budget set against a dev bundle is
meaningless in both directions, and the instruction was not to split the
difference. T-0010 makes the e2e job build first; flipping one line then turns
this into a live gate.

### The isolation suite is intermittently red, and I am stopping rather than chasing it

work around it. It is red, not reliably, and here is everything I know.

**Did my change make this worse? Partly, and I should say so.** I added a
sixth test to the `@harness` subset — the web-route tenancy case the T-0008

**What I did not do:** weaken the harness config, loosen a timeout, retag the

`apps/web`'s lint script covered only `app/`; it now covers `components/` and

### Two environmental flakes, neither in this change

Both cost me runs and both will cost the next person runs, so they are written
down rather than left to be rediscovered.

- **Playwright's trace writer fails on Windows** with `ENOENT` while writing a
  `.network` recording under `.artifacts/test-results/.playwright-artifacts-N`.
  I first wrote this up as an occasional flake that a retry cleared. **After
  the interruption I could not get a whole-suite run green at all**, so it is
  worse than that and I am correcting the record.

  The shape: the test body passes, `browserContext.close` then throws, and the
  failure takes `.artifacts/stack.json` with it — so every test after that
  point fails in milliseconds with "no running stack". Which test trips it
  moves between runs, and it looks exactly like a real failure in whichever
  test it hits.

  What I established. It is **not** specific to Playwright or to this change:
  `next build` on the same machine failed the same way in its own build-trace
  step (`ENOENT … page.js.nft.json`), and a plain `rm -rf` of the artifacts
  directory failed with "Directory not empty". That is the Windows Smart App
  Control / filesystem problem already documented under D-L20, not something
  this branch introduced. **30 orphaned Chromium processes** left by earlier
  killed runs made it worse; clearing them helped and did not cure it.

  What I tried. `page.unrouteAll` in an `afterEach` — kept, as hygiene, with a
  comment saying plainly that it did not fix this. Moving `tracesDir` out of
  the repository — **reverted**, because Playwright derives the per-context
  recording directory from `outputDir` and the change did nothing its own
  comment claimed.

  I did not weaken the harness config to get a green run. Tag-scoped runs are
  green, including the `--grep @harness` run the isolation suite actually
  shells out to, so the blocking gate is unaffected. **Someone should
  reproduce this in CI or the devcontainer before concluding anything** — if it
  is machine-specific it costs nothing, and if it is not, `retain-on-failure`
  tracing under `outputDir` needs rethinking, which is Agent 12's call.
- **Two `pnpm test:e2e` invocations in one worktree corrupt each other**, and
  this one is a harness defect rather than an environment quirk. Both write
  `tests/e2e/.artifacts/stack.json`, and the `@over-budget` path writes
  `{"webUrl": "", "apiUrl": ""}` there because that run needs no stack. A
  concurrent normal run then reads empty URLs and every remaining test fails
  with `navigating to ""` — which looks exactly like a broken route. I lost
  three runs to it before checking the file. Worth a lock, or a per-invocation
  artifacts directory, before CI runs the suites in parallel.
- **Running `next build` in `apps/web` breaks the next `next dev`.** The
  harness starts a dev server against the same `.next` directory and it fails
  with a missing `app-paths-manifest.json`, which surfaces as 500s in the e2e
  run and looks like a routing bug. `rm -rf apps/web/.next` fixes it. This will
  matter for T-0010, which is going to put a production build and a dev server
  in the same job.

## Open questions for the lead

1. **How does the web process learn the API origin?** It is
   `NEXT_PUBLIC_API_URL`, read once in `next.config.mjs` — a file the lint
   config already exempts — and rewritten same-origin so no app code touches
   `process.env`. `@kasuwa/config` would be the right home, but it requires
   `DATABASE_URL` and the web process has none. Worth settling before a second
   app needs it.
2. **`?locale=ar` renders a registered-but-unoffered locale once.** It sets no
   cookie and appears in no menu; `middleware.ts` carries it as a request header
   so the layout can set `lang`/`dir`. It is how RTL is proven against real
   strings, which is why `ar` is in the repository — but it is reachable by
   typing it, and someone should agree that is acceptable.
3. **`P01/1a` renders `attemptsRemaining` verbatim.** The coordinator notes that
   a real unknown address gets a 401 while a real locked one gets a 429, so the
   *status* still differs even though the copy does not. Nothing in the UI
   surfaces that, but it is the API's property to fix if it matters.
4. **New dependency:** `yaml@^2.9.1`, a devDependency of `@kasuwa/e2e`. The mock
   must be generated from the contract, the contract is YAML, and the workspace
   had no parser. Already in the store as a transitive dependency.
5. **Icons added** to `packages/ui/icon-subset.txt`: `passkey`, `domain`,
   `visibility`, `visibility_off`, `lock_clock`, `timer_off`, `key`, `public`,
   `language`, `verified_user`, `phone_iphone`. The subset is 80 glyphs and
   10.5 KB. `pnpm ui:fetch-fonts` now also emits
   `packages/ui/src/icons.generated.ts`, so an unlisted icon is a **compile
   error** rather than a blank box discovered in production.
