# T-0191 — Inbox realtime push

## What changed

- `recordOutboundMessage` appends `inbox.message_persisted` in the same tenant
  transaction as the message insert. The API send path calls that function on
  the request transaction, so the event commits with the send or not at all.
- Payload is four ids: tenant, programme, conversation, message. The schema is
  strict. A body, phone or email does not parse.
- The type is registered in `@kasuwa/db`'s outbox registry and routed on the
  existing `kasuwa.events.notifications` queue. Migration 0041 checks the
  shape of `event_type`, not a closed list, so no migration was required.
- The worker's existing outbox consumer publishes this type to Redis channel
  `kasuwa.realtime.events` (ADR-0020). Other types still go to the
  notifications handler. The published JSON is tenant, programme, type and
  the two ids. The message body is not selected and not sent.
- `apps/realtime` delivers a frame only when the socket's tenant matches and
  the programme is in the set fixed at connect, and in the subscribed subset
  of that set. A later subscribe frame cannot add a programme.

## Hard parts

- A new BullMQ queue would make `relayOutboxBatch` reject every caller that
  binds only `kasuwa.events.notifications`. Those callers are acceptance
  tests, which this task must not edit. The inbox event therefore rides the
  existing queue, and the consumer branches on event type.

## Left out

- `tests/acceptance/inbox/realtime-push.acceptance.test.ts` was not created.
  A new acceptance file needs the lead.
- Inbound messages have no persist path in this slice, so only the outbound
  send appends the event.
- No browser client and no second bus. No new `SECURITY DEFINER` function.
- No feature flag. The consumer is always on, as notifications already are,
  so a relayed event is not left sitting in the queue.

## Open questions

- None. The acceptance suite for this task still has to be written by the lead
  before the task can be closed.
