# T-0050 — en-XA pseudo-locale preview is development and test only

**Agent 11** · branch `agent11/T-0050-pseudo-locale-gate` · commit `9fbbea8` (on `5324342`, suite) · D-P15

## What changed

- `apps/web/lib/locale.ts`
  - New `resolveActiveLocale({ preview, cookie, nodeEnv })`, a pure function, plus the `LocaleNodeEnv` and `LocaleRequest`
    types the suite pins.
  - `en-XA` previews only when `nodeEnv` is `development` or `test`. This is an allowlist, so an unknown value fails closed.
    `ar` and the other registered locales preview in every environment, as before.
  - A refused preview is treated as absent: the request falls through to the menu cookie. The match is exact, with no
    trimming or case-folding, so there is no second spelling of `en-XA`.
  - `activeLocale()` now reads the header, the cookie and NODE_ENV, then delegates. It decides nothing itself.
- NODE_ENV is read at runtime through `flagProcessNodeEnv()` from `@kasuwa/config/feature-flags`. This is the same `.env`-free
  read the flag boot guard uses, and one of the two config entry points `apps/web` may import. The code never uses
  `process.env.NODE_ENV`.
- `apps/web/lib/locale.test.ts` has 19 unit tests for the resolver.
- `apps/web/CLAUDE.md`: the `?locale=en-XA` note now says it is dev and test only, and gives the runtime-read rule.

## What was hard

Nothing in the resolver itself. The care went into proving that the runtime read works on the built server, which only the
e2e can show.

## Left out

- Nothing in `middleware.ts`. The gate belongs in the resolver, because a client can send the header directly.
- `createTranslator('en-XA')` still produces pseudo text if called directly in production. Only the request path is gated,
  which is what D-P15 and the suite ask for.
