## What was hard / decided
- **The widget list exists twice by necessity.** The API cannot import from an app, so `home-layout.schemas.ts` repeats `WIDGET_TYPES`, the spans and the roles. `home-layout.schemas.test.ts` reads `home-model.ts` and fails if they drift. The web client imports `home-model.ts`, so there is one copy on that side.
- **The contract's cap is 19 and the catalogue is 20 widgets.** A layout holding every widget once would be a 400 and the save would silently fail (the store never throws), so Home would keep it for the visit only. The suite pins 19, so I did not change it. Raising it to 20 is a one-line contract change; the lead should decide.
- **`deleteHomeLayout` has a caller** (Reset), as the suite header says; it is not a PUT of the default.
- PUT is one `INSERT ... ON CONFLICT (tenant_id, user_id) DO UPDATE`. It needs SELECT, INSERT and the UPDATE column grants, and all three are granted.

## Flags for the lead (re-pin)

- `requestRecords` (shared) gained the `DELETE` method; it ships in every records screen's chunk, by a handful of bytes. If the byte-budget run complains, that is why.
