## What changed

### One timeline, two subjects (no fork)

**Domain.** The T-0061 statement moved, unchanged in behaviour, to
`packages/domain/core/src/timeline/record-timeline.repository.ts`, parameterised by a closed
`TimelineSubject` (`'contact' | 'account'`). The only per-subject SQL constants are:

| subject | `audit_event.object_type` | activity link | cursor key |
|---|---|---|---|
| contact | `contact` | `contact_id` | `k` (T-0061's, unchanged) |
| account | `account` | `account_id` | `a` |

Each is a constant chosen by the union, never by input. Same UNION ALL of the two sources, the
same millisecond keyset with the `COLLATE "C"` id tie-break, the same item ids, the same
`LIMIT n+1`, the same fail-closed row parse. The activity branch now also selects `a.version`.
`contact/contact-timeline.repository.ts` and the new `account/account-timeline.repository.ts`
are thin wrappers (the contact one keeps T-0061's exported names and cursor format).

**API.** `apps/api/src/timeline/record-timeline.ts` holds the shared operation
(`readRecordTimeline`): scope first (404), then the query (400), then both matrices loaded once,
the allow-list of visible change fields handed to SQL (so omission happens before the LIMIT),
and the activity item mapping. Each timeline supplies a small spec: whose matrix judges its
changes, its change-field allow-list, its change-row mapping, and the activity link that puts
an activity on it (`contactId` or `accountId`). `contacts/contact-timeline.ts` keeps its value
rules (D-L72) and is now one spec on that operation.

### Version on the activity item (D-L85)

`ActivityItemWire.version` is the row's `activity.version`, read live, never judged by field
security. Both timelines get it from the one `activityItem` mapping.

### `GET /api/v1/accounts/{accountId}/timeline` (listAccountTimeline)

- `AccountsController.timeline`, `apps/api/src/accounts/account-timeline.ts`.
- **A non-uuid id is the 404**, the same `notFound()` body as getAccount's for an absent id
  (`AccountIdParam.safeParse` failure becomes `notFound()`), before anything is read. The other
  account operations keep their 400.
- **Field changes are always `{ field, redacted: true }`**, whatever an audit row stores. Only
  the nine Account wire names in `AccountFieldChangedItem.field` can be items; `name` is never
  withheld, the rest follow the account matrix in the account's programme, failing closed. Any
  other name (`consentState`, `emails`, `programmeId`, ...) gives no item, and there is no
  `consent_changed` on this page.
- **Activities**: only `account_id` = the account (activity_account_keyset_idx; no migration).
- **Audit events**: only those recorded in the account's programme (`e.programme_id = $2`).
- **Cursor**: `{ a: accountId, t: ms, i: itemId }`, base64url JSON, strict. A contact cursor
  (`k`), a list cursor (`c`/`i`) or another account's cursor is 400 `invalid_cursor`; position
  only (the account's own id, a time, an md5 item id).

### `Cache-Control: no-store` on every records answer (closes D-L90's follow-up)

- **One middleware.** `apps/api/src/common/no-store.middleware.ts` is the only copy. T-0078's
  `admin/audit/no-store.middleware.ts` (#105) is deleted; `AdminAuditModule` and its unit test
  import the shared one. Only the import paths changed; what the audit tests assert is
  unchanged.
- **Every records route.** `AppModule.configure` applies it to `RECORDS_CONTROLLERS`: contacts
  (both timelines included), leads, accounts, activities and `me`. Every 200, 400, 404, 401 and
  scope-header 400 on them carries `no-store`. The per-handler `@Header` decorators stay.
- **Where `@Header` stops (correcting my first report and D-L90's wording).** Nest sets
  `@Header` *after the guards* and *before* the interceptors and the handler
  (`router-execution-context.js`). So a 400 or 404 thrown inside a handler already carried it;
  what never did is the guard's 401 and its scope-header 400. I proved this with a mutant that
  removes the middleware: the new integration test then fails 5 of 12, exactly the four guard
  401s and the scope-header 400, while the handler 404s and 400s still pass.
- **New integration test** `apps/api/src/contacts/records-no-store.integration.test.ts`, 12
  cases through the real guard, filters and database. It covers the contacts guard 401 and a
  contacts 404 as you asked, plus a contacts 200, scope-header 400 and bad-id 400, the 404s of
  both timelines and of an account, and the 401s of leads, activities and `me`.

### Security review follow-ups (third commit, 7256559)

- **Scope uses the get operations' own lookups.** The shared operation used to resolve scope
  with `findActivityTargetProgramme`. Each timeline spec now carries `findRecordProgramme`:
  the account timeline calls getAccount's `findAccountById` and the contact timeline calls
  getContact's `findContactById`. A future soft-delete (D-P27) therefore cannot 404 a record on
  one operation and serve it on the other. The 404 is the same `notFound()` as before, so the
  bodies are byte-identical (the suites pin them and pass). A unit test checks that each spec
  runs exactly its get operation's statement and values, and that a miss is `null`.
- **Runtime subject guard.** `timelineSubjectConstants()` throws `TimelineSubjectUnknownError`
  for anything that is not an own key of `SUBJECTS`. That covers values the type forbids but a
  cast could pass, including `'__proto__'`, `'constructor'` and `'toString'`.
  `listRecordTimeline` calls it first, before the scope check and before any SQL is built. The
  cursor encoder and decoder call it before parsing. Unit-tested with a transaction that
  records statements: no statement is ever issued for an unknown subject.

## What was hard

- Keeping the extraction behaviour-neutral for the contact timeline: T-0061's cursors had to
  stay byte-identical (`{ k, t, i }`), so the subject is told apart by the key name rather than a
  new field in every cursor.
- Working out where `@Header` stops. It is set after the guards, so only the guard's answers
  needed the middleware. The mutant run settled it.

## Decided here (the suite leaves it to the builder)

- **A withheld activity `contact_id` on the account timeline hides nothing.** The activity item
  carries no contact link at all, and the link that puts an activity on this timeline is
  `account_id`, which is judged (withheld: no activity items). Hiding it as well would make an
  account-plus-contact activity disappear from the account for a reader who may see the
  account link, with nothing disclosed by showing it. Subject and body still follow their own
  rows.
- **An activity's item id is the same on both timelines** (`ti_` + md5 of the activity id).
