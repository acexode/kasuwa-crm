## What changed

- **`packages/permissions/src/policy.ts`:**
  - A new programme action, `contact.claim_and_set_status`. It is held by `agent` only, and implied by `admin`, which
    holds every programme action.
  - `contactUpdateWithinClaim(body, callerUserId)` checks the body. The body must be a plain object, and its keys
    must exactly match `version`, `status` or `ownerUserId`. `ownerUserId`, if sent, must be the caller's own id,
    compared case-insensitively.
  - `canUpdateContact(grants, programmeId, callerUserId, body)` is the whole decision. `contact.write` allows any
    body; otherwise the caller needs the narrow grant in that programme and a body inside it.
  - The allow-list stays in code: no catalogue column, no migration.
- **`apps/api/src/contacts/contacts.service.ts`:** update calls `canUpdateContact` on the raw body, before validation,
  with `tx.session.userId` as the caller.
  - D-L53's order holds: 404, then 403, then 400.
  - Unchanged and still applied after the decision: field security, the D-L67 owner check, the version check and the audit.
  - Create still needs `contact.write`.
- **`apps/api/src/contacts/contact-audit.ts`:** review fix. Uuid fields (`ownerUserId`, `accountId`) are lower-cased
  before the "did it move" check, so an upper-case spelling of the stored id no longer records a false change.
- **`docs/api/records.openapi.yaml`:** description text only (createContact and updateContact). FEATURES.md is unchanged.
- **Unit tests:**
  - `policy.test.ts`:
    - The agent set holds exactly one action.
    - A `canUpdateContact` block covers allowed bodies and refused shapes, including case-variant and padded keys
      (`Status`, `OWNERUSERID`, `ownerUserID`, `" status"`).
    - It also covers per-programme judgement, out-of-scope programmes, admin, the tenant-admin flag and the four
      read-only sets.
  - `contact-audit.test.ts`: an upper-case id equal to the stored one is no change; a different id or a cleared one is.
    Confirmed to fail without the fix.
