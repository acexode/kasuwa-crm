## Tests I think are wrong (not edited)

1. **activity-table, "the catalogue check rejects a body or subject not classified pii, and a stray field"** (around l.1709). The lead edit (ac18252) added `['deal_id', 'deal']` to `catalogueProblems`' lookup pairs and `deal_id` to `REQUIRED_FIELDS`. It did not update this self-check's `good` fixture, which builds every required field as `text` except `contact_id` and `account_id`. So `catalogueProblems([object], good)` now reports `deal_id: text {}, expected a lookup to deal`. The check is pure and never touches the database, so no implementation can pass it. The fix is one more arm: `name === 'deal_id' ? field(name, { type: 'lookup', config: '{"targetObjectApiName":"deal"}' })`. The real catalogue tests in that suite (per tenant, and a fresh tenant) pass.
2. **features-register (3 tests).** `team/FEATURES.md` was already stale at ac18252 (`missing row: operation listDealTimeline`, from the 8077fef contract edit). After the flip it also needs that row as `built`. It is generated (`pnpm features`) and lives under team/, which I may not edit. The lead needs to regenerate it.

## What was hard

- The FK needs a unique key on `deal (tenant_id, programme_id, id)`, and 0036 only has one with `pipeline_id` third. D-L120 asks deal keys to lead with `(tenant_id, programme_id, pipeline_id)`. The new key leads with tenant and programme, then `id`, which the primary key already makes globally unique. An INSERT naming another tenant's deal id therefore fails on the PK first, exactly as before, and the key adds no oracle. The header argues this and section 8 checks the leading two columns. The suite leaves the key's name to the builder, so it expects one.
- Two of my own section-8 checks failed on the first run and were fixed before commit:
  - a two-array `unnest` cannot be schema-qualified;
  - a single column's `pg_get_indexdef` carries no `DESC`, so the direction is read from `indoption`.
