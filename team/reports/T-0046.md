# T-0046 — Permissions hardening, the D-L55 gaps (Agent 1)

**State:** merged to `main` (#85) as migration 0021, which adds three RESTRICTIVE policies on `user_programme`.

**What changed.** Each of these now requires a tenant-admin session:
- UPDATE. A non-admin gets 0 rows.
- INSERT that carries a permission set. A non-admin gets 42501.
- DELETE, which is also limited to programmes in the session's scope.

The side doors are closed too: delete-then-reinsert, rewriting `user_id`, and upsert. No new SECURITY DEFINER function was added.

**Evidence:**
- Lead suite: 19/19. With 0021 removed, 9 of those tests fail.
- Other suites: permissions 28/28, adversarial 17/17, and all tenancy suites pass. 127/127 after the review fixes.
- Integration: 109/109.
- Migration review: pass with findings, run on real Postgres 16. The fixes (2 s lock wait, row-lock warning) are in.

**Hard part:** a column REVOKE answers 42501 and misses a `user_id` rewrite. Guarding the whole row with restrictive policies covers both.

**Open:**
- T-0047: `kasuwa_app` can DELETE a `"user"` or `programme` row, and the cascade then removes memberships. That is a second lockout path.
- A non-admin can still insert a membership with no permission set. It grants nothing.
- The `app.user_id` forging residual (ADR-0010).
- The repeated EXISTS clause could move into one invoker-rights SQL function.
