## What it does now

A real user signs in with an email and a password, passes a TOTP second factor,
and every later request carries a server-issued session the API resolves
against the database. `KASUWA_AUTH_MODE=stub` still exists and the production
boot guard still refuses it.

Two commits:

1. **The contract, alone and first.** T-0007 (Agent 11) is in flight alongside
   this task and had to build the P01 screens against a mock. Endpoints, success
   shapes and every failure body are in `docs/api/auth.openapi.yaml`, with
   `x-kasuwa-implemented` on each operation saying whether it is real.
2. **The implementation.**

### The shape of it

- `POST /auth/sign-in` verifies the first factor and opens a challenge. It hands
  out nothing usable on its own.
- `POST /auth/mfa` verifies the code and issues the session. The only route in
  the API that returns a token.
- `POST /auth/mfa/challenge`, `POST /auth/sign-out`, `GET /auth/me`,
  `POST /auth/sso/lookup` are implemented. `sign-up`, `verify-otp` and
  `verify-otp/resend` are published and answer `501 not_implemented` — see
  "What I did not do".
- Five new tables in `packages/db/migrations/0002_authentication.sql`:
  `user_credential`, `user_mfa_factor`, `auth_challenge`, `auth_session`,
  `auth_attempt`. All carry `tenant_id`, all `ENABLE` **and** `FORCE` RLS, every
  policy's `WITH CHECK` is identical to its `USING`, every foreign key to a
  tenant-scoped parent is composite on `(tenant_id, id)`. All five are in
  `TENANT_SCOPED_TABLES` and mirrored in `schema.ts`.
- argon2id via `hash-wasm`; TOTP written by hand against the RFC 6238 vectors.
- Sessions are opaque: `ksw_s1_` plus 32 random bytes; only the SHA-256 is
  stored. ADR-0008 has the reasoning.

### Authentication changed who, not what

This was the point of the task and it is the thing to check first.

- `tests/acceptance/tenancy/` passes **unmodified**. I did not touch anything
  under `tests/acceptance/`, and I did not rename the `.pending.` file.
- No response anywhere in the API carries a programme id, a role or a
  permission. `/auth/me` is identity only. There is a unit assertion and an
  integration assertion that the session response matches no
  `/programme|role|permission/`.
- Scope is still resolved from `user_programme` inside `withTenantTransaction`.
  I changed nothing in `packages/db/src/session.ts`.
- `x-kasuwa-programme-ids` and friends are still a 400, now with or without a
  session.

### Two layers, not one

The guard resolves the token through `app.resolve_session`, then the
interceptor re-reads the same row **inside the tenant transaction, under RLS,
with explicit `tenant_id` and `user_id` predicates**. A mistake in the first
cannot serve a request past the second. This is also what makes a disabled user
and a revoked session fail on the *next* request rather than at expiry.

## The three things worth arguing about

### 1. Two SECURITY DEFINER functions now exist

Authentication has a real bootstrap problem: every RLS policy reads
`app.tenant_id`, and before a session exists nobody has set it. The answer is
`app.resolve_tenant_by_slug(text)` and `app.resolve_session(bytea)` — both
`STABLE`, both taking one opaque argument, both pinning `search_path`, both
returning identifiers and nothing else. They are the only RLS-free read path in
the system and the migration says so in a comment. **A third one should be
refused.**

Everything else in the sign-in path runs through `withAuthTransaction`
(`packages/db/src/auth.ts`), which opens a transaction, pins the resolved
tenant, and sets `app.programme_ids` to `'{}'` for the whole transaction — so
an authentication transaction can read no programme-scoped row at all. Not one
contact. That property is worth more than any amount of care in the caller, and
it is the thing to check if this file is ever changed.

### 2. A bug that would have passed its own tests

Every failure path has a side effect that must survive: a failed sign-in
increments a counter, a wrong code burns an attempt. Throwing from inside the
transaction rolls it back and silently discards exactly the row that was meant
to record the failure. The counter never advances, nothing ever locks, and a
test asserting "five failures lock the account" would pass only if it happened
to run five *separate* transactions that each persisted — which they do not.

I hit this: the lockout test failed with `expected 4 to be 3`, which is a very
quiet symptom. The callbacks now **return** an `AuthError` and it is thrown
after the commit (`commitThenFail`). Worth a reviewer's eye, because the naive
version reads better and is wrong.

### 3. The challenge id is not a uuid — a contract change from what I published

**Tell Agent 11.** `challengeId` was specified as `format: uuid`. It is now an
opaque string, `<tenantUuid>.<challengeUuid>`. Nothing else in the contract
changed.

Why: the second step arrives carrying nothing but that id, and every row is
behind a tenant predicate, so the id must name the tenant or the challenge
cannot be found at all. The alternatives were asking the client to repeat the
workspace slug (another field to get wrong, no more trustworthy) or a third
SECURITY DEFINER resolver for the sake of a five-minute row. The tenant in it is
identity, not scope, and it is not trusted — a forged one finds no challenge.

**The client impact is nil**: echo it back, do not parse it. The spec now says
so explicitly, and there is a unit test asserting the id has exactly two
components, so a later change that hides something else in there fails.

## Lockout

Threshold **5**, window 15 minutes, lock 15 minutes, all in `@kasuwa/config`
(`KASUWA_AUTH_LOCKOUT_*`). I flagged mid-task that the then-committed acceptance
suite made six consecutive failures against the seeded account and proposed
defaulting to 10; the lead's answer was that the suite was wrong, not the
threshold, and it has been fixed in PR #16. **PR #16 had not landed on
`origin/main` when I finished**, so I have implemented the behaviour the lead
described and covered it with my own integration tests:

- failures count down, and the fifth returns `429 account_locked` with `retryAt`
  and an IANA `timeZone`;
- a different address is untouched, and still gets a plain `401` — the counter
  is keyed on the submitted identifier, so a lockout is not itself evidence that
  an address is real;
- a successful sign-in resets the counter, so four typos across a week do not
  lock somebody out on the fifth;
- while the lock holds, even the right password is refused.

`auth_attempt` stores `sha256(tenantId + ':' + lower(email))`, never the
address. An email typed into a sign-in form may belong to somebody with no
relationship to Kasuwa, and storing it would also let anyone fill the table with
chosen text.

## What I could not do, plainly

### The acceptance suite is 6/10, and the other 4 are not mine to fix

`tests/acceptance/auth/authentication.pending.acceptance.test.ts` carries two
helpers, `signIn` and `disableUser`, that deliberately throw. The task file says
filling them in is part of the task; my instruction from the lead says do not
edit anything under `tests/acceptance/`. I followed the instruction.

Result today: **6 of 10 pass, and all 4 failures are the two throwing helpers**,
not the implementation. The passing six include the two indistinguishability
tests, the timing test, the "no credential material" test, the invalid second
factor, and the production boot guard.

The four behaviours the helpers gate are covered by
`apps/api/src/auth/auth.integration.test.ts` (23 tests, all green), so they are
proved by something that runs today — but that is my test, not the lead's, and
that distinction matters.

**The helper bodies, ready to paste.** `@kasuwa/testing` already exports what
they need and is already a dependency of `tests/acceptance`:

```ts
// add to the imports
import { disableSeededUser, seededCredentialsForTenant, seededTotpCodeForTenant }
  from '@kasuwa/testing';

async function signIn(server: unknown, tenantId: string): Promise<string> {
  const credentials = seededCredentialsForTenant(tenantId);
  const started = await request(server as never)
    .post(SIGN_IN)
    .send({
      tenantSlug: credentials.tenantSlug,
      email: credentials.email,
      password: credentials.password,
    })
    .expect(200);

  const verified = await request(server as never)
    .post('/api/v1/auth/mfa')
    .send({
      challengeId: started.body.challengeId,
      code: seededTotpCodeForTenant(tenantId),
    })
    .expect(200);

  return verified.body.accessToken as string;
}

async function disableUser(userId: string): Promise<void> {
  await disableSeededUser(inject('migrationUrl'), userId);
}
```

**One thing to watch when you do.** `disableUser(USER_A_AGENT_1)` is called by
the sixth test, and the seventh and eighth call `signIn(server, TENANT_A)` —
which is the same user. Unless the disable is undone, those two will fail at the
sign-in step, and they will fail for a reason that looks like my bug and is not.
`enableSeededUser(inject('migrationUrl'), USER_A_AGENT_1)` in the existing
`afterEach`/`afterAll`, or an `onTestFinished`, closes it. I could not add it
myself.

### Sign-up and OTP are 501, as agreed

Confirmed by the lead mid-task (D-P2, D-P3). Provisioning a tenant is a
regulatory and architectural decision T-0001 does not own; OTP delivery needs
Agent 5's channel provider. They answer `501 not_implemented` rather than 404 so
a screen built against the contract gets a documented refusal.

### The TOTP secret is not encrypted at rest

`user_mfa_factor.secret` is base32 plaintext, protected by RLS, by the app role
holding `NOBYPASSRLS`, and by never being selected into any response. It is not
encrypted because **D-L13 (field-level encryption and per-tenant key management)
is BLOCKED**, and inventing a key-management scheme here would be guessing at a
decision the human has not made. This is stated in the migration and I am
stating it here rather than letting it be discovered: it is the weakest thing in
this change.

### No audit log

An explicit non-goal of T-0001 and a separate M2 task. Sign-in, sign-out,
lockout and MFA failure are exactly the events that task will want, and they all
happen in one service.

### No expired-session cleanup

`auth_session` and `auth_challenge` accumulate expired rows. Correct without a
sweep — `expires_at` is checked on read — but it grows. It belongs in
`apps/worker`.

### No i18n keys, deliberately

The API returns a stable `error.code` and an English fallback `message`. I added
no catalogue keys: adding `auth.error.*` to `en` alone would make the other six
catalogues incomplete and could silently change which languages the menu offers,
which is exactly what the completeness gate exists to prevent. The keys are
Agent 11's, across all locales, in T-0007. Convention published in the spec:
`auth.error.<code>`.

### No feature flag

`packages/feature-flags` asserts in a unit test that `FLAGS` stays empty until a
real feature needs one, so I did not add one. The thresholds are configuration
instead. Flag it back to me if you want this behind a flag.

## Open questions for the human

1. **Session lifetime, refresh and concurrent sessions.** The task says to
   escalate these rather than pick. I have picked provisionally — 12 hours
   absolute, no refresh, no concurrency limit — because nothing could be built
   without a number, and made it a config variable so the answer costs a
   deployment variable rather than a release. It needs a real decision.
2. **`timeZone` on a lockout is an approximation.** P01/1b requires the zone
   with the time. The schema holds no tenant timezone, so it is derived from
   `tenant.region_cell` — which means Sahel BPO, a Nigerian tenant seeded into
   `za-1`, is told a Johannesburg time. An integration test asserts exactly that
   and says why. It stops being an approximation when `tenant` gains a timezone
   column, which is a migration I did not want to make unasked.
3. **An unknown workspace slug is not perfectly indistinguishable.** The first
   response and its timing are identical to a wrong password, but the
   `attemptsRemaining` countdown cannot decrement for a workspace that has no
   tenant row to hold a counter against, so a determined prober can tell after
   two attempts. Closing it means counting attempts against something other than
   a tenant, which needs a table with no `tenant_id` — a direct conflict with
   the invariant. I left the invariant alone and am reporting the gap.
4. **Self-serve tenant provisioning** — raised by the lead as D-P2. Nothing is
   blocked; P01/3 and P01/4 stay on the mock.

## Dependency added

**`hash-wasm` (`packages/auth-crypto`)** — argon2id without a native binary.
`argon2` and `@node-rs/argon2` ship native binaries, which Windows Smart App
Control blocks on the current development machine; that is the same problem
behind the rollup WASM pin (D-L20). WASM is portable, needs no install-time
compiler, and is fast enough at the OWASP parameters. If agents move to a
devcontainer and the pin is lifted, a native argon2 is a drop-in improvement.

**New workspace package `@kasuwa/auth-crypto`** (`scope:shared`), rather than a
folder in `apps/api`: the seed in `@kasuwa/db` must produce the same password
hashes and TOTP secrets the API verifies, and the test harness must be able to
generate a valid code. A shared package is the only arrangement where all three
agree by construction instead of by copy-paste. It holds no policy — no
thresholds, no lifetimes, no database access.
