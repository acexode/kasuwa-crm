## What it does now

A real user signs in with an email and a password, passes a TOTP second factor,
and every later request carries a server-issued session the API resolves
against the database. `KASUWA_AUTH_MODE=stub` still exists and the production
boot guard still refuses it.

Two commits:

1. **The contract, alone and first.** T-0007 (Agent 11) is in flight alongside
   this task and had to build the P01 screens against a mock. Endpoints, success
   shapes and every failure body are in `docs/api/auth.openapi.yaml`, with
   `x-kasuwa-implemented` on each operation saying whether it is real.
2. **The implementation.**

### The shape of it

- `POST /auth/sign-in` verifies the first factor and opens a challenge. It hands
  out nothing usable on its own.
- `POST /auth/mfa` verifies the code and issues the session. The only route in
  the API that returns a token.
- `POST /auth/mfa/challenge`, `POST /auth/sign-out`, `GET /auth/me`,
  `POST /auth/sso/lookup` are implemented. `sign-up`, `verify-otp` and
  `verify-otp/resend` are published and answer `501 not_implemented` — see
  "What I did not do".
- Five new tables in `packages/db/migrations/0002_authentication.sql`:
  `user_credential`, `user_mfa_factor`, `auth_challenge`, `auth_session`,
  `auth_attempt`. All carry `tenant_id`, all `ENABLE` **and** `FORCE` RLS, every
  policy's `WITH CHECK` is identical to its `USING`, every foreign key to a
  tenant-scoped parent is composite on `(tenant_id, id)`. All five are in
  `TENANT_SCOPED_TABLES` and mirrored in `schema.ts`.
- argon2id via `hash-wasm`; TOTP written by hand against the RFC 6238 vectors.
- Sessions are opaque: `ksw_s1_` plus 32 random bytes; only the SHA-256 is
  stored. ADR-0008 has the reasoning.

### Authentication changed who, not what

This was the point of the task and it is the thing to check first.

- `tests/acceptance/tenancy/` passes **unmodified**. I did not touch anything
  under `tests/acceptance/`, and I did not rename the `.pending.` file.
- No response anywhere in the API carries a programme id, a role or a
  permission. `/auth/me` is identity only. There is a unit assertion and an
  integration assertion that the session response matches no
  `/programme|role|permission/`.
- Scope is still resolved from `user_programme` inside `withTenantTransaction`.
  I changed nothing in `packages/db/src/session.ts`.
- `x-kasuwa-programme-ids` and friends are still a 400, now with or without a
  session.

### Two layers, not one

The guard resolves the token through `app.resolve_session`, then the
interceptor re-reads the same row **inside the tenant transaction, under RLS,
with explicit `tenant_id` and `user_id` predicates**. A mistake in the first
cannot serve a request past the second. This is also what makes a disabled user
and a revoked session fail on the *next* request rather than at expiry.

## The three things worth arguing about

### 1. Two SECURITY DEFINER functions now exist

Authentication has a real bootstrap problem: every RLS policy reads
`app.tenant_id`, and before a session exists nobody has set it. The answer is
`app.resolve_tenant_by_slug(text)` and `app.resolve_session(bytea)` — both
`STABLE`, both taking one opaque argument, both pinning `search_path`, both
returning identifiers and nothing else. They are the only RLS-free read path in
the system and the migration says so in a comment. **A third one should be
refused.**

Everything else in the sign-in path runs through `withAuthTransaction`
(`packages/db/src/auth.ts`), which opens a transaction, pins the resolved
tenant, and sets `app.programme_ids` to `'{}'` for the whole transaction — so
an authentication transaction can read no programme-scoped row at all. Not one
contact. That property is worth more than any amount of care in the caller, and
it is the thing to check if this file is ever changed.

### 2. A bug that would have passed its own tests

Every failure path has a side effect that must survive: a failed sign-in
increments a counter, a wrong code burns an attempt. Throwing from inside the
transaction rolls it back and silently discards exactly the row that was meant
to record the failure. The counter never advances, nothing ever locks, and a
test asserting "five failures lock the account" would pass only if it happened
to run five *separate* transactions that each persisted — which they do not.

I hit this: the lockout test failed with `expected 4 to be 3`, which is a very
quiet symptom. The callbacks now **return** an `AuthError` and it is thrown
after the commit (`commitThenFail`). Worth a reviewer's eye, because the naive
version reads better and is wrong.

### 3. The challenge id is not a uuid — a contract change from what I published

**Tell Agent 11.** `challengeId` was specified as `format: uuid`. It is now an
opaque string, `<tenantUuid>.<challengeUuid>`. Nothing else in the contract
changed.

Why: the second step arrives carrying nothing but that id, and every row is
behind a tenant predicate, so the id must name the tenant or the challenge
cannot be found at all. The alternatives were asking the client to repeat the
workspace slug (another field to get wrong, no more trustworthy) or a third
SECURITY DEFINER resolver for the sake of a five-minute row. The tenant in it is
identity, not scope, and it is not trusted — a forged one finds no challenge.

**The client impact is nil**: echo it back, do not parse it. The spec now says
so explicitly, and there is a unit test asserting the id has exactly two
components, so a later change that hides something else in there fails.

## Lockout

Threshold **5**, window 15 minutes, lock 15 minutes, all in `@kasuwa/config`
(`KASUWA_AUTH_LOCKOUT_*`). I flagged mid-task that the then-committed acceptance
suite made six consecutive failures against the seeded account and proposed
defaulting to 10; the lead's answer was that the suite was wrong, not the
threshold, and it has been fixed in PR #16. **PR #16 had not landed on
`origin/main` when I finished**, so I have implemented the behaviour the lead
described and covered it with my own integration tests:

- failures count down, and the fifth returns `429 account_locked` with `retryAt`
  and an IANA `timeZone`;
- a different address is untouched, and still gets a plain `401` — the counter
  is keyed on the submitted identifier, so a lockout is not itself evidence that
  an address is real;
- a successful sign-in resets the counter, so four typos across a week do not
  lock somebody out on the fifth;
- while the lock holds, even the right password is refused.

`auth_attempt` stores `sha256(tenantId + ':' + lower(email))`, never the
address. An email typed into a sign-in form may belong to somebody with no
relationship to Kasuwa, and storing it would also let anyone fill the table with
chosen text.

### Sign-up and OTP are 501, as agreed

Confirmed by the lead mid-task (D-P2, D-P3). Provisioning a tenant is a
regulatory and architectural decision T-0001 does not own; OTP delivery needs
Agent 5's channel provider. They answer `501 not_implemented` rather than 404 so
a screen built against the contract gets a documented refusal.

### The TOTP secret is not encrypted at rest

`user_mfa_factor.secret` is base32 plaintext, protected by RLS, by the app role
holding `NOBYPASSRLS`, and by never being selected into any response. It is not
encrypted because **D-L13 (field-level encryption and per-tenant key management)
is BLOCKED**, and inventing a key-management scheme here would be guessing at a
decision the human has not made. This is stated in the migration and I am
stating it here rather than letting it be discovered: it is the weakest thing in
this change.

### No audit log

An explicit non-goal of T-0001 and a separate M2 task. Sign-in, sign-out,
lockout and MFA failure are exactly the events that task will want, and they all
happen in one service.

### No expired-session cleanup

`auth_session` and `auth_challenge` accumulate expired rows. Correct without a
sweep — `expires_at` is checked on read — but it grows. It belongs in
`apps/worker`.

### No i18n keys, deliberately

The API returns a stable `error.code` and an English fallback `message`. I added
no catalogue keys: adding `auth.error.*` to `en` alone would make the other six
catalogues incomplete and could silently change which languages the menu offers,
which is exactly what the completeness gate exists to prevent. The keys are
Agent 11's, across all locales, in T-0007. Convention published in the spec:
`auth.error.<code>`.

### No feature flag

`packages/feature-flags` asserts in a unit test that `FLAGS` stays empty until a
real feature needs one, so I did not add one. The thresholds are configuration
instead. Flag it back to me if you want this behind a flag.

## Open questions for the human

1. **Session lifetime, refresh and concurrent sessions.** The task says to
   escalate these rather than pick. I have picked provisionally — 12 hours
   absolute, no refresh, no concurrency limit — because nothing could be built
   without a number, and made it a config variable so the answer costs a
   deployment variable rather than a release. It needs a real decision.
2. **`timeZone` on a lockout is an approximation.** P01/1b requires the zone
   with the time. The schema holds no tenant timezone, so it is derived from
   `tenant.region_cell` — which means Sahel BPO, a Nigerian tenant seeded into
   `za-1`, is told a Johannesburg time. An integration test asserts exactly that
   and says why. It stops being an approximation when `tenant` gains a timezone
   column, which is a migration I did not want to make unasked.
3. **An unknown workspace slug is not perfectly indistinguishable.** The first
   response and its timing are identical to a wrong password, but the
   `attemptsRemaining` countdown cannot decrement for a workspace that has no
   tenant row to hold a counter against, so a determined prober can tell after
   two attempts. Closing it means counting attempts against something other than
   a tenant, which needs a table with no `tenant_id` — a direct conflict with
   the invariant. I left the invariant alone and am reporting the gap.
4. **Self-serve tenant provisioning** — raised by the lead as D-P2. Nothing is
   blocked; P01/3 and P01/4 stay on the mock.

## Dependency added

**`hash-wasm` (`packages/auth-crypto`)** — argon2id without a native binary.
`argon2` and `@node-rs/argon2` ship native binaries, which Windows Smart App
Control blocks on the current development machine; that is the same problem
behind the rollup WASM pin (D-L20). WASM is portable, needs no install-time
compiler, and is fast enough at the OWASP parameters. If agents move to a
devcontainer and the pin is lifted, a native argon2 is a drop-in improvement.

**New workspace package `@kasuwa/auth-crypto`** (`scope:shared`), rather than a
folder in `apps/api`: the seed in `@kasuwa/db` must produce the same password
hashes and TOTP secrets the API verifies, and the test harness must be able to
generate a valid code. A shared package is the only arrangement where all three
agree by construction instead of by copy-paste. It holds no policy — no
thresholds, no lifetimes, no database access.

# Round two — after the security and tenancy reviews

The security review returned **fail** (one blocking, four major); the tenancy
review returned **pass-with-findings** and added one. This section is what
changed. Nothing above is withdrawn; where round one was wrong, it is marked
here rather than quietly edited.

Two of the five findings were races. **No test I wrote in round one could have
caught them**, because a sequential test never sees a lost update, and the suite
was green throughout. That is the thing to take from this round: green was not
evidence. Every finding below now has a test that fails against the old code.

## BLOCKING — the second factor could be brute-forced

Three separate gaps, all fixed.

1. **The attempt counter was a read-modify-write in application code.** It read
   `attempt_count`, added one in JavaScript, and wrote the result back. Under
   READ COMMITTED, N concurrent guesses all read 0 and all write 1, so the burn
   at the threshold never fired and **one challenge accepted unlimited
   guesses**. Now `UPDATE ... SET attempt_count = attempt_count + 1 ...
   RETURNING`, with the burn decided from the returned value.
2. **Nothing throttled `/auth/mfa`.** A per-USER counter now exists, separate
   from sign-in and from the challenge, defaulting to ten wrong codes before the
   second factor locks. This is the number that actually bounds a stolen
   password; burning one challenge bounds nothing, because the attacker opens
   another.
3. **No cap on open challenges.** Now three per user, and the cap consumes the
   OLDEST rather than refusing the newest — so it cannot be turned round and
   used to deny a legitimate user their sign-in.

## MAJOR — one challenge could mint several sessions

`findOpenChallenge` checked `consumed_at IS NULL` and the consume did not.
Eight parallel verifies with one valid code all passed the check and all issued
a session. Now `UPDATE ... WHERE ... AND consumed_at IS NULL RETURNING id`, and
the session is issued only if a row came back.

The review's sharpest point was not the bug: it was that **the comment claimed
the problem was handled**. "Consuming before issuing means a replayed challenge
id cannot mint a second token" was false as written, and a false comment is
worse than none because it stops the next reader looking. The comment now says
what the row count is for.

## MAJOR — workspace-slug enumeration

Disclosed in round one, now fixed as directed. The sign-in counter is keyed on
`sha256('signin' : slug : email)` — **what the caller typed, before anything is
resolved** — so a workspace that does not exist counts down and locks exactly
like one that does.

That required a table with no `tenant_id`, because a counter that can only exist
for tenants that exist will always answer differently for one that does not.
**ADR-0009** argues it. The exemption is named in `NON_TENANT_SCOPED_TABLES`,
honoured by `readTableSecurity`, stated in capitals in migration 0003, and
`readNonTenantScopedTableSecurity` asserts the exempted table still has RLS
enabled, forced and policied — so the exemption cannot be used to smuggle a
table past the invariant. `tests/acceptance/tenancy/` still passes
**unmodified**, because the exemption lives in the harness the test calls, not
in the test.

**I considered a third `SECURITY DEFINER` function** to keep `kasuwa_app` off
that table, and rejected it — the standing rule says a third is an ADR decision,
and the protection is small when the table holds only hashes and counts. The
count stays at two. The reasoning is in ADR-0009 so the next person does not
have to re-derive it.

The lockout `timeZone` is now one cell-wide configured value, not the tenant's.
That closes the hosting-region disclosure and also **resolves round one's open
question 2**: the per-tenant value was an approximation that was wrong anyway,
since the server does not know the user's zone. The browser does, and should
render `retryAt` in it.

## MAJOR — unauthenticated CPU and memory exhaustion

Two bounds, because the throttle alone does not cap memory and the cap alone
does not bound the queue:

- A per-client fixed-window throttle on the expensive routes, sixty a minute by
  default. **It counts the socket peer and ignores `X-Forwarded-For`** —
  trusting a header nothing in this repository sets or strips would make the
  limit bypassable by typing a different value, which is worse than no limit
  because it looks like one. Behind a load balancer this throttles the balancer
  and needs a trusted-proxy configuration; the guard says so in its own comment.
  The counter is also per process, so with several instances the effective limit
  multiplies. Both limitations are stated rather than papered over.
- A hard concurrency cap of six inside `@kasuwa/auth-crypto`, so argon2id costs
  at most about 120 MiB no matter what arrives. This is the bound that actually
  protects the cell.

**I did not take `@nestjs/throttler`, though it was pre-approved.** Its default
storage is also in-process, so it buys no correctness here, and it does not
provide the concurrency cap that is the real fix. Forty lines with no new
dependency and two honest comments seemed the better trade — say so if you
disagree and I will swap it.

## MAJOR — `pnpm db:seed` had no environment guard

Now refuses any host but localhost, exactly as `db:reset` does, and the error
says why: the seed installs five working users whose password and TOTP secrets
are committed to this repository, so running it anywhere shared publishes a way
in.

## The smaller ones

- **`db:reset` now drops the authentication tables.** It did not, so migration
  0002 failed on a re-run and live session rows survived what a developer
  believed was a wipe.
- **`/auth/me` now carries `AND tenant_id = $2`.** Both reviewers landed on this
  independently and both were right: it was the one query in the change with a
  single layer.
- **TOTP codes are single-use** (`last_used_step`, RFC 6238 section 5.2). See
  the caveat below — it is the one thing that is not green.
- **Suspension now contains.** `app.resolve_session` checks tenant status, and
  the client-supplied tenant id in a challenge id is confirmed rather than
  merely parsed. Checking per request beats revoking at suspension time: it is
  immediate, it cannot miss a session issued during the race, and un-suspending
  restores access without reissuing anything. Recorded in ADR-0008. **There is
  still no endpoint that suspends a tenant** — that is later M2 work.

## Two bugs I did not go looking for

Both were pre-existing, both were exposed by this round's tests, and both were
silent.

1. **`DatabaseModule` kept its pool in a `static`.** Correct for one app per
   process and wrong for two: the second `forRoot` overwrote the reference, so
   closing either app ended the second one's pool and orphaned the first's.
   Nothing had ever created two apps until these tests did. The symptom was not
   an error — it was connections leaking until a later suite's writes began
   failing, which reads like a bug in whatever is being tested. The pool is now
   injected and each app closes its own.

2. **`fileParallelism: false` inside a project block is silently ignored.** It
   is honoured at the root config or from the CLI. For as long as the
   integration project had one test file this looked like it worked; the second
   file arrived with T-0001 and the two immediately truncated each other's
   tables mid-test. It cost me most of an afternoon, and the failures it
   produced — "the counter did not increment", "the challenge does not exist" —
   pointed at my own new code every time. Fixed with `poolOptions.singleFork`,
   which is the project-level setting that is actually applied, on the
   integration, isolation and pending projects. **The isolation project has had
   several files sharing one database all along**, so this was latent there too.

# Round three — the flaky suite, and the third race underneath it

The lead's note was that the throttle was firing inside the test suite and that
the failing set changed between runs. The throttle was part of it. It was not
the interesting part.

## What the flakiness actually was: a deadlock in the authentication path

Chasing the moving failures — "the counter did not increment", "the challenge
does not exist", "the lockout never fired" — produced one run that said
`deadlock detected`, and that explained every symptom at once.

**Sign-in locked `auth_rate_limit` and then `auth_challenge`. Verifying a second
factor locked them in the opposite order.** Two requests for the same user
arriving together could each hold the row the other wanted. Postgres resolves
that by aborting one of them — and the aborted transaction rolls back the
counter increment it was in the middle of making.

That is why it was so hard to see. The damage is not the error:

- the request that aborted reaches the client as a 500, which a test asserting
  "not 200" happily accepts;
- the failure it was recording is gone, so the countdown stalls and **the
  lockout never arrives**;
- and the symptom surfaces in a *different* test, which is why the failing set
  moved on every run.

A brute-force control that quietly stops counting under concurrent load is
worth having found. Concurrent load is what an attack looks like.

**The fix is one lock order, everywhere: `auth_rate_limit` before
`auth_challenge`.** In `failSecondFactor` the rate-limit failure is now
registered before the challenge counter is bumped, and on the success path the
counter is cleared before the challenge is consumed. Both are commented at the
site with why, because the natural order to write them in is the wrong one.

**Regression test:** `the lock order the first fix introduced` in
`auth-hardening.integration.test.ts` fires two second-factor attempts and six
sign-ins for one user concurrently, asserts that nothing 500s, and then asserts
that the six failures actually counted by requiring the account to be locked.
It fails against the previous ordering.

I also stopped the test reset using `TRUNCATE`: it takes an `ACCESS EXCLUSIVE`
lock on every table named and deadlocks against exactly the same code path.
`DELETE` takes row locks and these tables are tiny.

## The throttle, as asked

1. **The limits are configuration.** `KASUWA_AUTH_SIGN_IN_PER_MINUTE` sits with
   the other `KASUWA_AUTH_*` numbers, default 60.
2. **State is reset between tests, not raised to infinity.**
   `auth.integration.test.ts` now runs with **no policy overrides at all** —
   the real lockout threshold, the real throttle, real single-use codes — and a
   `beforeEach` gives each test a clean slate instead. `SignInThrottleGuard`
   gained a `clear()`, which is a real operational seam (the window is sixty
   seconds in process; clearing it is the only way to hand an allowance back
   after a misconfigured limit locks staff out), not a test hatch.
3. **A test proves it fires.** `throttles sign-in per client address` hammers a
   deliberately low limit end to end. The property that suite *cannot* reach —
   that the counter is keyed per client at all — is covered by
   `sign-in-throttle.guard.test.ts`: one address exhausting its allowance leaves
   another untouched, a forwarded-for header does not move the key, and a
   limiter keyed on nothing would fail it. "It returned 429 when I hammered it"
   does not distinguish a working limiter from a global outage.

## On the lockout tests you asked me to re-check

Confirmed: they assert what they did before. `expected 4 to be 2` was not the
counter regressing — it was the deadlock above eating increments. The countdown
assertions, the fifth-failure lock, the untouched second address and the reset
on success are all unchanged and all now pass, with the threshold at five.

## One knob removed

`rejectReusedTotpCodes` is gone. It existed only to turn single-use TOTP codes
off in one test file, and a configuration switch whose only real use is
disabling a security control under test is not a control. The suite resets the
watermark between tests instead, exactly as it resets a rate-limit counter.

# Round four — the pool, and seven small things

## MAJOR — argon2 no longer holds a pooled connection

`verifyPassword` was awaited inside `withAuthTransaction`, so every sign-in
pinned a pooled `pg` client for the whole ~86 ms of hashing, plus however long
it queued behind other hashes first. With `DATABASE_POOL_MAX` at 10, roughly a
dozen concurrent sign-ins owned every connection in the process and **all other
tenant traffic in the cell blocked on `pool.connect()`** until they drained.
Unauthenticated: unknown slugs do the same argon2 work by design, which is what
makes the timing equal and is exactly what made this reachable. Round three
moved the memory pressure; it landed on the pool.

`signIn` is now three phases, and the shape is the point:

1. **read** — resolve the tenant, check the lockout, fetch the stored hash, then
   let the connection go;
2. **hash** — argon2id, holding nothing;
3. **record** — a second short transaction for the failure counter or the
   challenge.

It costs two short transactions instead of one long one and nothing in
correctness: the lock read was advisory either way, and `registerAuthFailure` is
atomic in a single statement, so nothing depended on the read and the write
sharing a snapshot. Both branches still do the same work against a dummy hash
when there is no account, and phase three still runs for an unknown workspace
exactly as for a real one.

**Regression test:** `serves other tenant traffic while sign-ins are hashing`
stands up an app with `poolMax: 3`, fires twelve concurrent sign-ins, and
requires an ordinary contacts request issued *during* the flood to return 200.
It cannot pass if the hash moves back inside the transaction.

**The other two parts.** The hashing queue is now bounded
(`MAX_QUEUED_HASHES`), and a caller past it gets `HashingOverloadedError`,
which the API turns into **503 `service_unavailable` — never 401**. Refusing to
do the work is not a decision about the credentials, and answering 401 would
both mislead a real user and hand an attacker a fast oracle for "this request
never reached argon2". The per-client **in-flight cap** is the other new limit:
a per-minute counter does not bound concurrency, since a client may legitimately
spend a whole minute's allowance inside one second.

## The minors

1. **The TOTP watermark is now claimed, not merely written.** The UPDATE carried
   `last_used_step < $3` but nobody looked at the row count, so two concurrent
   verifies with the same live code both got a session. It now `RETURNING id`s
   and a caller that matched nothing is refused like any other rejected code.
   "A code is usable once" is true under concurrency as well as sequentially.
2. **`KASUWA_AUTH_REJECT_REUSED_TOTP` was already gone** from the schema when I
   looked — removed with the policy field in round three. The only surviving
   mention is the error message in the acceptance file, which is yours. Suggested
   wording: *"Codes are single-use. Advance the clock, use a code you have not
   used, or call `resetSeededTotpUsage(migrationUrl)` between tests. There is no
   switch that turns single-use codes off."*
3. **`db:seed`** — you had already moved the guard onto `runSeed`. I added the
   bracketed IPv6 form: `new URL().hostname` returns `[::1]`, so the list needed
   it or a genuinely local database would have been refused, which teaches the
   next person to reach around the guard.
4. **The hash semaphore** already had your `while` re-check, which fixes the
   cap. I added the queue bound on top.
5. **`evictExpired`** was already replaced by your bounded `sweep`.
6. **Migration 0003** now says "Five changes" and lists the index, and asserts
   at the end that **neither SECURITY DEFINER function is executable by
   `PUBLIC`**. The `REVOKE ALL FROM PUBLIC` survives today only because
   `CREATE OR REPLACE` preserves the ACL; a future `DROP` + `CREATE` — how
   anyone would change a signature — starts from a fresh ACL, and Postgres
   grants `EXECUTE` to `PUBLIC` by default. That edit would hand every role the
   two RLS-free reads with nothing noticing.
7. **ADR-0009 now records the rule 3 deviation** beside the rule 4 one.
   `auth_rate_limit` has **one** layer, not two: its `USING (true)` policy
   confines nothing, so the `key_hash` the repository computes is the whole
   protection. Accepted on what the table holds — a SHA-256 and three integers —
   and explicitly the argument that would not work for any other table, which is
   why the list may not grow without another ADR.

**The two comments** in `isolation.ts` and ADR-0009 now say where
`readNonTenantScopedTableSecurity` is actually called, and say plainly that for
a while it was called nowhere while both texts claimed otherwise — the claim was
true of the code and false of the build.
