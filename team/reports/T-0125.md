## Why the session is not behind a feature flag

ADR-0019 does not call for one, and the session cannot sit behind one safely.

- The BFF **replaces** the `/api/v1` rewrite. An "off" position would have to keep that rewrite in the production
  artefact. The rewrite forwards stub identity headers and has no CSRF control: that is the hole the ADR closes.
- The CSRF check and the CSP are security controls, not features.
- The sign-out button means nothing without the session.

A flag here would mean shipping two doors to the API.

## Decisions ADR-0019 did not cover (please confirm or overrule)

1. **Landing after sign-in.**
   - The MFA screen does `router.replace('/')`.
   - `app/page.tsx` sends a request that carries one well-formed session cookie to the first live CRM screen in nav
     order, or else to `/admin`. A browser with no cookie gets P01/1.
   - This is navigation only. A dead cookie bounces once: its first read is a 401, the BFF clears the cookie, and the
     browser comes back to `/`.
2. **Pre-session routes get no Bearer token**, even when a cookie is present. These are sign-in, MFA, challenge,
   enrol, enrol confirm, SSO lookup, sign-up and verify-otp. A 401 from them (a wrong password or code) does not clear
   the cookie.
3. **Two session cookies in one request** count as no session. The request goes upstream with no credential, the API
   answers 401, and the cookie is cleared. Neither cookie is chosen. A malformed value (outside the API's token
   charset, or over 512 characters) also counts as no cookie.
4. **Path canonicalisation.**
   - Each segment is percent-decoded and then re-encoded.
   - A segment that is empty, `.` or `..`, or that holds `/`, `\` or a control character, gets the API's
     unknown-route 404.
   - Route classification is lower-case because Express routes case-insensitively. Without that,
     `/api/v1/AUTH/MFA` would be issued a token the BFF did not strip.
   - Separately, a `accessToken` key in any other route's 2xx body fails closed as a 502.
5. **The 502 body** keeps the `internal_error` code and message. I set `statusCode: 502` and `error: 'Bad Gateway'`
   so that the body matches the HTTP status.
6. **Request bodies are capped at 1 MiB**, twice the API's JSON limit. Over the cap the BFF answers 413 with the
   API's body-parser envelope.
7. **Response header allowlist:** content-type, content-disposition, content-language, etag, last-modified and
   retry-after.
   - `Location` and any upstream `Set-Cookie` are dropped.
   - JSON is buffered and gzipped at 1 KB or more when the browser accepts it.
   - Anything else (exports) streams through uncompressed.
8. **`x-forwarded-for` is forwarded verbatim** (allowlisted), so the API's hop count means what it meant before. A
   unit test shows two client chains arriving as two values.
9. **Replacing a session on re-sign-in waits for the old one's revocation**, with a 5-second cap, before answering.
   It is best effort: a failure does not fail the sign-in.
10. **The CSP.**
    - `style-src-attr 'unsafe-inline'` is included. I measured the need rather than guessing: server-rendered
      `style={}` props on the admin bars, the role tree, the script canvas and `/design/tokens`.
    - `next dev` alone adds `'unsafe-eval'`, the HMR websocket, and `style-src 'unsafe-inline'` with no nonce,
      because the dev server injects `<style>` elements.
    - `upgrade-insecure-requests` is sent only on an https origin that is not loopback.
11. **Middleware moved to the Node runtime** (stable in Next 15.5), so the CSP reads `webEnv()` rather than
    `process.env`.
12. **Where the shared constants live:** `@kasuwa/config/session`. This needed a path alias in `tsconfig.base.json`
    and `vitest.workspace.ts`, and an ESLint allowance for apps/web. The 404 and 500 bodies moved there too, so the
    BFF's navigation 404 is byte-identical to the API's.
13. **The ESLint rule bans every `fetch()` in apps/web** outside `lib/api-fetch.ts` and `lib/server/`, not only
    `fetch('/api…')`. That is stronger and simpler. A future cross-origin fetch (to the bucket) will need a named
    exemption.
14. **The wrapper sends the CSRF header on reads too.** One rule is easier to keep than two.
15. **A 401 means a full navigation to `/`**, unless the caller is the sign-in flow (`onUnauthenticated: 'return'`).
16. **Both URLs must be bare origins**, so `KASUWA_API_INTERNAL_URL` cannot carry a path prefix.
17. **The BFF logs nothing**, not even "upstream unreachable". See open question 2.
18. **The sign-out button is text only.** An icon would have meant changing the icon subset. The Pidgin string is
    "Comot", from a draft; Agent 11 should check it.

## What was hard

1. **The journey reads the MFA response body after the click.** A full `window.location.assign('/')` after MFA made
   Chromium discard that body ("No resource with given identifier found"). That caused both failures on the run, in
   `@bff-session-journey` and `@bff-session-cookie`. The screen now navigates client-side, and the server-side
   redirect on `/` does the landing.
2. **Express routes case-insensitively.** A naive `route === 'auth/mfa'` would have let `/api/v1/AUTH/MFA` take a
   token to page JavaScript. Hence the lower-case classification, plus the generic fail-closed check on `accessToken`.
3. Getting the CSP right for `next dev` without weakening it for any production or test process.

## Open questions

1. **A raw cross-origin fetch is now a lint error in apps/web.** The import upload (T-0096) sends parts to the bucket
   with `XMLHttpRequest`, which the rule does not cover, and `connect-src 'self'` will block it. ADR-0019 point 10
   already says the storage origin joins the CSP when uploads ship. That still has to be done before `crm_import` is
   production-ready.
2. **The BFF logs nothing at all**, so an unreachable API shows up only as 502s. A one-line, PII-free "upstream
   unreachable" event may be wanted once `redact()` or a web logger exists.
3. The suite's header still calls ADR-0019 "Proposed". That is cosmetic, and I made no edit.

## Tests I think are imperfect (not edited)

- **`@bff-session-cookie` and `@bff-session-journey` read `mfa.json()` after the screen has moved on.** That silently
  requires the post-MFA navigation to be a soft one. It is a fair constraint, but it is unstated in I1–I24. A future
  "reload after sign-in" would fail with a CDP error rather than a readable assertion.
