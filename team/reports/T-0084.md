## What changed

- **Migration 0035** (`packages/db/migrations/0035_list_keyset_indexes.sql`) adds six plain-column B-tree indexes, all
  tenant-led so that one index gives the order for a session reaching several programmes:
  - on contact: `(tenant_id, created_at, id)`, `(tenant_id, updated_at, id)` and `(tenant_id, display_name, id)`;
  - on account: `(tenant_id, created_at, id)`, `(tenant_id, updated_at, id)` and `(tenant_id, name, id)`.

  A B-tree reads either way, so each index serves a sort and its reverse. Leads is a status view of contact, so the
  contact indexes serve it too. The file has no expressions, GIN, GiST, trigram, extension, function or SECURITY DEFINER.
  - Its self-check reads `pg_proc.proleakproof` and raises if any of the six is missing, invalid, partial, an expression
    index, not a B-tree or on the wrong columns. It also raises if any operator served by a key column's operator family
    is not LEAKPROOF. It never marks anything.
  - The header gives the `-- kasuwa:no-transaction` + `CREATE INDEX CONCURRENTLY IF NOT EXISTS` recipe for a populated
    cell (D-L65). The statements are already `IF NOT EXISTS`, so the recipe is only "add the earlier file".
  - `schema.ts` mirrors the six indexes.
- **Cursors** (`packages/domain/core/src/cursor.ts`):
  - New `encodeListCursor` / `decodeListCursor`. The payload is `{"v":1,"s":"<sort>","i":"<uuid>"}` in base64url,
    strictly parsed: the id, the sort's name and a version, never a value.
  - A cursor issued under another sort is still `InvalidCursorError` (400 `invalid_cursor`).
  - The old `{c, i}` shape is accepted only under the contacts list's default `-createdAt`, and by its id alone. `c` is
    still validated (garbage stays 400) and then dropped.
  - The T-0041 valued `{s, v:<text>, i}` shape is no longer accepted, and `encodeSortedCursor`, `decodeSortedCursor`
    and `MAX_TEXT_SORT_POSITION` are gone. `MAX_CURSOR_LENGTH` stays at 2048, so the boundary schemas do not change.
  - `encodeKeysetCursor` / `decodeKeysetCursor` are unchanged. Audit, programmes and the adversarial suite use them.
- **Repositories** (`contact.repository.ts`, `account.repository.ts`):
  - The keyset seek is `(<col>, id) <op> (SELECT cursor_row.<col>, cursor_row.id FROM <table> cursor_row WHERE id = $c
    AND tenant_id = <session> AND programme_id = ANY(<session>))`.
  - That is an uncorrelated row subquery, so Postgres runs it once as an InitPlan, and the row comparison is an index
    condition. There is one statement per page, with no OFFSET.
  - The cursor row is resolved inside the session's scope and is not narrowed by `q` or filters (a position, R5). A row
    that is out of scope or invented gives NULL, which means an empty page with `nextCursor: null`.
  - The contacts name sort is now `display_name` (ruling 8). The `to_char` `sort_cursor` column is gone. Results and
    field security are untouched: same SELECT columns, same `q` and filters.
- **OpenAPI** (`docs/api/records.openapi.yaml`, the shared `Cursor` parameter): the description now says the cursor is
  id-only, is resolved in scope, is 400 under another sort, and that an out-of-scope id gives an empty page.
- **Tests:**
  - `sorted-cursor.test.ts` is replaced by `list-cursor.test.ts`, which covers the round trip, the exact payload,
    cross-sort refusal, garbage, version and extra keys, valued-cursor refusal, and the legacy rule.
  - The integration test's legacy-cursor case now asserts id-alone resolution, using a `c` that would give nothing if it
    were trusted.
  - A new integration case checks that a tenant-B id and an invented id both give `{data: [], nextCursor: null}`.

## What was hard

- **Whether an InitPlan row comparison stays an index condition under FORCE RLS.** It does. The InitPlan's outputs are
  Params, the comparison's operators (`timestamptz`, `text`, `uuid` B-tree) are LEAKPROOF, and the planner promotes it
  ahead of the policy quals. The two-statement alternative (resolve, then page) was not needed.
- **Keeping cursor-tampering green.** Its smuggle test expects **200 and empty** for an invented id, not 400, so "an
  unresolvable cursor id is an empty page" is forced by that suite as well as by I5. I kept the old `{c, i}` decodable
  under `-createdAt` only, as D-L112 suggests.

## What I left out, and why

- The older programme-led indexes (`contact_keyset_idx`, `account_keyset_idx`, `account_name_keyset_idx`) are not
  dropped.
  - None is a prefix of a new index, so schema-hygiene is fine, and dropping one is a contract step.
  - With `programme_id = ANY($n)`, Postgres 16 cannot take an order from them, so they may now be dead weight on every
    write. Worth a follow-up: measure, then `DROP INDEX CONCURRENTLY` in a no-transaction file.
- Trigram, jsonb GIN and LEAKPROOF marking are out of scope (D-P33's second step).
- I did not run `migration-reviewer` (lead review step).

## Open questions

- **Builder push rule versus the hand-off.** The hand-off asked me to push the branch. My standing builder instructions
  say never push (the lead pushes), so I committed locally and did not push.
- **Semantics a reviewer should confirm (all follow from D-L80/I5, not chosen by me):**
  - A cursor whose row was deleted, or moved out of the caller's scope between pages, now ends the walk with an empty
    page. Before, it continued from the stored value.
  - A cursor row whose sort key changed between pages (for example `-updatedAt` after an edit) re-positions at the
    row's current key. Rows can then repeat or be skipped, as with any live keyset.
  - A supervisor's cursor naming an A2 row, replayed by an A1-only agent, now gives an empty page. Before, it gave the
    agent's rows after that position. The accounts-api and leads-api "position, never authority" cases still pass,
    because their cursor rows are in A1.

## Risks I am aware of

- **Tenancy:** the cursor subquery repeats the session's tenant and programme predicates, by the same placeholders as
  the page, and RLS applies to it too. An out-of-scope id is indistinguishable from an invented one: the same 200 and
  the same empty body (I5, the integration test).
- **Skewed programmes:** the indexes are tenant-led. A one-programme agent in a tenant where their programme holds a
  tiny share of rows would filter many index rows per page. The suite's 50/50 split does not show this. A programme-led
  variant only helps if the repository sends `programme_id = $1` (not `= ANY`) for single-programme sessions. That is a
  follow-up if it shows up.
- **Host flakiness:** `argon2 failed`, the web app not becoming ready, and the container `ECONNREFUSED` all appeared
  only in combined runs, on a laptop at about 0.8 GB free with roughly 150 node processes and other agents' containers.
  Each suite passed when re-run alone. Worth knowing for batch verification (D-L109).
- **e2e mocks:** none decodes the real API's cursors. `leads-mock.ts`, `accounts-mock.ts` and `account-record-mock.ts`
  mint their own opaque cursors and look them up, so nothing under `tests/e2e/support` needed attention.
