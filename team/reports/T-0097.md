## What changed
- **Flag (I1).** `crm_duplicates` is registered: off, not production-ready, presentation only. FEATURES.md is regenerated. `crmLiveNav()` lists `duplicates` only through it. `run-e2e.mjs` serves it on the records process and publishes `webDuplicatesUrl` (typed in `support/stack.ts`).
- **Route.** `/contacts/duplicates` calls `notFound()` unless `crm_duplicates` and `crm_records` are on, and is read on the server only. The Contacts list links it where `live.includes('duplicates')`, as a quiet link beside the import action. It keeps `data-requires-connection` and is `aria-disabled` offline.
- **Client** (`lib/duplicates-api.ts`). The five operations plus `listMyProgrammes`, same-origin, never cached, Zod-parsed, no scope argument. The programme is the path of the scan. The cursor is echoed unchanged. `requestRecords` also learned:
  - two codes only the merge answers (`already_merged`, `undo_expired`), kept out of `RecordsErrorCode` so no other screen pays for their sentences;
  - a 429's `Retry-After` as whole seconds (`retryAfterSeconds`).
- **Sets (C, I2–I4).** Phone or email in words. No value, score or confidence exists in the contract, so none is drawn. A withheld name is a label, never "null" and never marked as record data. `<time>` for `updatedAt`. A pair opens the merge directly. In a larger set exactly two are picked, and picking a third is allowed and simply turns Review off. "Show more" echoes `nextCursor`.
- **The scan** is a framework-free state machine (`duplicate-scanner.ts`):
  - one scan per landing, programme change, next page, explicit retry, or return after a merge or an undo; never two at once; no polling and no refetch on focus;
  - a 429 is a wait, not a failure and not "no duplicates": the sets already drawn stay, and nothing is asked before `Retry-After`, across a programme change too (the budget is the user's);
  - one automatic retry per refusal. After 3 refusals in a row it stops and offers a button that is disabled until the wait is over;
  - cancel (unmount, programme change) aborts the request and clears every timer, and a late answer paints nothing.
- **Merge (C1, I5–I10).**
  - The main record is a radio group. Swapping it clears the picks and reads the preview the other way round. The radios stay mounted while that is read.
  - A table with a row header per field. Each choice is a labelled `fieldset` of two radios (stacked at 360 px, side by side from `sm`), preset to the API's default. A withheld field has no value and no choice. A readable field the API did not offer is locked and shows both values.
  - Compliance is a second, locked table showing the outcome the API computed, with "the most restrictive choice is kept" (D-P28). It is never sent.
  - The merge body carries the last preview's ids and versions and a choice for each drawn choice only.
  - The confirm dialog is the shared `Dialog` (focus in, Escape and cancel return it). A synchronous guard means a same-tick double click is one merge.
  - The result links `/contacts/<survivorId>` and never the merged-away contact. It shows Undo with `undoUntil` in `<time>`.
- **Refusals (I9, I10)**, all translated, none a raw code, in the one `duplicates-error` alert:
  - merge: `already_merged` (sets read again), `stale_write` (preview read again, new versions sent), `not_permitted` (controls stay, D-L84), `field_not_editable` at `choices.<f>` (that field is locked and never sent again);
  - undo: 410 turns the merge expired (the server's clock wins), 404 is the generic not-found words with nothing about permission, and 403 and 409 are translated. A refused undo is never sent again.
- **History (D-P27, I11).** As served, `cursor` only. Rows are open (Undo, also for another user's merge), undone (with the kept-edits note when `survivorReverted` is false), or expired ("Undo expired"). A merged-away party is never linked. A non-writer's empty list is the empty history, not an error.
- **Audit (I13, D-L162).** The web `AuditAction` enum is the admin contract's, `merged` and `restored` included. Both labels are bundled with the audit screen and are filters. It is not behind `crm_duplicates`.
- **i18n.** 63 `duplicates.*` keys, `records.error.already_merged` and `undo_expired`, `records.action.duplicates`, and the two audit labels, in all 8 catalogues. The comparison reuses the import wizard's field labels and the records status, source, channel and consent words. No plural is used (a wait is "{seconds} s"), so no catalogue needs a category it lacks. Passthroughs are declared for words spelled the same (pcm, fr).

## Decisions I made
- **Owner and account rows are not drawn.** They are ids with no name in the preview (D-L64), so a choice between two opaque ids is no choice. The merge leaves them unsent and the API's default applies.
- **`custom.<key>` choices are not drawn.** The suite serves none. A custom key in `defaults` is simply not sent, so the API's default applies. Nothing breaks on one.
- **The default main record** is the first contact the set served.
- **The 429 retries by itself**, because the wait message is static ("Trying again in N s") and the mock counts exactly four scans in the throttle journey. Having both an automatic retry and a button would double-send.
- **Undo from the history reads the sets again**, since a restored contact reappears as a duplicate. This is a scan inside the per-minute budget, and the screen never makes two at once.
- **The audit catalogue labels** are in the catalogue commit rather than the audit commit. The pre-commit typecheck needs the ids to exist before the code that names them.

## What I left out, and what I am unsure about
- **No React hook tests.** The repo has no component test setup (node environment only). That is why the scan and the merge view are a class and a reducer: all the rules are tested there, and the hooks only give them a lifecycle. The hooks and the JSX are proved by the journeys.
- **The audit screen prints the merged contact's record id** as the object label, because T-0095 labels the event with the id and the audit mock does the same. It is what the API serves, but it is an id on screen (D-L64's spirit). Worth a follow-up on the API side: a name is withheld-prone, so probably "Contact" plus a link, not an id.
- **Translations** in fr, ar, ha, ig, pcm, sw and yo are my drafts and have not been read by a speaker. All stay `awaiting-review`.
- **The comparison is a real `<table>`** with the two options stacked inside one cell at 360 px. I did not restyle table parts into blocks, because that drops the table's semantics. The journeys check overflow and axe at 360 px, and both pass.
- **The hand-run stack** differs from `run-e2e.mjs` only in having no database or API. The default process there is `NODE_ENV=production`, and the records one is `test` with the same flags. The lead's official run is still the one that counts.
