## Contract choices the suite left to me (please review)
1. **The new-account key is `newAccount`, and it holds only `{ name }`.**
   - The new account has no owner (`ownerUserId: null`). Any other field is set afterwards with `updateAccount`.
   - Keeping it to `name` keeps idempotency matching simple (see 3).
   - If P04 needs owner, tier or industry in the convert dialog, they can be added later from `CreateAccountRequest`
     without breaking anything.
2. **The success code is 200,** for both the first call and a repeat.
3. **When a repeat counts as a repeat.** D-L75 says "an exact repeat whose result is already in place" returns 200
   whatever its version. The contract defines "already in place" as:
   - status is `qualified` or `customer`; and
   - `accountId` equals the requested one, or, for `newAccount`, the linked account's `name` equals the requested name
     exactly.

   A repeat writes nothing: no audit event, and `version` does not advance. One consequence: a `newAccount` convert on a
   contact that is already linked to an account with the same name answers 200 without creating anything. I think that is
   correct, since the requested end state is in place, but say if you want a stricter rule. An `Idempotency-Key` header is
   the alternative.
4. **A contact already linked to a *different* account answers 400 `validation_failed` with
   `details[].code: already_linked`,** at `accountId` or `newAccount`.
   - I did not use 409, because no suitable code is in admin's `Error.code` enum: `stale_write` would be a lie. Adding a
     code is a shared-enum change, with i18n impact, that I did not want to make here.
   - Convert never moves a contact between accounts; that remains an `updateContact` `accountId` edit.
5. **The order of checks:**
   1. `404` for the contact;
   2. `403`, including `field_not_editable`. A caller without `contact.write` is refused before the body is read;
   3. `400` for the body;
   4. `404` for the account;
   5. the repeat rule;
   6. `409 stale_write`;
   7. `400 already_linked`.
6. **Field security for convert.** The caller must be able to **read and edit** both `status` and `accountId`. Otherwise
   the answer is 403 with `field_not_editable` naming the field.
   - Read is required too, because a repeat's `account` would otherwise disclose a link the caller may not read. This
     follows the suite header's rationale.
   - "May not read" therefore also produces `field_not_editable`. That code is broader than its name suggests.
7. **Permissions.**
   - Linking an existing account needs `contact.write` only.
   - Creating an account (`newAccount`) also needs `account.write`, which is admin-only (D-P18).
   - The `agent` set cannot convert, because convert sets `accountId`. Under D-P18 the same applies to `team_lead` and
     `programme_manager`.
8. **`listLeads` `q` also matches `companyName`** once T-0076 serves it, and only when the caller may read it. It keeps
   listContacts' schema. P04's Leads search also mentions Email, but email is not searched: listContacts does not search
   it, and I did not want the two lists to diverge more than the company column.
9. **Audit.** One event, on the contact (`objectType: contact`), naming `status` and `accountId`. An account created by
   convert is recorded in that same event, not in its own `account` event.
   - The consequence is that the new account's own audit trail has no creation event. T-0076's suite should pin how that
     one event refers to the account (for example, by id only).
