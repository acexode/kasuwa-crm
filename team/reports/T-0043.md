## What changed

**Contract first** (`docs/api/records.openapi.yaml`, commit 1):
- `GET /api/v1/me/programmes`, `listMyProgrammes`, tag `me`, `x-kasuwa-implemented: true`, screen `P04/02`. It takes no
  parameters and no body. It documents 200 (`MyProgrammeList`, closed `{ data: MyProgramme[] }`; `MyProgramme` closed
  `{ id: uuid, name }`, with a `Cache-Control: no-store` header), 400 (scope headers) and 401. It has no 403.
- `Contact.owner`: `oneOf [ContactOwner, null]`. `ContactOwner` is closed `{ id: uuid, displayName }`. The description
  says it is withheld together with `ownerUserId`.
- There is no user-lookup operation. The info block says why.

**Implementation** (commit 2):
- `packages/domain/core/src/programme/my-programmes.repository.ts`: `listMyProgrammes(tx)` joins the session user's
  `user_programme` rows to `programme`. The tenant and the session's programme ids are applied on both tables, and
  RLS applies on top. It takes no argument except the transaction. It never reads the tenant-admin flag. It never
  selects `client_name`.
- `apps/api/src/me/me.controller.ts`: `@Controller('api/v1/me')` with `KasuwaAuthGuard`,
  `TenantTransactionInterceptor`, `AdminErrorFilter` and `@Header('Cache-Control', 'no-store')`. It lives outside
  `src/auth` on purpose (apps/api CLAUDE.md 7). It is registered in `AppModule`'s `CONTROLLERS`, which also adds it to
  the telemetry vocabulary.
- `contact.repository.ts`: `Contact.owner: ContactOwner | null`. The name comes from a correlated subquery that is
  part of `SELECT_COLUMNS`, matched on `(tenant_id, id)` to the row's own tenant and owner. So it is read by the same
  statement on list, get, and insert/update `RETURNING`. That means a name only exists next to a row the statement
  already returns, and no input is keyed on a user id. I used a subquery rather than a JOIN so every unqualified
  column in those statements still means the contact's column.
  - `contactOwnerOf()` throws `ContactOwnerUnresolvedError` if an owner id has no readable name. The composite FK
    makes that impossible today. The alternative, sending `owner: null` beside a set `ownerUserId`, would claim the
    contact is unassigned.
- `contact-wire.ts`: `owner` is a derived wire property. `withheldWireFields()` puts `owner` straight after a
  withheld `ownerUserId`, and `toContactWire` leaves it out. There is deliberately no matrix row for `owner`, so the
  two can never disagree.
- `team/FEATURES.md` regenerated with `node tools/generate-features.mjs`. It adds one row, `listMyProgrammes`, as
  built. During the rebase I regenerated it rather than hand-merging.

     returned 401.
   - The other suites use the factory form (`audit-coverage` 1537, `dispositions-scripts` 763).
   - **Suggested lead edit:** `const cases: [string, () => request.Test][]`, then `await pending()`.
   - The behaviour the test means to check (401 for all three, no names) passes in

## What was hard
- Making `owner` follow field security without inventing a matrix field. The matrix is keyed by `field_def.api_name`.
  Adding `owner` to `WITHHOLDABLE_CONTACT_FIELDS` would have given it its own level (default `edit`), which could
  disagree with `owner_user_id`. A derived wire field avoids that.
- Keeping the change off the write path that T-0051 is editing. The only write-side effect is that `SELECT_COLUMNS`
  now carries the owner subquery, so create and update responses satisfy the `Contact` schema. The T-0041 suite reads
  Contact's property list from the spec, and already expects `owner` on every response. I did not touch
  `contacts.service.ts` or the permission path.
  - Expect small conflicts with T-0051 in `contact-wire.ts`/`contact.repository.ts` only if it edits the same lines.
  - A fixture there will also need `owner: null` added (I added it to `contact-audit.test.ts`).

## Left out, deliberately
- Whether an archived programme appears in `/me/programmes`. The suite takes no side. Today it does, because the
  session's programme ids include every membership, whatever its status.
- Ordering: by name, then id. The suite does not assert an order.
- Strict 400 on unknown query parameters. They are ignored, as on `listContacts`; the suite accepts either.

## Open questions
1. **Stale owner after a membership is removed.** D-L67 checks membership only when an owner is assigned. If the owner
   later leaves the contact's programme, the contact still names them, to people who can see that contact. That shows
   a person's name, not that another programme exists, so I did not treat it as the task's escalation case. Restricting
   the embedded name to current members would break the suite's `owner === null iff ownerUserId === null` rule.
   **Does a removed owner keep their name on the record, or should removal unassign?** That is the open D-L61 item
   ("what happens to contacts when ... owner is deleted").
2. T-0052's `AccountOwner` has the same shape as `ContactOwner`, and its description already says they may merge. One
   shared `RecordOwner` schema would be a contract edit for T-0055 or the lead.
3. Process: the RAM-slot convention does not cover git hooks. Pre-commit ran workspace lint, and the post-edit hook
   ran unit tests, outside any slot. The one OOM I saw came during a lint run while both slots were held.
