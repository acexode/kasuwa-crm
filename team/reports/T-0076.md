## What changed

- **Migration 0028** (`0028_contact_company_name.sql`), one transaction. The header covers lock impact (D-L65) and the rollback plan.
  - Lock order is catalogue, then contact. `object_def` and `field_def` are locked first, in SHARE ROW EXCLUSIVE (writes blocked, reads pass). `contact` is locked ACCESS EXCLUSIVE only LAST (review fix), after the pre-check, the backfill and the proof. It is then held only for ADD COLUMN, the CHECK and the COMMENT. The reviewer measured about 1 s of contact blocking at 2,000 tenants with the first order, and about 5 ms with this one.
  - D-P24 clash pre-check before anything changes. A custom `company_name` on `contact` in any tenant stops the file with `0028: a custom field company_name on object contact clashes ... in N tenant(s). Nothing was applied. ...`. A custom `company_name` on another object is not counted.
  - `ALTER TABLE contact ADD COLUMN company_name text`: nullable, no default, no rewrite.
  - `contact_company_name_length_check`, `char_length BETWEEN 1 AND 200`, added `NOT VALID`.
    - No scan of `contact`, but it binds every new write.
    - Every existing row holds NULL, because the column is created in the same transaction, so nothing can break it.
    - **It stays NOT VALID on purpose** (D-L65). A validating ADD CONSTRAINT would scan all of `contact` under the lock: 0.5–0.8 s at 3M rows. A later `-- kasuwa:no-transaction` `ALTER TABLE contact VALIDATE CONSTRAINT contact_company_name_length_check` (SHARE UPDATE EXCLUSIVE) may validate it.
  - Backfill: a standard `field_def` `company_name` (label `Company`, `text`, not required, `{}`, classification `pii` per D-L82) on every tenant's standard `contact`.
  - Proof: every tenant has the field with the catalogue's meaning; there is no standard contact field outside the catalogue's 18; there is no tenant without a standard `contact`.
  - No new table, no SECURITY DEFINER, no new grant. Contact's table-level grants to kasuwa_app (SELECT, INSERT, UPDATE and DELETE) cover the column.
