## What changed

- **Migration `0015_permissions_engine.sql`** (hand-written; the header argues each part):
  - `user_programme.permission_set_id uuid` (nullable; NULL means no permission). Composite FK
    `(tenant_id, permission_set_id) → permission_set (tenant_id, id)`, plus an index.
  - `"user".is_tenant_admin boolean NOT NULL DEFAULT false`. **kasuwa_app can no longer write
    it.** Table-level INSERT and UPDATE on `"user"` are replaced by column grants on every other
    column. Before this change, any statement on the request connection could have made its own
    user a tenant admin.
  - D-L51: two **AS RESTRICTIVE** policies on `user_programme` (`…_insert_in_scope` FOR INSERT,
    `…_update_in_scope` FOR UPDATE with USING = WITH CHECK). Each requires that the programme is
    either in `app.current_programme_ids()` or was written by the current transaction. No
    permissive FOR INSERT policy was added. SELECT and DELETE are untouched, because the session
    resolver reads memberships before scope is known.
  - One **permissive FOR SELECT** policy on `programme`, `programme_visible_to_creating_transaction`
    (see the marker below). It is not a FOR INSERT policy, so the allow-list catalogue test is unchanged.
- **The marker for "created in the same transaction" is the programme row's `xmin`**, compared with
  `pg_current_xact_id_if_assigned()::xid`. I chose it over a transaction-local GUC because every
  custom `app.*` setting can be set by kasuwa_app with `set_config`. A GUC marker is therefore
  forgeable from any statement on the request connection, the same weakness ADR-0010 records for the
  scope GUCs. The server stamps `xmin` and no SQL can choose it. A row version carrying this
  transaction's xid is one of two things. It may be a programme this transaction inserted, and
  `programme_insert_in_tenant` limits those to the session's tenant. Or it may be a programme this
  transaction updated, which had to pass the programme-scoped FOR ALL policy first. So the marker can
  never name an existing programme outside scope. The restrictive policy's subquery has to *see* the
  new row, and the FOR ALL policy hides it. That is the only reason the FOR SELECT policy exists. It
  admits the rows this transaction wrote itself, for the rest of that transaction, and nothing else.
  `_if_assigned` never forces an xid onto a read-only transaction; without an xid it returns NULL and
  the predicate is false. Edge case: an insert made inside a SAVEPOINT carries the subtransaction's
  xid, so its membership is refused. That edge fails closed. Nothing here uses SECURITY DEFINER, and
  no view or ownership trick stands in for it (CLAUDE.md 2.7).
- **`@kasuwa/permissions`** (was a placeholder): `policy.ts` holds the pure decision.
  `canTenant` requires the flag. `canProgramme` requires the programme to be reachable, then accepts
  tenant admin or a set key on the allow-list, and only `admin` is on it. `grants.ts` holds
  `loadGrants`, `mayTenant` and `mayProgramme`. They re-read `"user"` and `user_programme ⨝
  permission_set` on every call, using the session's tenant, user and scope with explicit predicates
  on top of RLS. New workspace deps: `@kasuwa/db` and `zod` in `@kasuwa/permissions`, and
  `@kasuwa/permissions` in `@kasuwa/api`. All are workspace links or already in the lockfile, so no
  new third-party package was added.
- **`apps/api/src/admin/common/admin-permissions.ts`**: `requireTenantPermission` and
  `requireProgrammePermission` throw `notPermitted()`. Every handler calls them in the same order:
  404 (programme; for disposition update and delete, the disposition too, via the new
  `dispositionExists` in domain-core; for role update and delete, the role), then 403, then body or
  query parsing. A refusal throws before any write, so it is never audited.
  - Tenant-level: createProgramme, updateProgramme, createRole, updateRole, deleteRole,
    updateRoleHierarchy, updateFieldSecurityMatrix, createAuditExport.
  - Programme-scoped: archiveProgramme, create, update, delete and reorder of dispositions,
    invitePortalUser, updateProgrammeSla, updateProgrammeRetention.
- **createProgramme** enrols the creator holding the tenant's `admin` set. If the tenant has no
  such set, the membership gets NULL.
- **Seed and fixtures**: `SeedUser` gains `isTenantAdmin` and `permissionSetKey`. USER_A_SUPERVISOR
  and USER_B_AGENT_1 are tenant admins and hold `admin`; the agents and the unassigned user hold
  `agent` and are not tenant admins. Permission sets are now seeded before users, because of the FK.
- **Spec**: `reorderDispositions` gains `403`. I also corrected the stale "no permissions engine"
  prose on createProgramme, updateProgramme, archiveProgramme, the audit tag and

## What I left out, and why

- `user_programme` DELETE is not restricted to in-scope programmes. D-L51 names INSERT and UPDATE
  only. Removing someone from a sibling programme is still possible at the database level for any
  code path that issues the DELETE. The adversarial suite also deletes a membership through
  kasuwa_app. Worth a follow-up decision.
- `permission_set` is still fully writable by kasuwa_app. A `field-security-matrix` acceptance
  fixture inserts a set through the app pool, so I could not revoke INSERT. The engine matches
  `key = 'admin'`, which is unique per tenant. No endpoint writes `permission_set`, but a raw
  `UPDATE … SET key` on the request connection could re-key a set. Revoking UPDATE (key) is a cheap
  follow-up.
- Audit reads are still open to every tenant user (D-L48 names restricting them; not ruled for this round).
- Admin-home alert dismiss/restore are not permission-checked. They are not in D-L53's list.
- No endpoint assigns permission sets or the tenant-admin flag. Both are operator actions for now.

  transaction wrote. I believe that set is exactly "programmes this session just created", for the
