## What changed

  (`NOLOGIN NOBYPASSRLS NOINHERIT NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION`, no password)
  only if it does not exist; an existing role is left alone. It is no longer named in `GRANT CONNECT`,

  comments included. The header says which file real provisioning applies.
- **New `packages/db/sql/bootstrap-test.sql`** (dev and test only): creates the role if missing, then
  `ALTER ROLE ... LOGIN BYPASSRLS PASSWORD 'kasuwa_test_admin_dev' NOSUPERUSER NOCREATEDB NOCREATEROLE
  NOREPLICATION`, `CONNECT`, `USAGE` on public and the same three default privileges it had on main.
  Idempotent, and a re-apply changes nothing in the privilege census.
- **Who applies it**: docker-compose's init directory (`20-bootstrap-test.sql` after `10-bootstrap.sql`),
  `tools/dev.mjs` (re-applies both on every `pnpm dev`), and `packages/testing/src/containers.ts`
  (both, in order). Nothing else.
- **`@kasuwa/config`**:
  - `database-target.ts` (new): `effectiveDatabaseTarget` parses with `pg-connection-string` and applies
    pg's own fallbacks (URL, then `PGHOST`/`PGPASSWORD`, then pg's default host) from the given source;
    `isLocalDatabaseHost` is exactly the R5 list; `assertMigrationTargetIsSafe` is the runner's
    pre-connect check (below).
  - `server-env.ts` (new): the exported `apiEnv` and `workerEnv` now wrap the schemas and, outside
    development and test, refuse a `DATABASE_URL` / `DATABASE_AUTH_URL` (API) or `DATABASE_URL` (worker)
    whose effective password is a repo dev password, and refuse `PGHOST`, `PGPASSWORD`, `PGUSER`.
  - It is TypeScript and not in `schemas.mjs` on purpose: `apps/web` imports `web.mjs` -> `schemas.mjs`
    natively and through Next's bundler (instrumentation), and `pg-connection-string` can `require('fs')`.
    Keeping it out of `schemas.mjs` keeps it out of the web graph. Consequence: `schemas.mjs`'s own
    `apiEnv`/`workerEnv` lack the credential guard; nothing imports them except through the index.
- **`runMigrations`** (`packages/db/src/migrate.ts`): new optional `env?: EnvSource`. Before connecting it
  calls `assertMigrationTargetIsSafe(connectionString, env)`:
  1. `migratorEnv(env)` (invalid NODE_ENV such as `''`, `staging`, `Production` is refused; stub auth in
     production is refused);
  2. NODE_ENV absent from the source, read raw: allowed only if the effective host is local, then treated

  3. outside development and test: refuse `PGHOST`/`PGPASSWORD`/`PGUSER`, and a repo dev password as the

  Then, outside development and test, its first query (before the advisory lock and the ledger) reads
  `pg_roles` + `pg_auth_members` and refuses a `kasuwa_test_admin` with LOGIN, BYPASSRLS, SUPERUSER,

- **`db:reset`**: judged the host with `new URL().hostname` (fooled by `?host=`) and dropped every table

## What was hard

- **Where the URL parser can live.** `@kasuwa/config`'s schemas are JavaScript that the web build loads
  natively, and `pg-connection-string` may `require('fs')`. Putting the guard in `schemas.mjs` would have
  pulled it into the Next instrumentation bundle. The wrapper module keeps the web graph unchanged, at the
  cost of `schemas.mjs` exporting a guard-less `apiEnv`/`workerEnv` (only reachable by importing that file
  directly).
- **Grants for the placeholder.** I moved the test role's CONNECT, schema USAGE and default privileges into
  `bootstrap-test.sql`, so in a real cell the placeholder holds only what the migrations grant by name.
  The suite allows "at most main's", so this is stricter than required; the harness gets exactly main's.
- **The runner calls `migratorEnv`.** That is what makes `NODE_ENV=''`/`staging` a refusal (R1) and keeps
  the stub-auth guard on every caller, but it also means a production migration needs
  `KASUWA_AUTH_MODE=jwt` in its environment even when invoked programmatically (R2 anticipates this).

## Lead rulings applied (follow-up commit)

1. **Managed Postgres:** an ADMIN-only membership (`admin_option` true, `inherit_option` and `set_option`
   false) was first ignored outright. **Narrowed by D-L95 and the security reviews:** it is ignored only
   when it is IN the role, its holder is SUPERUSER or CREATEROLE, and the checking role cannot reach the
   holder (`NOT pg_has_role(current_user, holder, 'MEMBER')`). Every other membership, either
   direction, is refused, including ADMIN-only held by kasuwa_app (which can self-grant WITH SET). Unit test pins the SQL; a new integration test
   (`packages/testing/src/test-admin-membership.integration.test.ts`, its own bare cluster) checks the boot
   check and the runner in production against two ADMIN-only shapes (ignored) and four SET/INHERIT shapes
   (refused). `packages/db/CLAUDE.md` invariant 10 says so.
2. **No-host URL is non-local** for the unset-NODE_ENV rule (`namesLocalDatabaseHost`): only a host the
   connection string itself names (a `?host=` included) can be local, whatever PGHOST or pg's default say.
   `db:reset` uses the same rule. Unit-tested (no host, PGHOST=localhost, PGHOST remote, userinfo with no
   host, empty `?host=`).
3. **PGPASSFILE** is refused outside development and test with PGHOST, PGPASSWORD and PGUSER (runner, API,
   worker). A default `~/.pgpass` stays a documented limit.
4. `packages/testing/CLAUDE.md` invariant 4 names `bootstrap-test.sql`.
5. The new dependency is accepted (the lead adds the justification to the PR).

## Left out / limits

- **db:reset through a loopback tunnel.** With NODE_ENV unset and the URL naming a loopback host,
  db:reset is treated as development and still drops every table, even if the loopback is a
  cloud-sql-proxy, `kubectl port-forward` or SSH tunnel to a real cell. The lead is ruling on it
  separately.
- **Loopback tunnels** (cloud-sql-proxy, kubectl port-forward, SSH) let an unset NODE_ENV migrate as
  development; the API and worker boot checks catch a real cell at its next deploy.
- **A default `~/.pgpass`** (no PGPASSFILE set) is not inspected; a dev password stored there is not
  detected (lead ruling: documented limit).
- **Effective values come from the given source.** If a caller passes `env` explicitly while the real
  `process.env` has `PGHOST`, pg uses the latter and the guard judges the former. Production callers use
  the default (`process.env`), where the two agree.
- **The worker boot check has no worker-level test**: it calls the tested `@kasuwa/db` function directly
  in `main()`, which has no harness today.
- Pre-existing prettier drift in `packages/db/src/migrate.ts` left as is (only my new files formatted).
