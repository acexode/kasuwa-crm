## What changed

**Migration `0006_roles_and_permission_sets.sql`**

- `role` — `tenant_id NOT NULL`, RLS enabled + forced, one `FOR ALL` policy
  with `WITH CHECK` = `USING` (tenant predicate only; the header says why it
  is not programme-scoped). Parent is a **composite** FK
  `(tenant_id, parent_role_id) → role (tenant_id, id)`, so a cross-tenant parent
  is impossible, not just rejected. Name unique per tenant on
  `(tenant_id, lower(name))`, never globally.
- `permission_set` — same invariants. `key` is the spec's `permissionSetId`
  (shape-checked, ≤ 64), unique per tenant; `locked` is the Admin padlock;
  `sort_order` gives the design's column order. `UNIQUE (tenant_id, id)` is
  there for the D-P9 `user_programme` link in the next task.
- `app.role_assert_acyclic()` + `AFTER INSERT OR UPDATE OF parent_role_id`
  trigger: a second, independent refusal of cycles. **SECURITY INVOKER** (the
  default) — not a third definer function; it runs under the caller's RLS,
  which is enough because the composite FK keeps every ancestor in-tenant.
- `tenant.role_hierarchy_version integer NOT NULL DEFAULT 1` — `RoleList.version`.
- `"user".role_id uuid NULL` + composite FK `(tenant_id, role_id) → role`,
  added `NOT VALID` then validated, plus an index. This is what `userCount`
  counts and what `deleteRole` reassigns. **See open question 2.**
- Explicit `GRANT`s for `kasuwa_app` / `kasuwa_test_admin` on both tables,
  restating what the bootstrap default privileges already give.

**`packages/db`** — Drizzle mirror for both tables and the two new columns;
`role` and `permission_set` added to `TENANT_SCOPED_TABLES`; six default
permission sets per seeded tenant (Agent, Team lead, QA analyst, Programme
manager, Client portal, **Admin — locked**), with fixed, obviously-invented
ids of kind `00000010`.

**`apps/api/src/admin/roles/`** — its own Nest module.

- `role-hierarchy.ts` — the only implementation of "beneath" and "is this a
  cycle", pure and unit-tested: `descendantsOf`, `rolesOnCycles`,
  `cycleConflicts` (returns only ids the caller submitted), `planRoleDeletion`.
- `roles.service.ts` — every statement inside the request's
  `withTenantTransaction` (via `currentTx()`), every statement with an explicit
  `tenant_id = $1` as well as RLS. Every write first takes the tenant row
  `FOR NO KEY UPDATE`, which serialises hierarchy writers per tenant (two
  concurrent moves, each acyclic alone, cannot commit a loop together) without
  blocking FK checks that take `FOR KEY SHARE` on `tenant`.
- `roles.schemas.ts` — Zod, every object `.strict()` (spec:
  `additionalProperties: false`; a `programmeId` in the body is refused, not
  ignored). Duplicate `roleId`s in one hierarchy write are a 400.
- `admin-errors.ts` — the spec's `Error` envelope and an `AdminErrorFilter`
  applied with `@UseFilters` **on the admin controllers only**. It gives the
  guard's bare 401 `code: not_authenticated` and the scope-header 400
  `code: validation_failed` without touching the global filter, so auth and
  contacts behave exactly as before. A unique violation becomes
  `duplicate_name` with no row named; an FK violation becomes `not_found`.
- A malformed role id is `404 not_found`, the same body as a missing or
  another tenant's role. Cross-tenant is always 404.
- `app.module.ts` — imports `AdminRolesModule`, and the root dynamic module is
  now `global: true, exports: [AUTH_MODE]`. **This was not the one-line change
  asked for, and why matters for Agents 2 and 3:** Nest resolves a guard's
  dependencies in the module that hosts the controller, and `AUTH_MODE` is only
  provided on `AppModule`. Importing a feature module whose controller uses
  `KasuwaAuthGuard` fails at boot with "can't resolve Symbol(AUTH_MODE)". With
  the export in place, each sibling admin module is a one-line import.

**`docs/api/admin.openapi.yaml`** — seven flags flipped; the
`listPermissionSets` description no longer says there is no table, and says
why `userCount` is `null`.

## What was hard

- **The version.** "Of the hierarchy as a whole" needs one row per tenant.
  A global sequence would leak another tenant's rate of admin activity; a
  `max(updated_at)` is not an integer and can go backwards on delete. The
  tenant row is the one per-tenant row there is, and locking it is also the
  concurrency control the cycle check needs, so it does two jobs.
- **`conflictingIds` without disclosure.** A cycle can run through roles the
  request never named. The function reports, for each move whose role lands on
  a cycle, that role and the parent it asked for — both submitted — and nothing
  else. Unit-tested on a loop that runs through unnamed roles.
- **Check order in `deleteRole`.** The suite pins it: reassign-to-self is a
  cycle before anything; an unknown target is 404; a target in the subtree is a
  cycle. That is `planRoleDeletion`, tested in isolation.

## What I left out — known gaps, stated plainly

1. **No `403 not_permitted`.** As instructed: there is no permissions engine,
   so any authenticated user in the tenant can administer roles. The acceptance
   suite drives tenant A as a *supervisor* and tenant B as an *agent*, so a
   check added later must still let those through or the suite changes.
2. **No audit rows.** `createRole`, `updateRole`, `deleteRole` and
   `updateRoleHierarchy` are `x-kasuwa-audited: true`, the spec says such an
   operation "MUST write an audit row when it is implemented", and CLAUDE.md
   6.7 lists permission changes. There is no audit table and audit is out of
   scope for this task; adding one is a new table, which is a decision. **These
   operations are therefore live and unaudited.** I recommend the lead either
   keep them behind a feature flag until the audit table lands or accept the
   gap explicitly. I did not add a flag: none was specified, and the acceptance
   suite calls the routes directly.
3. **No OpenAPI decorators.** `@nestjs/swagger` is not a dependency, and the
   spec is hand-written and authoritative. Each handler's doc comment names its
   method, path, `operationId` and statuses.
4. **No role seed.** Only permission sets are seeded. A dev database starts
   with an empty hierarchy and every `userCount` at 0; nothing assigns
   `"user".role_id` yet.
5. **`locked` is stored, not yet enforced** — there is no matrix write to
   refuse. That is the next task (T-0023-adjacent / D-P9).
6. **Tenant provisioning does not create the default permission sets**, because
   there is no tenant provisioning. Whoever builds sign-up must insert them.
7. **The spec header** still says "none is `true`" and "no role table". I left
   it alone because Agents 2 and 3 are editing the same file in parallel; the
   lead should reconcile it at merge.

## Open questions

1. **Audit** — see gap 2. This is the one I would not merge past without an
   explicit answer.
2. **`"user".role_id` is a schema decision I took.** The spec's `userCount`
   ("people directly in this role") and `deleteRole` ("move its people") imply
   one tenant-wide role per user, and the task asked for reassignment logic, so
   something had to hold the assignment. A nullable column with a composite FK
   is the smallest expand-only shape. If the permissions engine wants roles per
   programme, this becomes a `user_role` table and the column is contracted
   away — nothing reads it but this module.
3. **`userCount` counts every user holding the role, disabled ones included.**
   Say if disabled users should be excluded from the count (reassignment
   should move them regardless).
4. **Role names are unique case-insensitively.** The spec says "unique in this
   tenant" without saying about case; "Team Lead" and "team lead" side by side
   looked like a mistake rather than two roles.

No acceptance test looked wrong to me.

## Reviews

I had no subagent tool in this session, so `migration-reviewer` and
`tenancy-reviewer` were **not run**. What follows is a self-review against
their checklists, which is weaker evidence. Please run both.

- Append-only: pass. New file `0006` only; no applied migration edited.
- Expand-only: pass. Two new tables, two nullable or defaulted columns, no
  drops or renames. `ADD COLUMN … DEFAULT 1` is metadata-only on PG11+. The
  `"user"` FK is added `NOT VALID` then validated. The index on `"user"` is not
  `CONCURRENTLY`; the table is small and the runner is per-file transactional.
- Tenancy: pass by inspection. `tenant_id NOT NULL` on both tables, ENABLE +
  FORCE, one `FOR ALL` policy each with identical USING/WITH CHECK, composite
  FKs, both tables in `TENANT_SCOPED_TABLES`, the reason there is no programme
  scope stated in the header. No new `SECURITY DEFINER`.
- Queries: every query runs via `currentTx()` inside the interceptor's
  `withTenantTransaction`, with an explicit `tenant_id = $1` on every statement
  and `"user"` quoted. No scope comes from the request; `.strict()` bodies
  refuse `programmeId`.
- Leakage: cross-tenant and malformed ids give one 404 body. `duplicate_name`
  names no row. `conflictingIds` returns only submitted ids. pg error text is
  never echoed.
- Verification: **fail / not done.** It has not been run against Postgres.

Rollback plan: the change is expand-only and nothing outside this module
reads the new columns or tables. Rolling back the application leaves them
inert. A contract migration could drop `"user".role_id`, the trigger and
function, `tenant.role_hierarchy_version`, `role` and `permission_set`, in
that order.
