## Summary

Two defects, one change.

**FINDING-1.** The GUCs cannot be sealed, and the three obvious ways to seal
them do not work for the same structural reason. They are now **verified**
instead: the session context is read back immediately before COMMIT and a
divergence rolls the transaction back and throws, so a result read under a
changed scope is never returned and a write made under one never commits.
ADR-0010 is new and argues this; ADR-0002's "it holds even if a controller is
wrong" is corrected in the same change.

**FINDING-3.** `auth_rate_limit`'s `USING (true)` is replaced by a policy that
admits a row only to a session presenting that row's `key_hash`. The exemption
from `tenant_id` is untouched and still right; ADR-0009's argument for the
*policy* was the wrong part, and the amendment says so rather than quietly
rewriting the file.

`pnpm lint`, `pnpm typecheck`, `pnpm test:unit` and `pnpm test:integration` all
pass. `pnpm test:isolation` fails on **exactly the two characterisation tests
and nothing else** — see "Gates" below.

## FINDING-1 — what I found when I tried to seal it

The task offered three options. Two of them do not work, and that is the most
useful thing I have to report.

**Revoking `set_config` from `kasuwa_app` closes nothing.** `SET LOCAL
app.tenant_id = '…'` reaches the same GUC without calling the function.
Postgres 15's `GRANT SET ON PARAMETER` cannot help: the documentation is
explicit that it "cannot be used to restrict a parameter that any user could set
anyway", and a custom GUC in an unreserved class is USERSET. The control would
have been decorative, and would have cost a third `SECURITY DEFINER` function
for nothing. There is a test that attacks with `SET LOCAL` specifically, so that
anyone who later replaces this with a statement filter finds out.

**A narrow-only setter has the same problem** — it is only narrow-only if it is
the sole path to the GUC, which it cannot be.

**A seal (nonce, HMAC, sequence) fails deeper.** `withTenantTransaction` and its
callback are the same role on the same connection: any secret the framework can
read the callback can read, any function it may call the callback may call, any
GUC it may set the callback may set. There is no write-once state inside a
Postgres transaction — `set_config`, temp tables and advisory locks are all
re-enterable and `ROLLBACK TO SAVEPOINT` restores rather than freezes. The only
asymmetry available is a row in a migrator-owned table, i.e. a write plus an
index lookup per policy evaluation on every request.

**So there is no privilege boundary between a framework and its callback on one
connection under one role.** A real boundary is a proxy, a role per tenant or a
database per tenant — which is what Bridge and Silo already are. That is now
written down in ADR-0002 and ADR-0010, and it turns the isolation tiers into a
security argument rather than only a compliance one.

### What I built instead

`assertScopeIntact` in `packages/db/src/session.ts`, called immediately before
COMMIT by both `withTenantTransaction` and `withAuthTransaction`. It reads the
three GUCs back, compares them as text with what was resolved, and on any
difference throws `SessionScopeViolationError` — which rolls back and **discards
the callback's return value**. Two enforced properties: a forged read cannot
leave the transaction, a forged write cannot commit.

Cost: one extra round trip per transaction (three `current_setting` calls, no
table access).

**Why before COMMIT rather than per statement.** Per-statement checking buys
nothing — a caller can restore the GUCs inside one statement either way — and it
costs a doubling of round trips *and* breaks a legitimate pattern: `ROLLBACK TO
SAVEPOINT` reverts a transaction-local `set_config`, which the existing
acceptance test `narrows, never widens, when a subtransaction is rolled back`
exercises. That test passes unmodified, and I added an integration test that
pins the same case from my side so the reason is visible next to the control.

The error message names no identifier. It is thrown where the values in play may
belong to another tenant, and an error is a leak channel (section 6 rule 4).
There is a unit test asserting the message contains no id and is not empty.

## FINDING-3 — the policy

Migration `packages/db/migrations/0004_rate_limit_key_scope.sql`:

- `app.current_rate_limit_key()` — reads the transaction-local GUC
  `app.rate_limit_key`, returns NULL when unset, same fail-closed shape as the
  three accessors in 0000. **Not `SECURITY DEFINER`**; the count stays at two.
- `auth_rate_limit_presented_key` replaces `auth_rate_limit_open`, with
  `WITH CHECK` identical to `USING`.
- A `DO` block at the end that raises if any policy on the table is `true`, on
  the same principle as 0003's grant assertions: a later migration re-opening
  the table would otherwise make everything above a story about something that
  is no longer true.

`presentRateLimitKey` in `packages/db/src/auth.ts` presents the key
transaction-locally before each of the three store functions, which still write
`key_hash = $1` themselves — the table now has the two independent layers every
other table has, which retires the rule-3 deviation ADR-0009 accepted.

**Contract change worth flagging in review:** the store must now be called
inside a transaction on one connection. It fails closed if it is not (the
setting lapses, the policy denies, the write errors) and there is a test for
that, but it is a change and `packages/db/src/auth.integration.test.ts` had to
move off a plain pool because of it. Every production caller already passed an
`AuthTx`.

Properties I checked rather than assumed, each with a test:

- a session presenting no key sees **no** rows and deletes **none**;
- a session presenting key A sees exactly one row, and it is A's (so the
  emptiness assertions above are about the policy, not an empty table);
- `WITH CHECK` refuses a write under a key that was not presented;
- **the unresolved-workspace write still succeeds and still counts** — the
  property the whole table exists for. This is the one that would have made the
  fix wrong if I had got it wrong.

## What I left out, and open questions

- **`app.rate_limit_key` is itself a GUC the callback can set**, so FINDING-1's
  reasoning applies to it too. It does not matter: the GUC confines to one hash
  the caller must already be able to compute, so setting it grants nothing that
  making sign-in requests does not. Worth a reviewer's eye anyway, because it is
  the sort of thing that looks like a contradiction at a glance.
- **`assertScopeIntact` does not cover a callback that restores the GUCs before
  returning.** That is deliberate and documented in ADR-0010 as the limit of the
  control. If the threat model ever includes hostile code inside the monolith,
  the answer is a proxy or a role boundary, not a bigger check here.
- **The retention sweep for `auth_rate_limit` now has a hard constraint**: it
  deletes keys it does not know, so it must run as `kasuwa_migrator`. Recorded
  in ADR-0009 and in migration 0004. The sweep task should be told, or it will
  meet this as a mystery failure.
- I did not touch FINDING-2, -4 or -5; they are other owners'.
