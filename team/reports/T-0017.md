## What was hard

- **What to do with a provider throw the adapter cannot classify.** I made it
  `ProviderRejectedError` (not retryable) on `send`, and
  `ProviderUnavailableError` (retryable) on `getDeliveryStatus`. Reason: a
  timeout after the provider has actually accepted is indistinguishable from a
  failure, and with no idempotency key a retry can double-send. Status reads
  are idempotent, so retrying them is harmless. A real provider is expected to
  classify its own failures (timeouts/5xx as `ProviderUnavailableError`); the
  fallback only catches what it forgot. The lead may prefer the opposite
  default — it is one line in `adapter.ts`.
- **A DND lookup that fails** has no code of its own in the contract. I raise
  `ProviderUnavailableError` (retryable) and never send. A dedicated code
  (`dnd_unavailable`) would be clearer, but that changes the contract, so I
  did not add one.

## Open questions

1. **The provider decision is still open** (WhatsApp via a BSP, SMS via a
   Nigerian aggregator, or both — spend and a contract, so @acexode's). The
   task asks for options with real per-message prices in `DECISIONS.md`; I did
   not have pricing data and did not write to governance. It needs raising by
   the lead. The acceptance test "names no vendor anywhere yet" should be
   removed when it lands.
2. **Idempotency gap — recommend fixing before T-0016.** `send` has no
   idempotency key. A caller that retries a retryable `ProviderUnavailableError`
   (as the error invites it to) after a timeout the provider actually accepted
   will send the message twice — for a sign-up OTP, two different codes, the
   first of which the user may type. Recommendation: a required
   caller-supplied `idempotencyKey` on `SendRequest`, deduplicated in the
   adapter for the fake and passed to the real provider where it supports one.
   That is a contract change, so it needs the lead's say-so and an updated
   acceptance test.
3. **DND lookup cost.** If the real register is a licensed per-lookup service,
   that is spend and a compliance dependency (the task's escalation trigger).

## Risks I am aware of

- Personal data: the fake keeps accepted requests (including number and body)
  in memory in `sent`; that is test-only and never logged. Nothing else stores
  or emits them.
- Tenancy: no database access in this package. Delivery-status reads are
  scoped by tenant and programme in the fake; a real provider must enforce the
  same, since the adapter cannot see a provider's records. A future real
  provider should persist message ownership in a Kasuwa table (a new table is a
  decision — raise it then).

## Security-review follow-up (commit 6221161)

Four review findings were addressed.
1. **DND fails closed.** Only a literal `false` from the register clears a number; `undefined`, `null` or any non-boolean is refused.
2. **The wrapper enforces delivery-status scope** instead of trusting the provider. The adapter records messageId → {tenantId, programmeId} at send time and answers any other scope with `MessageNotFoundError`, the same answer as for an unknown id. A unit test proves a scope-ignoring provider cannot leak across tenants or programmes. The map is an in-memory stand-in capped at 10,000 entries; a real provider needs a durable tenant-scoped store, which is a new table and so a decision to raise.
3. **Provider output is Zod-parsed** before it is returned or logged. Malformed send output becomes `ProviderRejectedError`, not retryable since the message may have gone. Malformed status output becomes `ProviderUnavailableError`.
4. **The fake's `sent` buffer is capped at 1,000.** The fakes stay on the main entry, because the acceptance suite imports them there. Lead decision: a lint rule forbids importing them from application code instead.

**Gates:** lint, typecheck, unit (330) and boundaries pass. The acceptance file passes 11/11 without Testcontainers. Integration, isolation and the isolation-project acceptance run are not run (Docker down).
