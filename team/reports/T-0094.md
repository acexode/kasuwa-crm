The failures fall into four causes. Each needs a lead edit or a ruling. I have not edited any test.

1. **The suites' SQL (test defects, 4 tests).**
   - import-api "every FK on import_job carries tenant_id..." and "contact.import_job_id is a nullable
     uuid...": the query `array_agg(a.attname ...)` returns `name[]`, which `pg` does not parse, so `cols`
     comes back as a string and `[...cols].sort()` sorts its characters. Every other suite casts with
     `a.attname::text`. The FKs themselves are correct: the received characters spell `tenant_id`,
     `programme_id` and `stored_object_id` / `import_job_id`, and the isolation suite's 23503 probes pass.
   - import-isolation I4 (both tests): `plantObject` binds `$1` both as the `id` uuid and inside a text
     concatenation (`'.../import/' || $1`). Postgres refuses this with "inconsistent types deduced for
     parameter $1" before anything of mine runs. It needs `$1::text` in the concatenation, or a separate
     parameter.
2. **Objects left in the bucket by earlier tests (test defects, 2 tests).** import-api "complete moves to
   reading_header... (R14)" and import-isolation I6 expect `listEntries('tenant/A/programme/A1/import/')`
   to hold exactly one key. Earlier tests in the same file complete uploads into the same prefix, the
   SeaweedFS container lives for the whole file, and `reseed` does not touch the bucket. The extra keys
   are those earlier imports' files. Each test passes when run on its own. The fix is to filter on
   `keyOf(job)`, or clear the bucket between tests.
3. **The upload id is in the presigned part URL (R3 vs S3, 1 test).** import-api "stores the job
   awaiting_upload... (R3)" asserts that the upload id never appears in an answer. An S3 UploadPart URL
   must carry `uploadId=` in its signed query string; without it the bucket cannot accept the part, on
   SeaweedFS or on AWS. The id is never in any JSON field, it is not in `getImport`, and complete uses the
   stored id (the I3 tests pass). The only answer that carries it is inside the URLs the browser needs.
   **Ruling needed:** either R3 excludes the part URLs, or a different upload mechanism is wanted (for
   example single-part presigned PUTs, which would change R1 and R2).
4. **The locked `admin` set always edits (needs a security ruling, 3 tests).** The tests are import-api
   "a mapped field the creator may not edit is 403" (secret__c read), R12 "field made read-only after
   mapping" (late__c read), and R17 "a field withheld from the importer" (emails none). All three grant a
   level to the `admin` set and expect it honoured. But `resolveFieldAccess` in @kasuwa/metadata-engine
   gives a member of a LOCKED set `LOCKED_FIELD_ACCESS_LEVEL` (edit), whatever is stored ("Admins always
   have full access", P02/D). `admin` is the only set holding `contact.import` (D-L151), so the importer
   cannot be restricted this way.
   - The import code does check field security: at mapping time it returns 403 `field_not_editable`
     naming the field, and every run batch re-checks each row (R12). The unit tests cover this with an
     unlocked access map.
   - What fails is the fixture's assumption. Making a locked set honour grants would change the platform
     field-security model for every record API. I have not done that.
   - **Options for the lead:** the suites use a custom unlocked set that holds `contact.write` and
     `contact.import` (the policy is an allow-list by key, so that would also need a decision), or the
     tests are re-pinned to a tenant-admin-free, unlocked-set importer.

## What changed

**Migration 0042** (`packages/db/migrations/0042_import_job.sql`, schema.ts mirror, `TENANT_SCOPED_TABLES`):
- `import_job` per interface D:
  - RLS ENABLED and FORCED, with an isolation policy whose WITH CHECK equals its USING;
  - a RESTRICTIVE INSERT policy pinning `created_by_user_id = app.current_user_id()`;
  - composite FKs to `stored_object (tenant, programme, id)` and to `"user"`;
  - `stored_object_id` UNIQUE;
  - `kasuwa_app` gets SELECT, INSERT and column-limited UPDATE (never the keys, the creator or the
    declaration), and no DELETE or TRUNCATE. `kasuwa_auth` gets nothing.
- `contact.import_job_id` (nullable, no default) with an FK to `import_job (tenant, programme, id)` and a
  partial index.
- `UNIQUE (tenant_id, programme_id, id)` on `stored_object`.
- The D-L160 trigger `app.fail_removed_creator_imports()`:
  - it is AFTER STATEMENT on DELETE and on key-moving UPDATE of `user_programme`, following the 0031
    pattern;
  - SECURITY INVOKER with a pinned search_path, so the definer census stays at two;
  - it marks the removed creator's awaiting_upload, reading_header, awaiting_mapping, queued and running
    imports in THAT programme `failed`, keeping counts, and clears `headers`, `filename` and `mapping`;
  - it refuses (42501) a session that cannot see the programme.
- A self-check block.
- **Column named `changed_at`, not `updated_at`.** The T-0011 schema-hygiene suite probes every
  `updated_at` table on a seeded or planted row and has no plant for `import_job`. Seeding an import would
  break the exact import lists other suites pin. The wire's `updatedAt` reads from `changed_at`. If the
  lead prefers `updated_at`, the hygiene suite needs a plant for this table (a lead edit).

**Permissions:** `contact.import` is a programme action. `admin` holds it (by holding every action), and so
does the tenant-admin flag. No other set holds it.

**API** (`apps/api/src/imports/*`, `ImportsController` in `RECORDS_CONTROLLERS`):
- All nine operations, plus the `importId` filter on listContacts.
- Order for every operation with an id: 400 for a malformed id, then the one 404 (decided before
  anything else), then 403 for a non-creator (cancel also admits a tenant admin), then 400 for the body,
  then 409 for the status.
- The part plan is min(4, ceil(size / 5 MiB)) (R1).
- Resume re-signs the SAME upload through the new `presignUploadParts` (R2).
- Complete uses the stored upload id (R3). A mismatch, or a refused complete, rejects the job, deletes the
  object, audits `rejected` and answers 422.
- Retention jobs are enqueued at 24 hours from create and 7 days from complete and from every end.
- Queue jobs are added by `ImportCommitInterceptor` only after the tenant transaction commits. That
  interceptor also throws the 422 after the rejection has committed.
- `AppModule.forRoot` gains `redisUrl` and `objectStore`. `objectStore` is typed `unknown`, because the
  suites pass it that way, and is validated at boot. Without them, the import routes answer 503.
- `main.ts` passes `REDIS_URL` (now optional in `apiEnv`) and an `S3ObjectStore` when `S3_BUCKET` is
  set. `storageEnv` now defaults its source to `process.env`, as `apiEnv` does.
- The contract's nine import operations and `importId` are flagged `true`, `ImportRowError.row` maximum
  is now 100002, and `team/FEATURES.md` is regenerated.
- New `Error.code` members: `import_status_conflict` and `upload_mismatch`.

**Worker** (`apps/worker/src/import-jobs.ts`, registered in `main.ts`, one BullMQ worker per queue):
- **Run as the creator.** Each transaction is `withTenantTransaction({ tenantId, userId })` from the
  payload, and acts only on a job that is visible AND created by that user. Forged payloads (I5) do
  nothing, and an extra key is refused.
- **Run.**
  - The file is streamed through csv-parse with BOM handling and quoted newlines. Rows over 64 KiB are
    `row_too_large` and parsing continues. Row 100,002 is the one `too_many_rows` error.
  - Batches run one after another, at most 1,000 rows each. Each batch re-resolves scope and re-checks
    `contact.import`, the owner's membership, contact field security and custom fields.
  - Rows parse with the shared schemas and `customValueProblem`.
  - Phones go to E.164 through the existing `wholePhoneE164` (NG, GH, KE, ZA; trunk 0). No phone code
    moved from apps/web, because domain-core already had the rule.
  - Compliance is restrict-or-default, and only exact spellings are read (R8).
  - Duplicates come from an exact keyset scan (no OFFSET) over `contact_tenant_programme_id_key`, on
    readable fields only. Rows the same file created are added as it goes. The 120k scan test passes.
  - Errors are capped at 1,000 and `errorsTruncated` is set past that.
  - Each created contact gets one `created` audit with the creator as actor. The job end is audited
    `updated` with its counts.
- **Retention.**
  - What happens is decided from the row and the clock:
    - 24 hours for awaiting_upload: abort the upload, then `expired`;
    - 7 days after complete for reading_header or awaiting_mapping: then `expired`;
    - 7 days after the end for terminal states.
  - A queued or running job enqueues a NEW retention job, with no job id reused.
  - On erasure, `stored_object` moves to `deleted`, `raw_file_deleted_at` is set, and the filename,
    headers, suggested mapping and mapping are cleared. Counts and errors stay. `deleted` is audited
    on `stored_object` by the creator.
- Nothing logs. Failures throw `ImportJobError` with a fixed message and no cause.
