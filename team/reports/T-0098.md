## What was hard
1. **The ADR's NOT EXISTS, taken literally, fails the suite.** "Exclude any row with an earlier unpublished event for the
   same aggregate" in the claim means one event per aggregate per batch, but section 7's "released" test expects both
   events of one aggregate from a single call, in order. So the claim takes rows in seq order with SKIP LOCKED, and a
   second, non-locking query sets aside a claimed row only when an earlier pending row of its aggregate was **not**
   claimed by this batch (another relay holds it). Earlier rows that were claimed go first in the same `addBulk`.
2. **Backoff and head-of-line blocking.** Without a publish backoff, a ten-second Redis outage at one poll per second
   kills every pending event. I added `2^attempts` seconds, capped at an hour (about 17 minutes to the tenth failure).
   That created a liveness trap: rows behind a backed-off row would be claimed and held every batch, starving other
   aggregates. So the claim also skips rows behind an earlier event of their aggregate that is inside its backoff, and
   the tick loops only while a whole batch was settled. An integration test pins "a poison row blocks only its own
   aggregate".
3. **Bad rows are attempts, not instant death.** R3 accepts either. Instant death would lose every event of a type a
   newly deployed API produces before the worker knows it (rolling deploy skew). Ten attempts with backoff give that
   window about 17 minutes. A rejected row holds back the later events of its own aggregate only.
4. **Where the event schema lives.** `@kasuwa/db` must parse it and cannot import a domain, so it is defined in the db
   registry and re-exported by domain-core. ADR-0018 point 9 reads as if the domain defines it; the suite's I5 makes the
   two the same object either way. Each new event type is therefore a `@kasuwa/db` change.

## Open questions
1. **No FK on `actor_user_id`.** The forgery suite plants, as the migrator, a row naming another tenant's actor and pins
   that the consumer drops it; a composite `(tenant_id, actor_user_id)` FK would make that row unwritable. An FK would
   also block a user delete (D-L61, still open). The actor is bound instead by F-R3 at insert and re-resolved by the
   consumer. Accept, or ask for a different shape?
2. **A tightening beyond D-L156:** the relay's UPDATE WITH CHECK also requires `last_attempt_at IS NULL OR
   last_attempt_at <= now()`. My backoff skips a row until `last_attempt_at` plus a delay has passed, so SQL running as
   the relay could future-date it and park an event indefinitely. It cannot be `= now()` (a later mark-published keeps
   the earlier failure's time). Pinned by an integration test. Accept or drop.
3. `attempts` is still free for the relay to set (0 to 32,767). Setting it to 9 makes the next failure fatal: "loses an
   event, leaks nothing", inside ADR-0018's stated blast radius. I left it.
4. The ADR says the relay "needs no EXECUTE on the app accessors". It also needs none on `pg_catalog` functions beyond
   PUBLIC's default (`pg_try_advisory_xact_lock`, `now()`, `make_interval`), which every role has. Noting it in case the
   lead wants a stricter catalogue rule later.

## Risks I am aware of
- **Cross-tenant reach, by design.** SQL running as `kasuwa_relay` reads identifiers of undispatched and expired events in
  every tenant and can mark them published or dead. It cannot read any other table (42501 on every TENANT_SCOPED table,
  `auth_rate_limit`, the accessors and both definers, all pinned), cannot insert, cannot change identity columns, and
  cannot back-date into retention.
- **Redis holds payloads.** The envelope includes the strict payload (identifiers only, D-P29), so Redis holds contact
  and staff ids for up to seven days of completed jobs and indefinitely in the failed set. That is ADR-0018's envelope;
  noting it for NDPA review.
- **The app can still insert a row the relay will reject** (raw SQL, any payload object up to 8 KiB). R3 stops it at the
  relay; the row then sits for up to ten attempts and 30 days as dead. It never reaches Redis.
- **Shared harness change.** Every integration and isolation run now starts a Redis container (a few MB) because
  global-setup must provide `redisUrl` (I9).
