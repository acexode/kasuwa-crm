## Open questions

Places the designs imply a capability **no PRD module owns**. These are
decisions for @acexode, not gaps for me to fill.

1. **Field-level security: tenant-wide or per programme?** The matrix has two
   axes, field and permission set, and no programme axis. Either a grant is
   tenant-wide — and a BPO cannot honour two clients with different contractual
   rules about the same Contact field — or the screen is missing an axis and one
   admin's save silently overwrites another programme's settings. **I did not
   pick.** There is no `programmeId` in `FieldSecurityWrite` and
   `PUT /field-security/matrix` returns `501` until this is answered. This is
   the single most consequential open item in the file.
2. **Permission sets have no model.** Six columns are named (Agent, Team lead,
   QA analyst, Programme manager, Client portal, Admin) with user counts. M2
   lists "profiles, permission sets" as P0; nothing designs them, and the
   admin-console menu has a "Permission sets" page that is not in this round.
3. **The audit log's write side has no owner.** I specified the read side, as
   instructed, and marked it `false`. Whoever builds the store owns the write
   side in the same task: a reader with no writer is a screen that says "no
   events match" forever, and a row the subject of the audit can write is not an
   audit row. M2 also requires hash-chaining and WORM export, neither specified.
4. **Setup health score.** No module defines which checks exist or what each is
   worth. I made `checkId` and `points` server-side so the rules live in one
   place, but the rules themselves are unowned.
5. **Admin home alerts aggregate six modules** (M8 templates and sender IDs, M2
   MFA policy, M21 DSR, M23 seats). No module owns the aggregation or the
   per-user dismissal.
6. **Usage meters are M23 (billing and subscription), which is unassigned.**
   Seats, WhatsApp conversation spend, storage and AI credits, including a
   money figure on the admin home.
7. **SLA policy has no owner.** SLAs are per-programme configuration (PRD 2.10)
   but M12 owns ticketing SLAs, M8 owns inbox response targets and M18 owns the
   client-facing breach report. Someone must own the model and the clock.
8. **Retention is M21, unassigned, and D-T4 is BLOCKED** — if the telephony
   platform already does recording retention, the call-recording period on this
   screen may not be the one actually enforced. That is a compliance screen
   promising something we may not control.
9. **Programme lifecycle has no column.** `programme` has no status field, so
   Active/Paused/Draft/Archived, plus 30-day restore, is a migration and a
   successor task.
10. **Skill cover needs WFM** (`packages/wfm-adapter` is a placeholder, D-W1
    BLOCKED) and the agent presence column needs telephony (D-T5 BLOCKED). Both
    are nullable in the contract for that reason.
11. **Contract card** (reference, start, renewal, billing basis) — no module.

## Risks I am aware of

- **The audit log is the personal-data risk in this file and I want it read
  carefully.** The design's own data has an audit row whose record is
  `fatima.bello@sabicc.example`. I specified `objectLabel` as a display name and
  never an email address, `AuditActor` as name and role only, `sourceIp` as
  nullable and permission-gated (null must not be distinguishable from "none
  recorded"), `AuditChange` with a `redacted` flag so that the *fact* a
  sensitive field changed is auditable while its content is not, and audit
  exports that return no download URL and default `includeIpAddresses` to false.
  If any of those is relaxed during implementation, personal data leaves the
  system through a file an admin emails to themselves.
- **404-not-403 is written into the contract, including for `exportId`.** A BPO
  running two competitors on one workspace makes a `403` a working enumeration
  oracle. The `403 not_permitted` response exists but is documented narrowly:
  "if you are unsure which applies, it is `404`."
- **Unique-constraint leakage.** `duplicate_name` and `duplicate_code` carry a
  field path and a reason code, never the conflicting row and never a database
  message. This is the accidental-leak channel the brief warned about and it is
  called out in the envelope's `details` description.
- I did not touch `tests/acceptance/tenancy/`, `packages/db` or `packages/permissions`.
