## What changed

- **New module `apps/api/src/deals/`**, with its own repository, so it does not collide with T-0107:
  - `deals.controller.ts`: `PipelineDealsController` (`listDeals`, `createDeal`) and `DealsController` (`getDeal`, `updateDeal`, `moveDeal`). Operation annotations are in doc comments, as elsewhere (there is no `@nestjs/swagger`).
  - `deals.service.ts`: the decisions, in the published order for each operation (404, 403, 400, 409, 422; R20 for moves).
  - `deal.repository.ts`: SQL. Every statement repeats `tenant_id` and the session's programmes as well as relying on RLS. Ids are minted here. `amount_minor` is bound as text and cast `::text::bigint`, and read back as `::text`. Moves set `stage_entered_at = now()` and set `closed_at` from the target stage's kind. The version-guarded `UPDATE` gives R14 its single winner. Check ticks are `INSERT … ON CONFLICT DO NOTHING` as the session user, which gives R6. The `DealCursor` lookup (R22) uses the page's own WHERE.
  - `deal-wire.ts`: the closed `Deal`. Withheld fields and their summaries are omitted. Weighted amounts are half-even in BigInt and converted to a string before `JSON.stringify`. `rotting` counts whole days.
  - `deal-fields.ts`: deal field security over `loadFieldAccess(tx, 'deal')`. `name` is never withheld on reads (R13), but it is still judged for edit on writes.
  - `deal-audit.ts`: changes are recorded by name only. The exceptions are a move's `stageId` (before and after) and a reassignment's `ownerUserId` ids. The label is the deal id.
  - `deals.schemas.ts`: Zod schemas with closed bodies. `amountMinor` must match `^(0|[1-9][0-9]{0,17})$` as a string. A well-formed but unknown currency is `unknown_currency`; any other bad value is `invalid_string`.
  - `deals.unit.test.ts`: 12 unit tests.
- **`packages/permissions/src/policy.ts`**:
  - New actions `deal.write` (agent, team_lead, programme_manager, admin, flag), `deal.write_any` and `deal.reassign` (team_lead, programme_manager, admin, flag).
  - `canReadDeals` covers every staff set and the flag. It excludes client_portal, a missing set and unknown keys, and is answered 404 (R1).
  - `canWriteDeal` gives own-open-only to `deal.write` alone, treats own as none when `ownerUserId` is withheld, and requires write-any to touch a won or lost deal (R17).
  - `dealBodyAssignsOther` covers null or another uuid. It treats a malformed id as a 400, not `owner_not_self`, because the suite's closed-body test sends `ownerUserId: 'not-a-uuid'` as an agent and expects 400.
  - Exports go through `index.ts`, and `policy.test.ts` is updated with deal cases.
- **Shared, small and additive:**
  - `app.module.ts`: the two controllers are added to `RECORDS_CONTROLLERS`, so they get no-store and the telemetry vocabulary. `no-store.middleware.test.ts` is updated to match.
  - `audit-writer.ts`: adds object type `deal`.
  - `audit-field-security.ts`: `deal` is field-secured. Its only value field is `ownerUserId`, judged by `owner_user_id`. See Open questions about `stageId`.
  - `admin-errors.ts`: adds the codes `transition_not_allowed` and `requirements_unmet` (already in the admin `Error` enum), and the 422 reason phrase.
  - `common/json-body-limit.ts` (+test): **a global change; please review it.** A JSON body-parser parse failure, meaning malformed JSON or a strict-mode top-level `"x"`, `null` or `42`, used to reach the client as Nest's `BadRequestException(err.message)`. That body had no `code` and quoted the request body. It is now the fixed envelope `400 validation_failed` with details `[{path: '', code: 'invalid_json'}]`, `no-store`. It is installed as an Express error middleware right after the JSON parser. R15's raw-body cases needed it. Every other error passes through untouched.
- **`docs/api/records.openapi.yaml`**: exactly the five deal operations are flipped to `x-kasuwa-implemented: true`. Nothing else changed.
- No new dependency, table, migration or SECURITY DEFINER function.

## Acceptance tests I believe are wrong (not edited)

1. **`createDeal … qa_analyst is 403 … one 404 (R1)`, l.1512, `nothing audited`.**
   - The test itself runs `unassign(USER_A_NO_PROGRAMME, PROGRAMME_A1)` after taking `quiet`.
   - Migration 0031/0033's removal trigger writes a system `programme` event for every membership removal (`removedMember`, `unassignedContacts: "0"`).
   - No implementation can stop that. The fix is to take `quiet` after the unassign, or to filter on `object_type = 'deal'`.
2. **`money … 18 nines round-trips … (R19)`, l.1799–1809.**
   - The test moves S1→S2 (Proposal) without the Proposal check `RC_PROP`, ignores the answer, and plants `RC_PROP` only afterwards.
   - Requirements are the target stage's entry requirements (contract: "Requirements (D-P20) are entry requirements of a stage", moveDeal "are the target stage's"). So S1→S2 is 422, the deal stays in S1, and the final S1→S3 is 409 `transition_not_allowed`.
   - The fix is to plant `RC_PROP` before the S1→S2 move.
3. **`moveDeal … checks are attributed to the SESSION user … (R6)`, l.2499 ("back").**
   - The deal is planted in S2 without `RC_PROP` and moved to S3. The test then expects S3→S2 ("Back to Proposal") to be 200.
   - Proposal's entry requirement `RC_PROP` was never ticked, so the contract makes it 422 `requirements_unmet` (that is the body returned).
   - The fix is to plant `RC_PROP`, or to tick it in the "back" move body. Alternatively, a ruling could say backward moves are not gated. I did not invent that rule, because the contract says otherwise.

## What was hard

- **The rule order around the owner.**
  - R21 needs `field_not_editable` to win over `owner_not_self` when both apply (an agent with a withheld owner sending `null` or another id). So field security is judged before the owner rule.
  - A malformed owner id from an agent has to be a 400 (the closed-body test), so `dealBodyAssignsOther` ignores values that are not uuids.
- **Malformed and non-object JSON bodies** never reached the route at all. Fixing that meant the global error-middleware change described above.
- **The required-field 403 has two cases.** A withheld field (`none`) refuses the move whatever its value; a `read`-only field refuses it only when unmet. Both come before the 409s (R20) and after every 400.

## What I left out, and why

- **The pipeline reads (listPipelines, getPipeline, getPipelineBoard).** They belong to T-0107.
- **Unassigning deals when an owner leaves the programme**, as 0031 does for contacts. A former owner is shown as an id with `displayName: null`, as the contract says. Making 0031 sweep deals would need a migration. That is a decision, not part of this task.
- **The membership advisory lock for the default owner (the caller).** `programmeMemberExists`, and with it the lock, runs for every owner named in a body. It does not run for the implicit caller-as-owner on create. The caller is a member by construction of the session, and no deal sweeper exists to race with.

## Open questions

- **Reading a deal audit event's `stageId` values.** The audit reader redacts them, because they are not on the deal value allow-list. They are stored unredacted, as R9 requires. Should the reader show stage ids, which are configuration? That needs a small decision about whether a stage id should count as a value field.
- **Should backward moves be gated by the target stage's requirements?** I followed the contract: yes, always. See suite defect 3.
- **No-op updates.** An update whose values equal the stored ones still bumps `version` and writes one event, with empty `changes` (allowed: "the builder's").

- **Tenancy.** Every query is scoped by the session's tenant and programmes, explicitly and through RLS.
