# T-0180 — Portal invitations

## Summary

Hardened admin portal invitations (rate limit, `portal_invite` rows, fragment-based
accept links, paginated list) and implemented portal `POST /api/v1/portal/invitations/accept`
on `kasuwa_auth` under RLS (no `app.resolve_portal_invite`).

## Files changed

- `packages/db/migrations/0064_portal_invite_auth.sql` — `kasuwa_auth` grants/policies for invite accept
- `packages/domain/core/src/portal-invite/*` — list/rate-limit helpers
- `packages/db/src/fixtures.ts`, `packages/db/src/seed.ts` — seeded accept token (`a`×48)
- `apps/api/src/admin/portal-users/*` — list route, rate limit, dual-write to `portal_invite`, email body
- `apps/api/src/admin/common/admin-errors.ts` — `rate_limited`
- `apps/api/src/auth/portal/*` — accept route and service
- OpenAPI already marks list/accept `x-kasuwa-implemented: true`

## Token storage

- Plaintext: outbound email only (`#token=…` primary link; `&token=` legacy line for T-0030 seam).
- Database: SHA-256 **hex** in `portal_invite.token_hash`; `portal_user.invite_token_hash` remains **bytea** for T-0030.

## Residual gaps vs acceptance

- Acceptance suite not run here (no Docker/Testcontainers in this environment).
- `portal_invite` has no `access` field; accept does not propagate `portal_user.access` to membership.
- HTTP list uses `{ data, nextCursor }` per acceptance (OpenAPI still documents `items`/`page`).
