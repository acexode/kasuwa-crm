## The one thing I could not do

`tests/acceptance/metadata/metadata-isolation.pending.acceptance.test.ts`
defines its fixture helper *inline*:

```ts
/** T-0002 implements this; it is part of the task, not of the contract. */
const seedObjectDef = async (_tenantId: string, _objectId: string, _apiName: string) => {
  throw new Error('T-0002: implement seedObjectDef() for this suite.');
};
```

The task file and my instructions both say implementing it is mine. My
instructions also say, in the same breath, **do not edit anything under
`tests/acceptance/`** — and `.claude/hooks/protect-paths.mjs` blocks it. Those
two instructions cannot both be satisfied, because the helper is a local
constant in the protected file. I chose not to route around the hook.

So I implemented the helper where a builder legitimately can — exported from
`@kasuwa/testing` — and left the delegation for the lead, who is renaming the
file at PR time anyway. The replacement is exactly this:

```ts
import { readTableSecurity, seedObjectDef as seedObjectDefFixture, withForcedScope } from '@kasuwa/testing';

// ...
const seedObjectDef = async (tenantId: string, objectId: string, apiName: string) =>
  seedObjectDefFixture(pool, tenantId, objectId, apiName);
```

`seedObjectDef(pool, tenantId, objectId, apiName)` is idempotent, goes through
`withTenantTransaction` and the real repository (not a privileged connection,
so the fixture exercises the same RLS path the application does), and picks the
tenant's first seeded user as the acting identity. It is covered end to end by
`packages/testing/src/metadata-factories.integration.test.ts`, which mirrors the
acceptance assertions — including the "not programme-scoped" one — so the
delegation above is a formality rather than a leap of faith.

## What was hard

1. **The `seedObjectDef` contradiction**, covered above. It is a task-design
   problem, not a code problem: a helper that a builder must implement cannot
   live inside a file only the lead may edit. Suggested fix for future task
   files — have the pending suite import the fixture from `@kasuwa/testing` and
   let the builder implement it there. Then the acceptance file never needs a
   builder's hand on it.
2. **Confirming the composite FK is what stops a cross-tenant parent.**
   Referential integrity checks bypass row security in Postgres, so the RLS
   policy alone would *not* have caught it — the parent row is visible to the RI
   check regardless of session. `tenant_id` being part of the referenced key is
   the entire mechanism. Said so in the migration comment.
3. `pnpm install` was needed in this worktree before anything ran (no
   `node_modules`), and adding two workspace dependencies needed a second run.

## Open questions

Seven, written into `docs/prd/M15-customisation-and-app-builder.md` as items
7–13 rather than repeated here. The two I would raise first:

- **Is `api_name` immutable after creation?** (#9) The schema currently permits
  an update. A rename breaks every formula, layout and integration referencing
  it. Immutability is the conservative default and should be decided, not
  inherited by accident.
- **The `nin` field type** (#13). The PRD lists NIN as a P0 field type; the
  security guardrails forbid NIN in logs or fixtures and M3 stores a token. I
  allowed `nin` in the type constraint because the PRD is explicit, but nothing
  yet forces a `nin` field to store a token rather than a number. That must be
  settled before anything writes one.

Nothing here contradicts an open decision in `team/DECISIONS.md`. D-L06 is
answered (explicit programme enumeration, no wildcard) and this work relies on
it only negatively: the metadata policies contain no programme predicate at all.
