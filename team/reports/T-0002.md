The task file and my instructions both say implementing it is mine. My

// ...

  seedObjectDefFixture(pool, tenantId, objectId, apiName);

`withTenantTransaction` and the real repository (not a privileged connection,

## What was hard

1. **The `seedObjectDef` contradiction**, covered above. It is a task-design
   problem, not a code problem: a helper that a builder must implement cannot
   live inside a file only the lead may edit. Suggested fix for future task
   files — have the pending suite import the fixture from `@kasuwa/testing` and
   let the builder implement it there. Then the acceptance file never needs a
   builder's hand on it.
2. **Confirming the composite FK is what stops a cross-tenant parent.**
   Referential integrity checks bypass row security in Postgres, so the RLS
   policy alone would *not* have caught it — the parent row is visible to the RI
   check regardless of session. `tenant_id` being part of the referenced key is
   the entire mechanism. Said so in the migration comment.
3. `pnpm install` was needed in this worktree before anything ran (no
   `node_modules`), and adding two workspace dependencies needed a second run.

## Open questions

Seven, written into `docs/prd/M15-customisation-and-app-builder.md` as items
7–13 rather than repeated here. The two I would raise first:

- **Is `api_name` immutable after creation?** (#9) The schema currently permits
  an update. A rename breaks every formula, layout and integration referencing
  it. Immutability is the conservative default and should be decided, not
  inherited by accident.
- **The `nin` field type** (#13). The PRD lists NIN as a P0 field type; the
  security guardrails forbid NIN in logs or fixtures and M3 stores a token. I
  allowed `nin` in the type constraint because the PRD is explicit, but nothing
  yet forces a `nin` field to store a token rather than a number. That must be
  settled before anything writes one.

Nothing here contradicts an open decision in `team/DECISIONS.md`. D-L06 is
answered (explicit programme enumeration, no wildcard) and this work relies on
it only negatively: the metadata policies contain no programme predicate at all.

## `migration-reviewer` pass (2026-09-27)

**Verdict: pass-with-findings. No blocking defect in the SQL.**

Run independently, against real Postgres via Testcontainers rather than by eye:
`pnpm test:integration` 13/13, `pnpm test:isolation` 95/95.

### The deliberate omission of `programme_id` — checked, and safe

Asked to weigh it rather than flag it, and it held up on three counts: both
policies are a bare tenant predicate with no programme term, matching the
precedent `"user"` and `user_programme` already set; nothing else in the change
assumes programme scoping; and the cross-tenant reference is **impossible
rather than unlikely**, because `FOREIGN KEY (tenant_id, object_id) REFERENCES
object_def (tenant_id, id)` puts the tenant discriminator inside the key.

That last point is the one worth remembering: **referential-integrity checks run
with RLS bypassed**, so a plain `object_id` FK would have been checkable across
tenants. The composite key is not belt-and-braces, it is the mechanism.

### The builder's six self-check claims — all verified true

Sorting, single transaction, no `ALTER` on populated tables, no `CONCURRENTLY`
needed, `timestamptz` throughout, grants via `bootstrap.sql`. The reviewer also
noted `CONCURRENTLY` would have been *wrong* here, since it cannot run inside
the runner's per-file transaction.

### MAJOR — already closed, and worth recording why it was raised

claimed the exception is enforced by

Recording it rather than deleting it, because the general form is worth keeping

false**, and this one would have shipped citing a test that did not run.

The reviewer also narrowed the exposure honestly rather than overstating it —
`rls-enforcement.acceptance.test.ts` was never pending and already covered
`ENABLE`, `FORCE`, policy presence and `TENANT_SCOPED_TABLES` set-equality for
both tables. What was uncovered was the programme-visibility assertion and the
composite-FK rejection.

### MINOR — both inherited from `0001`, both now **T-0011**

Redundant tenant-prefix indexes, and `updated_at` that nothing maintains.
Neither is a defect in this migration; both are patterns `0001` set and every
future table would copy. Raised as a separate task on the reviewer's own
framing — "a repo-wide habit worth correcting once rather than a defect in this
commit".

The `updated_at` one is the one that bites: the column is silently wrong the
moment an update endpoint lands, and a stale timestamp that *looks* maintained
gets believed by cache invalidation and sync cursors.

### Rollback

Free today — both tables are empty and no deployed code reads them, so a
forward `0003` dropping them loses nothing. **That window closes at the first
production write**, after which a drop destroys tenant configuration
irrecoverably. Noted because it will not be true of the next migration here.
