# T-0019 — keyset pagination drops rows below millisecond resolution

**Agent:** 3 — Core CRM & Pipeline
**Branch:** `agent3/T-0019-cursor-precision` (not pushed, no PR opened)

## What changed

`packages/domain/core/src/cursor.ts`

- The cursor's timestamp is now a **string, end to end**. Postgres renders it,
  it travels in the payload verbatim, and it goes back into the query as a
  bound `timestamptz` parameter. No JavaScript type on that path can truncate
  it.
- New precision-preserving pair `encodeKeysetCursor` / `decodeKeysetCursor`
  over `KeysetCursor { createdAt: string; id: string }`. Repositories use these.
- `encodeCursor` / `decodeCursor` (the `Date`-valued pair) are kept, documented
  as lossy by construction, and delegate to the same encode/validate path.
- Validation moved off `z.string().datetime({ offset: true })` to an explicit
  regex plus a `Date.parse` refinement. Reason: zod's `precision` option pins
  the fractional part to an *exact* length, and what is needed is "0 to 6
  digits" so that cursors issued before this change still decode. The regex is
  no weaker than the old check — it still demands an explicit offset — and the
  refinement rejects shapes the calendar does not allow (month 13).
- The payload keys are still exactly `c` and `i`. **No tenant, no programme, no
  user, no signature.** The cursor still encodes position, never authority.

`packages/domain/core/src/contact/contact.repository.ts`

- `listContacts` selects one extra column,
  `to_char(created_at AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.US"Z"') AS created_at_cursor`,
  and builds the next cursor from it. `to_char` rather than `::text` so the
  format does not depend on the session's `DateStyle`. `created_at` in the
  response body is unchanged — still a `Date`, still millisecond, which is
  fine because nothing compares against it.

Tests I added (mine, not the acceptance suite):

- `packages/domain/core/src/cursor.test.ts` — seven new cases, **every
  timestamp sub-millisecond on purpose**, including one that asserts the trap
  directly: a microsecond instant passed through a `Date` names an earlier
  position than the same instant passed as a string.
- `packages/domain/core/src/contact/contact.repository.integration.test.ts` —
  new file. Inserts four contacts at `.000900`, `.000500`, `.000100` and
  `.999999` within one second, pages to exhaustion at limits 1, 2, 3 and 100,
  and compares against a direct `count(*)` in the same scope rather than a
  hard-coded number. Verified it fails without the fix: **5 of 7 returned**,
  and passes with it.
- `packages/domain/core/tsconfig.json` gains the root
  `types/vitest-provided.d.ts` in `include`, which is how the other packages
  type `inject('databaseUrl')`. No new dependency: the pool is typed as
  `ReturnType<typeof createPool>` so this package still does not depend on `pg`.

## Why a string and not microseconds-as-a-number

A `bigint` epoch-microsecond count also survives the round trip, but it has to
be converted back into a `timestamptz` in SQL, and every conversion is another
place to lose a digit. The string is the value Postgres itself printed and the
value Postgres itself will parse; the middle of the system never interprets it.
It is also readable in a decoded cursor during an incident, and it keeps the
payload shape (`c` as an ISO-8601 string) unchanged, so a cursor from before
this change is still a valid cursor.

Not a library: `to_char` with `US` and a regex are the whole requirement.

## What happens to a cursor issued before the change

**It is accepted, not rejected.** Reasoning:

- Such a cursor carries a millisecond timestamp and points where it always
  pointed. Honouring it is exactly as lossy as yesterday — at most one page
  boundary — and it is lossy once, because the *next* cursor it yields is
  precise.
- Rejecting it means a `400` on every in-flight paging session at deploy, and
  the client cannot distinguish that from a tampered cursor. Trading a bounded,
  one-boundary loss that already happened for a user-visible error on rollout
  is a bad trade.
- Rejecting would also have turned two lead-owned acceptance tests red —
  `cursor-tampering`'s "ignores tenant and programme fields smuggled into a
  cursor" and "cannot reach another tenant's rows by pointing a cursor at them"
  both hand-build millisecond cursors and expect `200`. I would not have edited
  them; I mention it because it independently confirms that millisecond
  cursors are part of the contract, not just legacy.

There is no version field, deliberately: `cursor.test.ts` and the adversarial
property test both assert the payload has exactly the keys `c` and `i`, and the
format is self-describing by its fractional digits anyway.

## Left out / open

- Only `listContacts` paginates today, so only it was fixed. Any future keyset
  repository must select its own `*_cursor` column and use
  `encodeKeysetCursor`; the header comment in `cursor.ts` says so. A lint rule
  cannot see the difference, so this is a review-time thing.
- `encodeCursor`/`decodeCursor` remain exported and lossy. They are a trap for
  the next person even with the comment. I kept them because the adversarial
  property test (`decodeCursor yields only positions it could have produced`)
  exercises them with `Date` positions. If the lead would rather they go, that
  is a one-line deletion here and an edit in a lead-owned file.
- No ADR: this is a bug fix inside an existing module, no contract changed. The
  cursor remains an opaque base64url string at the HTTP boundary, so the
  OpenAPI annotation is unchanged.
- No new dependency.
