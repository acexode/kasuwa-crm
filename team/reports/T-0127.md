## Byte budgets

**The font, measured:** `material-symbols-rounded-subset.woff2` grows from **14,240 to 30,416 bytes (+16,176)**. The
WOFF2 is already compressed, so the transfer cost is about the same, and it lands on every page that draws an icon,
which is every shell page. The other six font files came back byte-identical. The Noto Sans latin-ext, Noto Sans
Arabic and JetBrains Mono latin-ext `unicode-range` lines changed upstream at Google and are committed as served.
U+20A6 and U+20B5 are still carved out of latin-ext (D-L44).

Where the bytes go, measured against Google's subsetter with the same names:

| Subset | Bytes |
|---|---|
| Before: 121 glyphs, FILL 0 | 14,240 |
| 198 glyphs, FILL 0 (no FILL axis) | 21,820 |
| **198 glyphs, FILL 0..1 (shipped)** | **30,416** |
| All 280 glyphs the 15 exports draw, FILL 0..1 | ~41,800 |

**I re-pinned nothing.** The rule (D-L182, applied in D-L187 and D-L189) allows a re-pin only for a *measured*,
required cause, with about 1 to 1.5% headroom, inside the suite's ceiling and the 5% rule. I was not allowed to run
e2e, so I have no page measurements. The cause is required (the task mandates the glyphs and the axis). The amount
is known: about +16.2 KB per icon-drawing page, plus a few hundred bytes of CSS. Projected from the current pins,
which run 1 to 1.5% above their last measurements:
- **Every page pin fails.** Their headroom is about 2 to 4 KB.
- **Ceilings at risk.** The contact record's 245,000 ceiling: the 239,000 pin is about 236 K measured, so about
  252 K after this change. The account record's 250,000 ceiling (D-L190): about 247 K → 263 K. The pipeline board's
  259,000, the P02 scripts tab's 270,000 (about 266 K → 282 K) and `/admin/field-security`'s 261,000 (about
  257 K → 273 K) are all still under PRD 2.13's 300,000.
- **Sign-in critical path (250,000):** affected only if an icon is requested before first paint. Measure it.

**A cheaper option, if the lead prefers it:** ship two faces.
- The main subset is static FILL 0: 21,820 bytes, +7,580.
- A second family carries FILL 0..1 for only the glyphs the design fills: the bell, `notification_important`,
  `gpp_maybe`, `lock` and the bottom-tab icons. That is 4,992 bytes for 14 glyphs, downloaded only on a page that
  draws a filled icon.
- It saves 8.6 KB on pages with no filled icon and about 3.6 KB on pages with one.
- The cost: a second list, and a second union whose missing names render as blank boxes. And the acceptance
  regex reads only `fetch-fonts.mjs`, so it would still pass.

I followed the task as written (one subset, FILL 0..1). Switching is about an hour.

## What was hard

1. **The icon face claimed the naira sign.** `fonts.test.ts` (D-L44) failed once the subset passed 20 KB. Google
   sends no `unicode-range` for an `icon_names` subset, so the face claimed every code point, ₦ and ₵ included. It
   only passed before because the font was 14 KB. The browser would never actually fetch the icon font for a ₦ in
   Noto Sans text, but loosening the test would have hidden the next real D-L44 breach. So the face now states what
   it covers:
   - the characters the names are spelled with;
   - plus the space, because CSS takes an element's line metrics from the first font covering U+0020.

   Rendered in Chromium, old font against new: the icon box is in the same place and the same size (top 128, height
   20). The ligatures, the FILL axis and the digit names (`battery_5_bar`, `signal_cellular_4_bar`) all render.
2. **The icon component ships in client bundles.** A value import from the `@kasuwa/ui` barrel would pull every
   colour plus the CSS and preset builders into them. So `icon.tsx` imports types only. `const ALIAS: typeof
   ICON_SIZE_ALIAS` still pins its mapping to the package's, value for value, at compile time. `Record<IconSize, …>`
   makes a new `ICON_SIZE` entry without a class a compile error.
3. **Finding every glyph.** The exports are bundles that unpack at runtime: the CSS isn't greppable, and frames only

## Open questions

1. **The design's own icons are faux-bold, and we now are not.** In the rendered exports, the Material Symbols face
   is weight 400 only (`document.fonts` reports `w=400`). Many icons sit inside 600 or 700 text and inherit that
   weight with synthesis on. That is 39 + 12 of 78 icon name and weight pairs in P04, and 34 + 11 + 3 of 88 in P05. So Chromium
   draws those export icons synthetic-bold. The task says `.k-icon` keeps weight 400, so ours will look slightly
   lighter than the export in those places, for example icons in buttons and chips. If parity reviewers flag it,
   the fix is a decision: allow synthesis, or fetch a wght range. It is not a component bug.
2. **Byte budgets:** re-pin the pins and raise the two ceilings (contact and account records) with the +16,176 B
   cause, or take the two-face option above first.
3. **The `ring-focus` name.** `focus` is a semantic colour, so `ring-focus` also generates Tailwind's ring-colour
   rule (`--tw-ring-color`) on the same class. It's harmless, since that rule sets no box-shadow, but anyone reading
   the compiled CSS may find it confusing. Renaming it (`focus-ring`) would avoid that; the task named it
   `ring-focus`, so I kept it.
