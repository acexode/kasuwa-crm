## What changed

### Timeline: `GET /api/v1/contacts/{id}/timeline`

**Route.** `ContactsController.timeline`, with `no-store`.

**Service.** `apps/api/src/contacts/contact-timeline.ts`. The order of checks:
1. Scope first: the contact must be reachable, or the one 404 body is returned.
2. Then the query (`limit` 1..100, never clamped).
3. Then the cursor.

Field security is computed per caller and handed to SQL as an allow-list of change fields.

**Repository.** `packages/domain/core/src/contact/contact-timeline.repository.ts`. One statement does all of this:
- `jsonb_array_elements(changes)` over the contact's `created`/`updated` audit events;
- `UNION ALL` the activities whose `contact_id` is the contact;
- the filter on visible fields;
- the order: `date_trunc('milliseconds', …) DESC, item_id COLLATE "C" DESC`;
- `LIMIT n+1`.

Withheld items therefore never reach the LIMIT (T5).

**Keyset and cursor.**
- The keyset is the millisecond the wire shows, plus the item id. Items that differ below the millisecond tie on the wire and are ordered by id, so the order checker and paging always agree.
- The cursor is `{ k: contactId, t: ms, i: itemId }`. A cursor issued for another contact is 400 `invalid_cursor`.

**Item ids.** `'ti_' || md5('change:' || event_id || ':' || field)`, or `md5('activity:' || id)` for an activity. An id depends only on its own event and field (T3), and is never the event id.

**Actors.** Read at request time from `"user"` by `(tenant_id, id)`. A former member, a tenant admin outside the programme and a disabled user are all named. `null` is used only for the system (`actor_user_id` NULL, or `created_by_user_id` NULL). An unresolvable actor throws rather than rendering `null`.

**Values (T6/T7).**
- Decoded only for D-L72's value fields, and only when the change has `redacted: false`.
- A legacy value-field item has no `before`, `after` or `redacted`.
- Redacted fields never carry a value, whatever the row holds.
- `consentState` becomes a `consent_changed` item, with values only when both values are ConsentState codes.

**Activity items.**
- They follow the activity object's field security in the contact's programme: `subject`, `body`, `dueAt` and `completedAt` are omitted when withheld.
- `type` is always sent.
- When `contact_id` is withheld, no activity item is shown at all. That is my choice; the suite leaves it to the builder.

### Contact audit values (T10, D-L72, D-L81)

`contact-audit.ts` has been rewritten.

- **Value fields** (status, source, language, channel, consent, whatsappOptIn, state, lga, tags):
  - recorded with `before` and `after` when the value moved;
  - booleans as `'true'`/`'false'`, tags as their JSON array text, `null` meaning "had none".
- **Names, phones and emails** are recorded whenever sent, redacted.
- **Owner and account** are recorded when moved, redacted.
- **Create** records every field it set. Value fields get `before: null`; consent gets `before: 'unknown'` (D-L81).
- **Behaviour change:** tags, state and lga used to be recorded "whenever sent". They are now recorded only when they actually moved, so an unchanged value no longer yields a no-op item.
- **Long values.** A value longer than the writer's 300-character limit is recorded by name only, so the write is never refused. In practice that means a very long tag list. `AUDIT_CHANGE_VALUE_MAX_LENGTH` is now exported from `audit-writer.ts`.

### Activity writes: `POST /api/v1/activities`, `PATCH /api/v1/activities/{id}`

The code is in `apps/api/src/activities/*` and `packages/domain/core/src/activity/*`.

**Create order** (D-L53):
1. **400** if there is no target, or a target is malformed. Without a target there is no programme to judge anything in.
2. **404** if the target is unreachable. The contact decides the programme when given, otherwise the account.
3. **403** without `activity.write` (plus `activity.reassign` for an owner other than the caller), or for any touched field that is not `edit`.
4. **400** if the strict body fails.
5. **400** `unknown_reference` for a second target outside the programme, or an owner who is not a programme member.
6. Otherwise insert, audit and respond.

**Update order:**
1. **404**.
2. **403**: the same permission rule, plus field security on `completed` (judged as `completedAt`) and `ownerUserId`.
3. **400**: the strict body, `task_only` when completing a note or call, and the owner's membership.
4. **409** if the version is stale.

`completed_at = COALESCE(completed_at, now())`, so completing twice keeps the first time.

**Ids and creator (D-L79).** The id is minted in the repository. `created_by_user_id` comes from `tx.session.userId`. The closed bodies refuse `id`, `createdByUserId`, `programmeId`, `tenantId`, the timestamps, `version` (on create), `completedAt` and retargeting.

**Free text.** `apps/api/src/common/text.ts` (with its test) is copied byte-for-byte from T-0055's branch, so the two branches merge without a conflict. NUL is 400 `invalid_character`.

**Audit.** One event per write: `objectType: 'activity'`, labelled by the id, with changes by name only. A refused write writes no event.

### Permissions

Two new programme actions in `policy.ts` (the policy unit tests are updated):

| Action | Held by | What it allows |
|---|---|---|
| `activity.write` | `agent`, `team_lead`, `programme_manager`, `admin`, and the tenant-admin flag | Log and complete activities |
| `activity.reassign` | `team_lead`, `programme_manager`, `admin`, and the tenant-admin flag | Give an activity to any member |

`canWriteActivity(grants, programmeId, caller, body, 'create' | 'update')` decides on the raw body. An agent may set the owner only to itself. On update, `null` (clearing the owner) counts as reassigning; on create, `null` means "unowned" and is allowed.

## What was hard

- **Paging over a filtered union with sub-millisecond ties.** Sorting on full-precision timestamps would let two items that look identical on the wire come out in non-id order, and the suite's order checker would fail. Sorting and paging on the millisecond the wire shows, with the id as tie-break, makes the order and the keyset agree by construction.
- **D-L53 order for createActivity.** Unlike createContact, a reader-only caller must get 404 for an unreachable target, not an early 403 (the suite's "order" test). So the target is resolved before any permission check, and the only 400 that can precede a 403 is "no or malformed target".
