### 2. The suite contradicts itself on the empty pipeline (I think a test is wrong)

- **`stage rules > exactly one won and one lost stage`** requires `noStages` to be refused. That case is
  `INSERT INTO pipeline ...` alone, followed by `SET CONSTRAINTS ALL IMMEDIATE`.
- **`keys > a one-statement rotation of stage or contact ids ...`** (around line 2489) runs its control probe with
  `keep = true`:
  - `probe()` executes `SET CONSTRAINTS ALL IMMEDIATE` and then `RELEASE SAVEPOINT`.
  - A RELEASE keeps the changed constraint mode for the rest of the transaction. PostgreSQL restores the saved mode only
    on a rollback to the savepoint (`AfterTriggerEndSubXact`).
  - Line 2517 then inserts the pipeline alone (`await query(INSERT_PIPELINE, [PR, ...])`) and adds its stages in a
    second statement.
- **In IMMEDIATE mode, every deferrable check fires at the end of that INSERT,** when the pipeline has no stages. This
  is true of a constraint trigger, a deferrable FK, or any other mechanism.
- So any schema that refuses `noStages` also refuses line 2517, with 23514, and the whole rotation test fails. The two
  scenarios cannot be told apart at the database. The only difference is which command is running, and keying a rule
  on `current_query()` would be a hack I won't write.
- **I kept the rule.** An empty pipeline is refused, as R4 and S require. I expect the rotation test to fail at line
  2517 for the reason above. I could not run it to confirm, because of blocker 1.
- **Suggested suite fixes (the lead's call):** any one of these:
  - pass `deferred = false` to that control probe;
  - plant the rotation pipeline before the control probe;
  - run `SET CONSTRAINTS ALL DEFERRED` after it.

## R9: how the default pipeline is created without a new SECURITY DEFINER (please review)

The four configuration tables each have ONE FOR ALL policy, with USING identical to WITH CHECK:

`tenant_id = current_tenant_id() AND (programme_id = ANY(current_programme_ids()) OR <0015's creation marker>)`

- The marker is copied word for word from 0015: the programme row's `xmin` is this transaction's xid, AND its
  `created_at` is at or after the transaction start.
- The marker branch can only name a programme this transaction INSERTED (0012 holds that to the session's tenant), or
  one it UPDATED, which requires the programme to be in scope already. So it admits nothing a session could not
  already reach. 0036's header gives the full argument.
- No permissive FOR INSERT policy is added, so the permissions suite's allow-list is unchanged. No SECURITY DEFINER
  function is added.
- `deal` and `deal_requirement_check` have no marker branch.
- **This is the one judgement call in the task.** D-L117 says "no wider policy" and names 0015's marker as the
  precedent. I read that as allowing the marker and forbidding a tenant-wide or scope-free policy. If the lead reads it
  more strictly, R9 cannot be met as kasuwa_app at all, because some permissive policy must admit the INSERT. In that
  case this needs a decision, not a rework.
