## What changed

- **`packages/domain/core/src/tenant/provision-tenant.ts`** has
  `provisionTenant(options)`, the one implementation of "create a tenant". It
  exports three errors: `TenantSlugTakenError`, `InvalidTenantSlugError` and
  `InvalidRegionError`. It also exports `RegionNotServedError` and
  `InvalidProvisioningInputError`, plus the audit-event builder. In one
  transaction it creates:
  - the tenant (`active`, `region_cell` set once);
  - one business unit;
  - the six default permission sets, with new ids;
  - the first admin (`active`), with an argon2id hash of a one-time setup
    credential and **no** MFA factor, so sign-in returns
    `enrolmentRequired: true`;
  - the default programme, **through `createProgramme`**, which also makes the
    admin its only member.
- **`packages/domain/core/src/tenant/tenant-slug.ts`** holds the slug rules,
  all pure functions:
  - 2–63 characters;
  - lower-case ASCII letters, digits and single hyphens, not at either end;
    upper case is refused, not folded;
  - no `--` anywhere, which rules out every `xn--` punycode label;
  - not one of the reserved words `admin`, `api`, `www`;
  - `slugSkeleton` catches ASCII look-alikes (`rn`/`m`, `1`/`i`/`l`, `0`/`o`,
    `vv`/`w`, hyphens dropped). `provisionTenant` refuses a slug whose skeleton
    matches an existing tenant's (`TenantSlugTakenError('confusable')`).
- **`packages/domain/core/src/cli/tenant-provision.ts`** is the CLI, run as
  `pnpm -s tenant:provision --slug … --name … --admin-email … --admin-name …
  [--region ZA|NG|KE] [--allow-non-local]`.
  - It reads `DATABASE_MIGRATION_URL` through `@kasuwa/config`, like `db:seed`.
  - Progress goes to stderr. The credential goes to stdout once. The admin's
    email and name are never printed.
- **`packages/db/src/permission-set-catalogue.ts`** now holds the default
  permission-set list once. Both the seed fixtures and provisioning read it,
  and the seed output is byte-identical.
- **Root `package.json`** has a new `tenant:provision` script.
  **`packages/domain/core/package.json`** gains the `provision` script and the
  dependencies listed below.
- **Unit tests:** `tenant-slug.test.ts` (7) and `provision-tenant.test.ts`
  (13). They cover the guard, regions, slug validation, the credential's
  shape, the audit-event shape, and the fact that validation fails before any
  connection opens.

## The migrator connection, argued against CLAUDE.md rule 2.1

Rule 2.1 says every query on tenant data runs inside `withTenantTransaction`,
with no admin connection and no escape hatch. Provisioning cannot start there:

- A tenant transaction needs a tenant row and an active user in it before it
  can open, and neither exists yet.
- Under `kasuwa_app`, the `tenant` policy refuses an `INSERT` whose id is not
  already the session's tenant.
- So the application role cannot create the row its own context would name.

The alternatives are a third SECURITY DEFINER function (which needs an ADR,
rule 2.7) or an operator command. D-L54 chose the operator command, on the
`db:seed` precedent. What keeps this from becoming the "admin connection"
rule 2.1 forbids:

1. **It is not reachable from traffic.** `provisionTenant` takes the
   connection string as an argument. `apps/api` has no migrator URL in its
   configuration (D-L07), so nothing serving requests can call it with one.
2. **Only two rows are written outside a tenant context:** `tenant` and the
   first `user`. Those are the rows a tenant context is built from.
3. **Everything else is written inside a real, unmodified
   `withTenantTransaction`** for the new tenant:
   - the business unit, credential, permission sets, programme and membership;
   - session resolution runs, and the scope-seal check runs;
   - every tenant id comes from `tx.session`, never from the caller.

   The default programme comes from the same `createProgramme` the admin API
   uses.
4. **It is still one transaction.** The tenant transaction runs as a
   savepoint on the same connection, through a private adapter that maps its
   BEGIN/COMMIT/ROLLBACK to SAVEPOINT/RELEASE/ROLLBACK TO. A failure anywhere
   leaves nothing behind.
5. **It refuses a non-local host** unless given the explicit
   `allowNonLocalDatabase` / `--allow-non-local`. The refusal names the
   switch. When the switch is used, a warning naming the host is logged.
6. **No SECURITY DEFINER function was added.**

**Where this argument is weaker than D-L54 states:** D-L54 says that inside
the tenant transaction "the RLS rules are exercised, not bypassed". They are
not:

- `kasuwa_migrator` holds BYPASSRLS, and BYPASSRLS overrides FORCE, so the
  policies are never consulted on those writes.
- What does run is session resolution, the sealed-scope check and the
  explicit `tenant_id` predicates in the reused code.
- Making the policies apply would need `GRANT kasuwa_app TO kasuwa_migrator`
  in `sql/bootstrap.sql`, so the command can `SET LOCAL ROLE kasuwa_app` for
  the tenant transaction. That is a role-model change, so I am raising it
  rather than making it.

## Can the slug ever change?

No path exists, and I recommend there never be one. The slug is typed at
sign-in, appears in every link, and under D-P6 may become a subdomain:

- A rename breaks every link already sent.
- It frees the old slug for someone else to claim, which is a phishing gift.

If a rename is ever needed, it should be an operator command that keeps the
old slug as a reserved redirect. The proposed migration below also stops the
application role from updating `slug`, so "never" is enforced by the database
and not only by convention.

## What was hard

- **The region test needs a migration this branch cannot write.** This is the
  blocker above. The task file and D-L54 do not mention that `kasuwa_app` can
  currently update `tenant.region_cell`. That is a real gap today, regardless
  of provisioning: any code under a tenant session can move the tenant's
  recorded region.
- **"One transaction" and "through `withTenantTransaction`" pull in opposite
  directions,** because the helper owns its own BEGIN/COMMIT on a pooled
  connection. I chose the savepoint adapter over two transactions with
  compensation, and over changing the tenancy primitive's API. Reviewers
  should look at `savepointPool` specifically.
- **pnpm echoes script arguments.** `pnpm tenant:provision …` prints the full
  command line, admin email included, before any of our code runs. The inner
  call is now `--silent`. The outer banner belongs to the operator's pnpm, so
  the usage text says `pnpm -s`.

  - string values;
  - `admin_email` as a redacted change.

  It is logged on every run with the note "NOT persisted". The migrator could

  does not.
- **Forcing a credential change.** There is no change-password endpoint yet

- **NG and KE.** `region: 'NG' | 'KE'` raises `RegionNotServedError` rather

  true is the one thing "region is where the data lives" forbids. **If
  @acexode needs an NG tenant before that decision, this will block it.** That
  is deliberate and should be decided rather than worked around.
- **Locale and currency defaults.** The table defaults (`en-NG`, `NGN`) are
  left as they are. Onboarding (T-0018) sets them, and region is not market.

## Risks I am aware of

- **Tenancy:** the savepoint adapter is a `Pool` look-alike around the
  migrator connection. It is private to the file, not exported, and only
  narrows the meaning of transaction control. It is still a BYPASSRLS
  connection; see question 2.
- **Personal data:**
  - the admin email and display name are never logged by the function or the
    CLI, and validation errors name the field, never the value;
  - the credential is returned once and only its argon2id hash is stored;
  - `provisionTenant` is now exported from `@kasuwa/domain-core`, which
    `apps/api` imports. It is inert without a migrator URL, which the API does
    not have.

## Proposed migration (blocked by protect-paths; not in this branch)

```sql
-- 0015 - the application role may no longer change a tenant's region, slug,
--        status or identity (T-0015; D-P2, D-L54).
--
-- tenant.region_cell is where the tenant's data lives, set once by the
-- operator. kasuwa_app held table-level UPDATE on tenant and tenant_isolation
-- admits any write to the session's own tenant row, so any code under a tenant
-- session could move the recorded region. RLS answers "which rows", not
-- "which columns"; a column privilege is the tool.
--
-- Re-granted: name, locale_default, currency_default (tenant settings),
-- role_hierarchy_version (roles.service.ts bumps it; its SELECT ... FOR NO KEY
-- UPDATE needs UPDATE on at least one column), updated_at.
-- Not granted: region_cell (residency), slug (public, permanent), status
-- (commercial state), id, created_at. FAIL CLOSED: a future tenant column is
-- not app-writable until a migration grants it.

SET LOCAL lock_timeout = '5s';

REVOKE UPDATE ON tenant FROM kasuwa_app;
GRANT UPDATE (name, locale_default, currency_default, role_hierarchy_version, updated_at)
  ON tenant TO kasuwa_app;

DO $$
BEGIN
  IF has_column_privilege('kasuwa_app', 'public.tenant', 'region_cell', 'UPDATE') THEN
    RAISE EXCEPTION 'kasuwa_app can still UPDATE tenant.region_cell after 0015';
  END IF;
  IF has_column_privilege('kasuwa_app', 'public.tenant', 'slug', 'UPDATE') THEN
    RAISE EXCEPTION 'kasuwa_app can still UPDATE tenant.slug after 0015';
  END IF;
END
$$;
```

I checked every `UPDATE tenant` in the repo against this. Application code
only bumps `role_hierarchy_version`, which stays granted. The auth
integration tests that update `status` do so as `kasuwa_migrator`, which owns
the table and is unaffected. A refused write raises `42501`, which the
acceptance test catches as "refused".
