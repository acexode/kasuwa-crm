## What changed

- **Migration `0007_metadata_api_name_immutable_no_nin.sql`**
  - D-P4: `app.reject_api_name_change()` (plpgsql, SECURITY INVOKER, pinned
    `search_path`, `REVOKE ALL FROM PUBLIC`) and two `BEFORE UPDATE ... FOR
    EACH ROW WHEN (OLD.api_name IS DISTINCT FROM NEW.api_name)` triggers, on
    `object_def` and `field_def`. Raises `23001 restrict_violation`, with a
    message that names the table but no value. Because of the `WHEN` clause,
    label, description and config updates never call the function.
  - D-P5: a `DO` block counts `field_def` rows typed `nin`/`bvn`. If there are
    any it **fails the migration** and gives the count only; it never converts
    them. Then `field_def_type_check` is dropped and re-created under the
    same name, without `nin`. `bvn` was never in the list and is still not.
  - No new tables, no RLS changes, no SECURITY DEFINER.
- **`packages/metadata-engine`**
  - `FIELD_TYPES` / `fieldTypeSchema` no longer have `nin`; `bvn` was never
    there.
  - New `objectDefSummarySchema` and `listObjectDefSummaries(tx)`. This is a
    `LEFT JOIN` count with `tenant_id = $1` (taken from the session) on both
    sides of the join, ordered by `api_name`, and rows are Zod-parsed. Unit
    tests check the parameterisation, the tenant filter on both sides, the
    zero count, and that rows are parsed rather than cast.
- **`apps/api`**: new `src/admin/field-security/`
  - `FieldSecurityAdminModule.register({ authMode })` is its own module. It
    takes `authMode` because `AUTH_MODE` is an AppModule provider and a child
    module cannot see it. AppModule changes by two lines: one import and one
    entry in `imports`.
  - `FieldSecurityController`: `GET /api/v1/admin/field-security/objects`,
    with `KasuwaAuthGuard` and `TenantTransactionInterceptor`. The response is
    parsed through a strict Zod schema on the way out, so an id or tenant id
    cannot leak into the payload. OpenAPI cross-reference is in the doc
    comments; the API has no swagger decorators.
  - `AdminNotAuthenticatedFilter` is applied at controller level with
    `@UseFilters`. It turns a bare `UnauthorizedException` into the
    contract's `{statusCode, error, code: 'not_authenticated', message}`.
    Auth's global behaviour and the other routes are unchanged.
  - `@kasuwa/metadata-engine` was added as a workspace dependency (an
    internal package, not a new external dependency; `pnpm-lock.yaml` +3
    lines).
- **`docs/api/admin.openapi.yaml`**: `listFieldSecurityObjects` is now
  `x-kasuwa-implemented: true`, and its description says what is live.
  `tests/e2e/support/admin-mock.generated.ts` was regenerated, which changed
  one line.
- **`nin` grep across the repo, including `apps/web` and the i18n
  catalogues**: no field-type references outside `types.ts` and 0002.
  `admin.ret.redact` mentions "BVN and NIN" as a redaction policy label, not a
  field type, so I left it. No i18n keys were added or removed, so the
  catalogues stay complete.

## What was hard

- `AUTH_MODE` is only provided in AppModule, so a sibling admin module cannot
  inject `KasuwaAuthGuard` without being given it. I used `register({
  authMode })`. Agents 1 and 3 will hit the same thing. If three admin
  modules each re-provide the guard, interceptor and `AUTH_MODE`, a shared
  `AdminCommonModule` (or making `AUTH_MODE` global) is the obvious follow-up.
  That is Agent 1's call, because they own `tenancy/`.
- The 401 body. The stub guard's `UnauthorizedException` has no `code`. I
  fixed it with a controller-scoped filter rather than changing the guard,
  per the brief. `AdminNotAuthenticatedFilter` lives inside
  `admin/field-security/` so it cannot add/add-conflict with siblings. It
  should move to a shared `admin/` location once the second admin module
  needs it.

## What I left out, and why

- **No 403 / admin permission check.** There is no permissions engine yet.
  Any authenticated user of the tenant can read the object list (names,
  labels, counts; never records). The gap is documented on the controller
  and in the spec description.
- **No feature flag.** This is a read-only API endpoint, and the web screen
  is still on the generated mock. The user-visible switch is wiring P02/D to
  the real API, and that is where the flag belongs.
- **No standard objects synthesised.** Contact, lead and the rest appear
  only when a tenant has an `object_def` row for them (per the brief). Today
  the seed has none, so a fresh tenant's list is `[]`. For P02/D to show the
  five tabs, something has to create standard `object_def` rows (`is_custom =
  false`) per tenant. That is a decision (seed or provisioning), and I did
  not make it.
- **`tenant_id` / `object_id` immutability** on the definition tables is not
  enforced. D-P4 covers `api_name` only. RLS `WITH CHECK` already stops a
  cross-tenant move.
- The spec's file header still says "EXACTLY ONE OPERATION IS `partial` AND
  NONE IS `true`". That is now stale. I left it because Agents 1 and 3 are
  flipping operations in parallel and the line would conflict three ways. The
  lead should reword it at merge.

## Risks I am aware of

- The endpoint is tenant-wide by design (metadata is not programme-scoped).
  The acceptance suite asserts this, and a reviewer should not "fix" it.
- The trigger also binds the migrator and seed. Any future data fix that
  renames an api_name must be an explicit migration that disables the
  trigger and argues why. That is intended.
