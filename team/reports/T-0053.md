## What T-0053 does

**Migration 0025**
- **Backfill:** every tenant gets standard (`is_custom = false`) `contact` and `account` object definitions, and one
  `field_def` per standard field. `is_custom = false` is 0002's own meaning of "standard", so **no new column** was
  needed.
- **Adopting pre-existing rows:** a row that already carries a catalogue name keeps its id, label, description and
  grants.
  - It is marked standard.
  - A field takes the catalogue's `type`, `config` and `is_required`.
  - Its `classification` is raised to the catalogue level, never lowered.
- **Proof:** a per-tenant, per-name anti-join against the catalogue. It checks that every standard object and field
  exists and is standard, and that each field has the catalogue's type, config and is_required, and at least its
  classification.
- **Stray standard rows:** the backfill also fails if any `is_custom = false` object or field is not in the catalogue.
  The message gives row and tenant counts only.
- **Guards:**
  - **Restrictive DELETE policies:** kasuwa_app can delete custom definitions only. The migrator's offboarding cascade is
    unaffected.
  - **Restrictive INSERT policies:** kasuwa_app inserts custom definitions only. The check is the tenant predicate plus
    `is_custom`, and it applies to tenant admins too.
    - Re-review: the earlier version admitted a tenant admin's field on contact or account. That field would be
      undeletable and frozen, and would pre-empt a later catalogue addition of the same name.
    - No application caller writes standard rows. Migrations, the seed, provisioning and the repair all run as the
      migrator.
  - **Trigger on is_custom:** no role may flip `is_custom`.
  - **Trigger on object_id:** no role may move a standard field to another object.
  - **Trigger on meaning:** kasuwa_app may not change a standard field's `type`, `config` or `is_required`.
    - The check fires whether current_user or session_user is kasuwa_app, as 0023's guard does.
    - A later migration can still correct these values.
  - Labels, descriptions and classification stay editable.
  - Rename was already blocked by 0007.
  - The trigger messages name the table and the rule.
- **Locking:** `LOCK TABLE object_def, field_def IN ACCESS EXCLUSIVE MODE` up front, under `lock_timeout = 5s`.
- **Privilege proof:**
  - It covers kasuwa_app and every role it is a member of (kasuwa_sweeper included).
  - It fails if any of those roles has TRUNCATE on either table, or BYPASSRLS.
- **Header:** documents the deploy window. Do not provision tenants between `db:migrate` and rollout, or call
  `ensureStandardObjectDefs` for every tenant after rollout.
- **Not added:** no new table, no SECURITY DEFINER function. The census is still the two.

**Catalogue:** `packages/db/src/standard-object-catalogue.ts`
- `STANDARD_OBJECT_CATALOGUE` and `ensureStandardObjectDefs(query, tenantId)`.
- `ensureStandardObjectDefs` is idempotent (`ON CONFLICT DO NOTHING`). Fields attach to the tenant's standard object of
  that name.
- It then checks the result per catalogue name: existence, standard, type, config and is_required. Classification is not
  compared (D-P25). If anything is missing or mis-typed, it throws `StandardCatalogueIncompleteError`, naming the
  catalogue entries.
- The seed and `provisionTenant` call it. Provisioning calls it inside the tenant's transaction.
- The header gives the recipe for adding a standard field:
  1. add it here;
  2. in a new migration, check for clashes first, and RAISE naming the object, the field and the number of tenants;
  3. then insert the rows, as the migrator;
  4. end with 0025's two-way check.

**Loader:** `loadFieldAccess(tx, objectApiName)` in `@kasuwa/metadata-engine`.
- One round trip.
- T-0026/T-0041 semantics.
- Unknown, foreign and malformed names all reject identically, with `UnknownObjectDefError` and the message
  `No object definition`.
- `fieldLevel(access, programmeId, fieldApiName)` defaults to `none`. Callers should use it rather than `.get()`, as the
  doc comment says.

**metadata-engine create inputs:** they no longer accept `isCustom`. Everything created through the engine is custom.

**Contact path**
- `loadContactFieldAccess` is unchanged in signature. It is built on `loadFieldAccess` through
  `contactFieldAccessFromObjectAccess`.
- It fails closed where T-0041 defaulted to `edit`:
  - a tenant with no contact definition now rejects;
  - a withholdable field with no field_def now reads as `none`.
- `resolveContactFieldAccess` (T-0041's resolver, which failed open) is **deleted**. `apps/api/src/contacts/contact-wire.test.ts`
  now builds `ContactFieldAccess` directly.
  - **#92 had not merged when I finished.** If #92 changes that test, the rebase will need the same treatment: build the
    map instead of calling the resolver.

**Dependency:** `@kasuwa/domain-core` gains a workspace dependency on `@kasuwa/metadata-engine`. There is no new
external dependency.

## Tests added or changed (none under tests/acceptance)

- `packages/db/src/standard-object-guards.integration.test.ts` (new, 14 tests):
  - the INSERT policies refuse a standard object or field to both the admin and an agent, including the reviewer's
    `x_std` example;

    mis-typed;
  - the type, config and is_required freeze for kasuwa_app;
  - labels and custom fields stay editable;
  - the migrator can still correct a standard field;
  - `ensureStandardObjectDefs` is idempotent and restores a deleted row.
- `metadata-engine/src/field-access.test.ts`:
  - resolution rules;
  - `fieldLevel` fails closed;
  - malformed names are rejected with no round trip;
  - the catalogue is valid metadata.
- `domain-core`:
  - contact mapping and fail-closed behaviour;
  - catalogue alignment with `WITHHOLDABLE_CONTACT_FIELDS`;
  - provisioning rollback and savepoint placement.
- **Coverage of the adoption rule:** the T-0053 backfill block plants `contact.emails` as `text`. 0025's own proof
  requires the catalogue type, so a backfill that did not adopt the type would fail "applies 0025 cleanly".
