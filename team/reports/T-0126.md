# T-0126 — The TOTP step offers "Text a code to …" only when SMS is possible

**Agent:** 11 — Frontend & Design System
**Branch:** `agent11/T-0126-totp-sms`
**Screens:** P01/2, P01/2a (`docs/design/P01/v1.0/Kasuwa Auth and Onboarding.html`)

## What changed

- **`apps/web/lib/mfa-sms-option.ts` (new).** The rule as pure functions:
  - `smsOptionHint(methods)` returns the masked number only when the challenge's `sms` entry is `available` AND has
    a non-blank `deliveryHint`; otherwise `null` (hide). A blank or whitespace hint counts as no number.
  - `rememberSmsOption` / `recallSmsOption` / `forgetSmsOption` keep that decision in `sessionStorage` under
    `kasuwa.mfa.sms:<challengeId>`. A `null` decision removes the entry rather than storing "no", so a reissue that
    withdraws SMS leaves no number behind. A missing, throwing, corrupt or foreign entry reads as `null`, so the
    option stays hidden.
  - `verifyPath(challengeId)` builds `/verify?challenge=…` and nothing else.
- **`sign-in-screen.tsx`.** On a successful first factor it records `smsOptionHint(result.value.methods)` against the
  challenge id, then navigates with `verifyPath`.
- **`mfa-screen.tsx`.** The "Text a code to …" button renders only when `smsOffer !== null`, and its label uses that
  hint. `smsOffer` starts as `null`, so the server render and first paint never show an empty label. It is read from
  `sessionStorage` after hydration, which is how a reload of `/verify` keeps the decision. `applyChallenge` (after a
  reissue) applies the same rule to the reissued `methods` and stores the result, so both paths agree. A successful
  verify forgets the entry.
- **`app/verify/page.tsx`.** I removed the `?hint=` search parameter. Nothing in the app ever set it, but a page that
  reads a masked phone number from the URL invites someone to put it there. P01/2a's body now gets its hint from the
  reissued challenge, as before, or from `sessionStorage` on a reload. The `method` and `resendAt` parameters are
  unchanged.
- **`apps/web/lib/mfa-sms-option.test.ts` (new), 16 unit tests.** They cover the 2x2 available/hint matrix, a
  missing `sms` entry, a blank hint, never borrowing another method's hint, a round-trip keyed by challenge,
  removal on `null` and on forget, corrupt entries, a missing or throwing store and an empty id, and `verifyPath`
  carrying one parameter only. They fail without the change, because the module does not exist without it.

No new i18n keys, because `auth.mfa.alt.sms` already exists in every catalogue. No restyle. No new dependency.

## What was hard

Not much. The one design choice was where the decision lives. The task allowed `sessionStorage` alone, or a URL
`sms=1` flag with the hint in `sessionStorage`. I chose `sessionStorage` alone: a flag in the URL would still need
the hint from storage, so it adds a second source that can disagree with the first and buys nothing. The option is
read after hydration, not during render. Reading it during render would make the server and client HTML differ, and
the button would appear for one frame before hydration.

## Left out

- On a reload while on **P01/2a**, the screen goes back to P01/2, because the method is not carried. That was
  already the behaviour and is outside this rule.
- On P01/2, the "Use a backup code" and passkey alternatives still render unconditionally. The same kind of rule
  probably applies to them, but this task does not ask for it. This is a possible follow-up (the lead numbers it).
- Design-parity shots for the PR (see above).

## Open questions

None blocking. The live API sends `{ available: false, deliveryHint: null }` for `sms`, so today no real user sees
the option. That is the intended result until M08 supplies a channel provider.
