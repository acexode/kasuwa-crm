## Migration review fixes (`f118aa8`)

The review found no blockers. 0029 has not been applied anywhere outside tests, so it was amended in place:

1. **Rollback plan.**
   - First a forward `ALTER TABLE field_def DISABLE TRIGGER field_def_classification_raise_only`, which takes SHARE ROW
     EXCLUSIVE, so reads carry on.
   - Later, `DROP TRIGGER` and `DROP FUNCTION`, which take ACCESS EXCLUSIVE and block reads.
   - Each step runs with `SET LOCAL lock_timeout`.
   - Never `DISABLE TRIGGER ALL` or `USER`: either would switch off 0025's `field_def_standard_fixed` and 0018's
     `field_def_touch_updated_at` too.
2. **Header.**
   - No role may lower a standard field's classification *by UPDATE*. That covers a plain UPDATE, an upsert's DO UPDATE
     and MERGE.
   - DELETE followed by a re-INSERT is refused for kasuwa_app by 0025's restrictive policies. The BYPASSRLS roles
     (kasuwa_migrator, kasuwa_test_admin) can still do it.
   - kasuwa_test_admin never exists in a real cell (D-L92, T-0117).
3. **Self-check.** The trigger's WHEN clause, extracted from `pg_get_triggerdef`, must equal
   `((NOT old.is_custom) AND (old.classification IS DISTINCT FROM new.classification))`. Only the clause is compared, so
   search_path-dependent table qualification cannot make the check flaky. The integration posture test pins the same
   clause on every build.

Open question 1 is answered: drift stays fail-closed under the raise-only constraint, T-0089 maps it, and there is no new
SQLSTATE.

## Design choice: a trigger beside 0025's, AFTER rather than BEFORE

The suite leaves this to the builder. I did **not** extend `app.guard_standard_field_def()`:

- **Extending would redefine an applied object.** It would mean `CREATE OR REPLACE` of 0025's function plus a DROP and
  re-CREATE of `field_def_standard_fixed` to widen its WHEN. 0025 would then no longer describe what runs.
- **The rules differ in kind.** 0025 mixes every-role rules (23001) with kasuwa_app-only rules (42501). This rule binds
  every role, has its own code and constraint, and its own way out. Disabling one trigger by name for a deliberate
  lowering must not switch off the is_custom, object_id and meaning guards with it.
- **AFTER, not BEFORE.**
  - BEFORE triggers fire in name order and each one may rewrite NEW, so a BEFORE guard is only as good as whatever sorts
    after it. An AFTER trigger judges the row as it will actually be stored. The integration test proves this.
  - The CHECK runs before AFTER triggers, so an unknown value such as `'secret'` is always the CHECK's 23514, never
    reported as a lowering.
  - The cost is a small AFTER-trigger event queue per bulk statement, on a catalogue of dozens of rows per tenant.
- **One consequence: two refusals in one statement.** A statement that lowers *and* flips `is_custom` is refused by
  0025's BEFORE trigger first (23001). The suite accepts "whichever guard speaks first".

## Risks I am aware of

- **Tenancy is unchanged.** No policy, grant or table was added. A cross-tenant lowering matches no rows, so the trigger
  never fires and there is no oracle (the suite pins this).
- **Deliberate lowerings.** Any future migration or repair script that lowers a standard field's classification will
  now fail until it uses the DISABLE/ENABLE recipe. The seed is unaffected because it TRUNCATEs and re-inserts. The
  0025–0028 adoption upserts only ever raise.
