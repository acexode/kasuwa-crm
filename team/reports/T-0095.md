## Escalations (please read)

1. **M8 latency: not met.**
   - First page and deep page measured 525 / 485 ms in the suite. The host's load average was 11–16 during every run;
     other suites were running in both slots.
   - My first version took 2.1 s, mostly JIT (PG chose JIT because jsonb set-returning functions estimate 100 rows each)
     plus a disk spill. The shipped statement avoids both: one index-led scan, the RLS functions as index conditions, one
     unnest, and COLLATE "C" keys. Its cost estimate stays well under `jit_above_cost`.
   - On the same host a bare `count(*)` of the programme's 60k rows took 40–220 ms, so I cannot tell what a quiet host
     gives. My estimate is about 120–200 ms.
   - I did not add a table, an index or any GUC change.
   - The remaining options are lead decisions:
     - re-measure on a quiet host;
     - allow `SET LOCAL work_mem` for this one statement, which stops the aggregate spilling to disk;
     - relax the budget to the lookup's 500 ms, which is the closest comparable scan;
     - or approve a precomputed key table (D-L146 says escalate rather than add one).
2. **No database READ layer for D-P27.**
   - Every form of it needs either a new `app.*` setting (so undo can still reach the row it restores) or a third SECURITY
     DEFINER function.
   - The one GUC-free variant I found is a restrictive SELECT policy admitting deleted rows that have an open merge row.
     It admits every merged-away row during exactly the window that matters, so it hides nothing.
   - I built the write layer, which needs neither, and stopped there, per CLAUDE.md 2.7 and the brief.
3. **I think the offboarding test is wrong** ("does not stop offboarding: deleting a programme that holds merges still
   succeeds").
   - It fails on `audit_event_programme_same_tenant_fk`, not on anything in 0043.
   - M3 requires the merge's audit event to carry the programme. 0008's audit FK to programme has no ON DELETE, so any
     programme with any audited write cannot be deleted directly. That is true on main for any createContact.
   - `contact_merge` itself cascades correctly: the test's own failure point is the audit row.
   - Either the test should delete through the tenant, or plant the merge row directly rather than through the API.
