### Observability (`apps/api/src/telemetry/`)

- `request-telemetry.ts` — `RequestTelemetryMiddleware`, applied to every path
  in `AppModule.configure`. One SERVER span and one log record per request.
  The span is always a **new root**: `traceparent`, `x-request-id` and similar
  are never extracted, so the trace id is minted by the server.
- `attributes.ts` — **the allow-list.** A span or log can carry only
  `http.request.method` (normalised, unknown -> `_OTHER`), `http.route` (the
  template Express matched), `url.template`, `http.response.status_code`,
  `error.type` (5xx only), `tenant_id`, `programme_id`, `cell`. Every write goes
  through `allowListed()`. For a path that matched no route, `url.template`
  keeps only words that occur in a declared route; everything else, including
  the query string, never reaches it. No header, body, client address or user
  id is recorded.
- `tenant_id` and `programme_id` are set from **inside `withTenantTransaction`**
  (`tenant-transaction.interceptor.ts`), i.e. the scope the database resolved.
  The guard does not set them: before the session is resolved, a tenant id is
  only what the caller claimed. `programme_id` is the list of the session's
  programmes.
- `sdk.ts` + `main.ts` — `KASUWA_OTEL_EXPORTER=none|console` (default `none`).
  Deliberately not the auto-instrumenting NodeSDK: http/express/pg
  auto-instrumentation records `url.full`, `user-agent`, client addresses and
  SQL text, none of which is on the allow-list.
- `@kasuwa/config` — `KASUWA_CELL` (a slug; free text is refused) and
  `KASUWA_OTEL_EXPORTER`. `.env.example` updated.
- `packages/testing/src/telemetry.ts` — `collectTelemetry()`, exported from
  `@kasuwa/testing`, matching the contract in `tests/acceptance/support/telemetry.ts`.
  It installs an in-memory span exporter and log sink and restores the previous
  providers afterwards. Spans are `{ name, traceId, attributes }`; logs are flat
  records (attributes plus body, severity and trace/span id).

Unit tests: `apps/api/src/telemetry/attributes.test.ts` (7) and one new case in
`packages/config/src/config.test.ts`.

## What was hard / worth knowing

- **The dependency scan finds 36 known vulnerabilities already in the
  lockfile** (1 critical, 13 high, in 14 packages). A blocking scan would have
  turned every PR red on day one, and fixing them means major upgrades (vitest
  3/4, nx 22, vite 6). So they are **baselined, not accepted**: every one is in
  `osv-scanner.toml` with the same expiry, **2026-10-31**, after which the scan
  goes red until each is fixed or re-accepted with a real reason. New
  vulnerabilities block immediately. Most are dev/test tooling (vitest's
  critical is its API server; undici and uuid come in via testcontainers). **One
  is in the API's runtime path: `drizzle-orm` 0.38.4 (GHSA-gpj5-g38j-94v9,
  CVSS 7.5), via `@kasuwa/db`. That should be triaged first.** The baseline and
  its expiry date are a decision the lead may want to change.
- I chose "any known vulnerability" over a severity floor because OSV
  severities are often missing, and `pnpm audit --audit-level=high` would have
  let an unscored one through silently.
- Full-history gitleaks found four existing hits; all four are invented values
  (the documented example token in `docs/api/auth.openapi.yaml`, the e2e mock
  generated from it, and a base32 TOTP fixture). They are ignored by exact
  fingerprint, so the same value committed anywhere new still fails.
- `ProxyTracer` caches its delegate, so the middleware looks up the tracer and
  logger per request. Without that, a provider swapped in by `collectTelemetry`
  is only honoured the first time.

## Left out, and open questions

- **Scope 2 (Terraform, cost estimate)**: not in this round.
- **Container scanning (Trivy)**: nothing builds an image yet; it belongs with
  the first Dockerfile (the ci-hardening suite says the same).
- **Nx remote cache**: not set up. It needs an Nx Cloud account and token, which
  is a spend and a third-party data question. `nx affected` plus the local
  cache gives the structural win without it.
- **OTLP export**: no collector exists (D-A4), and where traces are hosted is an
  NDPA cross-border question. `console` is the only exporter.
- **Nest's own error logger is a PII path this task did not close.** For an
  unhandled exception Nest's `ExceptionsHandler` logs `exception.message` and
  the stack through the Nest logger, which `main.ts` keeps on (`error`, `warn`)
  in production. A pg error message can contain row values (`Key (email)=(...)`).
  It is not an OTel log, so the acceptance suite does not see it (the test app
  runs with `logger: false`). Suggest a follow-up that replaces the Nest logger
  with one that records the exception class only.
- **Suggestion on the contract**: `collectTelemetry` returns only span
  `attributes`, not span events or status messages. My implementation records
  neither, but a future `span.recordException(err)` would put the exception
  message in an event the PII grep cannot see. Including events in the
  returned spans would make the grep cover that too.
- **Required status checks**: listed in the runbook for @acexode (D-L34 says the
  lead configures them once Pro exists). `Secret scan` and `Dependency scan`
  are new names on the list.
- **Size**: about 800 hand-written lines, plus the lockfile and the generated
  baseline. It is two commits (CI ~390, observability ~580 with the lockfile)
  that split cleanly into two PRs if wanted.
