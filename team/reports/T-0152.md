# T-0152 — Recreate the e2e lock, and fix the e2e README

**Status:** build PR open, awaiting CI and review. Acceptance suite merged in #219, unedited.

## What changed

- **`tools/e2e-locked.sh`** (new, committed `100755`). Runs `pnpm test:e2e -- "$@"` from the repo root under a
  machine-wide lock.
  - The lock is a directory taken with `mkdir` (atomic), holding `owner.pid`, at
    `${KASUWA_E2E_LOCK_DIR:-${TMPDIR:-/tmp}/kasuwa-e2e.lock}`: outside the checkout, so every worktree shares it.
  - `KASUWA_E2E_LOCK_TIMEOUT` seconds to wait (default 3600). A lock whose owner pid is dead is taken over; a live one
    never is, and nothing is ever stale by age.
  - Exit 3 when `docker info` fails (the lock is released first, and the script never starts Docker), exit 4 on a wait
    timeout (the owner pid is in the message), otherwise the e2e command's own status.
  - Released on every exit, by a trap that only removes a lock still naming this process.
- **`tests/e2e/README.md`** rewritten where it was wrong:
  - the "there is no mock server" claim: screen specs run on contract mocks (`support/*-mock.ts` via `page.route`), and
    only `tenancy` and `bff-session` talk to the real API through the web app;
  - the stub-header sign-in step: ADR-0019's same-origin BFF and `__Host-kasuwa_session` replaced it, and
    `support/bff-session.ts` is how a journey signs in for real;
  - every contract mock must answer `GET /api/v1/auth/me`;
  - a "run it through the lock" section with the env vars and exit codes, and the suites that start the harness
    themselves (`records-ui`, `admin-ui`, `scripting-ui`, `session/`, `auth-ui/p01-auth-screens`) with the `-t` way to
    run only their static checks.

## Checks

CI is the gate (D-L207). Locally I ran only the named suite, `e2e-lock.acceptance.test.ts`: **15 of 15 pass**. It uses
stub `docker` and `pnpm`, so it needs no Docker and starts no e2e run. Nothing else was run locally.

## What was hard

- The suite builds the child's `PATH` inside bash, because tests may not read `process.env`. That also means the script was
  exercised through MSYS `bash` on Windows (paths converted with `cygpath`); it is plain POSIX bash and has no Windows-only
  parts.
- `git` on Windows does not keep an exec bit from the working tree, so the script is committed with
  `git update-index --chmod=+x`, which the suite checks with `git ls-files -s`.

## What I left out

- `pnpm test:e2e` and `scripts/run-e2e.mjs` are unchanged, and no e2e spec or mock was touched (pinned by hash).
- I did not make `pnpm test:e2e` refuse to run without the lock. The task asked for the script and the README; forcing it
  is a change to the runner.
- The README now says "run through the lock", but the nightly workflow and any `ci.yml` job call `pnpm test:e2e`
  directly. A CI runner is one job at a time, so the lock is for developer machines; I did not touch any workflow.
