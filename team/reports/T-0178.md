## Summary

Recommended option: **separate `portal_identity` / `portal_session` / `portal_programme` tables; no third `SECURITY DEFINER`.** Sign-in and invite acceptance resolve the tenant with the existing `app.resolve_tenant_by_slug` (invite URL carries the tenant slug; token in fragment or POST). Portal session resolve uses a presented-token SELECT policy and a non-definer GUC accessor (ADR-0009 amendment pattern). Scope always from `portal_programme` inside the tenant transaction.

## Recommended option (short)

1. **Identity:** do not reuse `"user"` / `user_programme`. Three portal tables; invitations hardened separately in T-0180.
2. **Sign-in before session:** slug → existing definer → auth-pool verify → `portal_session` token.
3. **Invite lookup:** slug in path (webhook precedent), not a third definer. Auth-pool SQL under RLS.
4. **Session resolve:** presented-token policy; third definer only as an explicit fallback amendment.
5. **Scope:** `portal_programme` only; client-supplied programme ids never authoritative.
