# T-0024 — Admin API: programmes read and update

**Agent:** 3 — Core CRM & Pipeline
**Branch:** `agent3/T-0024-admin-programmes`, cut from `lead/T-0024-acceptance` (not pushed, no PR opened)

## What changed

`packages/domain/core/src/programme/`

- `programme.repository.ts` — `listProgrammes`, `countProgrammes`, `findProgrammeById`,
  `updateProgramme`, `listProgrammeMembers`. Every query takes a `TenantTx` and repeats
  `tenant_id = session.tenantId` **and** `id/programme_id = ANY(session.programmeIds)` on top of
  RLS. `user_programme` and `"user"` are tenant-scoped only under RLS, so the members query is
  gated on the programme being in the session *and* readable before it runs — RLS alone would
  list a sibling programme's members. Each query carries `// tenancy-reviewed`.
- `programme-version.ts` — the lead's ruling on `version`: epoch milliseconds of `updated_at`,
  parsed from a Postgres `to_char` rendering by an explicit pattern (truncated, never rounded).
  Every write sets `updated_at = GREATEST(date_trunc('ms', clock_timestamp()),
  date_trunc('ms', updated_at) + 1 ms)`, so the version strictly increases even for two writes
  in one millisecond or a backwards clock step.
- Optimistic concurrency: `updateProgramme` reads the row `FOR UPDATE`, returns `null` if it is
  unreachable (before any version check, so a foreign id never reaches the 409 path), throws
  `StaleProgrammeVersionError` if the version differs, then updates — one transaction, row locked.
- `23505` on `programme_tenant_id_name_key` becomes `DuplicateProgrammeNameError`, which carries
  no identifier and no database text. The constraint is `UNIQUE (tenant_id, name)`, so
  uniqueness is tenant-scoped by construction.
- Cursors use the existing `encodeKeysetCursor` / `decodeKeysetCursor` (position only:
  `created_at` to the microsecond + row id). No scope in them; a cursor replayed by another user
  only moves the window inside that user's own set.

`apps/api/src/admin/programmes/`

- `programmes.controller.ts` — `GET /api/v1/admin/programmes`, `GET /:programmeId`,
  `PATCH /:programmeId`, `GET /:programmeId/agents`, each annotated with its `operationId` and
  statuses. `@UseGuards(KasuwaAuthGuard)` + `@UseInterceptors(TenantTransactionInterceptor)`.
  No tenant or programme id is read from the request.
- `programmes.schemas.ts` — Zod, every object `.strict()`. `pageSize` 1..200 default 50,
  `cursor` ≤ 512, `q` ≤ 200, `status` filter from the enum. PATCH: `version` required integer,
  `name` 1..200 (trimmed), `clientName` ≤ 200 or null, and **any** `status` refused at path
  `status` with detail code `not_supported`.
- `programmes.errors.ts` — the admin `Error` envelope (`statusCode`, `error`, `code`, `message`,
  `details[{path, code}]`) for these routes only. Unrecognised keys are reported at their own
  path (`programmeIds`), which the global filter would report at the root. A bad cursor is
  `validation_failed` at `cursor` (the admin spec has no `invalid_cursor`). The global filters
  and every existing route's errors are untouched.
- `programmes.presenter.ts` — response shapes; unbacked fields `null`, `initials` derived.
- One 404 body (`not_found`) for: unassigned sibling, other tenant, nonexistent, and malformed
  (non-uuid) id. For PATCH and `/agents` the id is resolved before the body/query is judged, so
  an unreachable id is 404 whatever else was sent.

`apps/api/src/app.module.ts` — `AdminProgrammesController` added to `controllers`. Prettier
broke the array onto several lines, so it is a 7-line diff, not one. **Why a controller and not
a Nest module:** `KasuwaAuthGuard` needs `AUTH_MODE`, which `AppModule` provides non-globally;
a guard on a controller in an imported module cannot resolve it without either duplicating the
`'stub'` default into a `forRoot(...)` or making `AppModule`'s providers global. Both change auth
wiring; adding the controller does not. Agents 1 and 2 will hit the same constraint — the lead may
want one `AdminModule` pattern decided once.

`docs/api/admin.openapi.yaml` — the four operations flipped to `x-kasuwa-implemented: true`, each
with a short "Built (T-0024)" paragraph saying what is null and what is not enforced; header note
updated. `tests/e2e/support/admin-mock.generated.ts` regenerated from it (4 flag lines), so the
committed mock does not drift from the spec.

## Lead rulings applied

- `status` — no column; always `active`; `statusCounts` = `{active: <matches>, paused: 0,
  draft: 0, archived: 0}`; a `status` filter other than `active` returns an empty page. PATCH
  refuses any status (400 at `status`).
- `version` — derived from `updated_at`, as above.
- `presence` — `null`. `teamName` — `null`. `languages` — omitted (no column; an empty array
  would assert "speaks nothing").

## Not done / gaps (please track)

1. **`403 not_permitted` is not enforced.** No permissions engine: any member of a programme
   can rename it, including a plain agent. This is a real authorisation gap on a write, not
   only a missing status code.
2. **`x-kasuwa-audited: true` on `updateProgramme` is unmet.** No audit table. Guardrail 6.7
   says audit permission/admin changes; a rename currently leaves no trail.
3. `status` changes, `channels`, `agentCount`, `slaAttainment7d`, `retentionSummary`,
   `reference`, `countryCode`, `contract`/`operating`/`people` — no columns or owners.
4. No `@nestjs/swagger`, so "OpenAPI annotations" are doc comments naming the operationId and
   statuses; the YAML stays the contract. Adding swagger is a dependency decision I did not take.
5. `listProgrammeAgents` lists every `user_programme` member, including a `disabled` user still
   assigned. Whether disabled users should appear (greyed) or be hidden is a product question.
6. `isDefault` is read but not returned — it is in the list description's prose but not in the
   `Programme` schema. If the screen needs it, add it to the schema first.

## Open questions

- Should an agent (as opposed to a supervisor/admin) be able to reach the admin programmes API at
  all? Today membership is the only gate — see gap 1.
- `duplicate_name` within a tenant can name-probe a programme the caller cannot read (rename to a
  guessed name → 409 vs 200). The spec accepts tenant-scoped uniqueness; flagging that it is an
  intra-tenant existence oracle for names. Fixing it needs either case-folded per-programme-set
  uniqueness or the permissions engine to restrict who may rename.
