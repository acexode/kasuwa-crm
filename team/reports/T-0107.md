## What was hard

- **The won column sorted under FORCE RLS.** With a constant `LIMIT 21`, Postgres picked a different plan for the won
  card statement: it moved the policy's `programme_id = ANY(app.current_programme_ids())` into the closed index's
  condition and then Sorted the 1,400 rows in the window, instead of reading the index in order. The cause is that it
  multiplies the selectivities of tenant, programme, pipeline and stage as if they were independent. It estimated 15
  rows where there were 1,400.

  The fix is that the card statement's LIMIT is a subquery, `LIMIT (SELECT $n::int)`. The planner costs a LIMIT it
  cannot read as 10% of the rows, so the ordered board-index path wins. Runtime reads are unchanged. This is documented
  at `deal-board.repository.ts:456-469`.

  **Recommendation (a decision, not made):** extended statistics, `CREATE STATISTICS ... (dependencies) ON
  programme_id, pipeline_id, stage_id FROM deal`, would correct the estimate itself. That needs a migration, so I did
  not add one.
- **Won column cursor.** The seek is spelled out as `closed_at <= key AND (closed_at < key OR id < key_id)` rather than
  as a row comparison, because the closed index's columns are DESC. Only the cursor's own ties are filtered.
- A docker outage on the host (not caused by this run; another session was waiting on it too) cost one debugging
  stack. My slot was released when it happened.

## Tests I think are wrong (please review; not edited)

Both are in `getPipelineBoard: counts, totals and cards (I4, D-P19)`. Each reads a card that, by the suite's own
model, is not on the first page at the default limit of 20.

1. **"the whole board: … closedSince echoed"**, l.2416-2417. It expects S0's first page to contain the unpriced
   `d(24)` and `d(25)`. Those deals entered 6-7 hours before T0, so in "oldest first" order (the contract, and the
   suite's own `columnOrder`) they are positions 21-22 of 25. `expectBoard` in the same test has just asserted that the
   page is `order.slice(0, 20)` (it passes). The two assertions contradict each other.
2. **"weighted totals are rounded half-even per deal …"**, l.2515. `weightedOf(d(20))` reads `d(20)` (3 hours, the
   newest S0 deal, position 25) from `servedBoard()` at the default limit, so it is `undefined`. The other three probes
   (`d(13)`, `d(17)`, `d(1)`) are on page 1 and pass. `d(20)`'s weighted amount `"4"` is served correctly on page 2,
   and the GHS total that contains it (`90071992547409942`) passes in the same test.

Suggested fix for both: send `['limit', '50']` in those two `servedBoard()` calls and pass `{ limit: 50 }` to
`expectBoard`, as the cards test already does.
