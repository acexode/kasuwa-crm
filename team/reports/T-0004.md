## Summary

The nine `it.todo` entries in `tests/acceptance/tenancy/adversarial.acceptance.test.ts`
are now seventeen real tests, all running inside the blocking isolation gate.

**Five findings, three of them new attack classes the stub did not list.** Two
are defects I would call serious; one is a defect in a document's reasoning
rather than in code; one is latent and unreachable today; one is an oracle that
exists but has no path to it.

I did **not** fix any of them. Three are pinned by **characterisation tests** —
tests that assert the wrong behaviour on purpose, say so in capitals, and go RED
the moment the defect is fixed. The alternative was a red blocking gate on
`main`, which is a stop-the-line condition and would have pressured somebody
into a fast fix rather than a right one. Each names its finding and its owner in
a comment and tells the fixer exactly which assertion to flip.

**No cross-tenant leak of business data was found through any supported path.**
The RLS layer held against everything I threw at it from below. FINDING-1 is
about what happens *above* that layer, not a hole in it.

## Findings

### FINDING-1 — a `TenantTx` callback can re-scope itself to any tenant (HIGH)

**Owner:** Agent 1 / the lead (architectural, ADR-0002).
**Test:** `CHARACTERISES FINDING-1: a TenantTx callback can re-scope itself to any tenant`.

`withTenantTransaction` hands the callback a `tx.query` that is an unrestricted
statement channel on the same connection that carries the RLS session GUCs, and
`set_config` is executable by `kasuwa_app`. So:

```ts
await withTenantTransaction(pool, { tenantId: TENANT_A, userId: USER_A_AGENT_1 }, async (tx) => {
  await tx.query(
    `SELECT set_config('app.tenant_id', $1, true), set_config('app.programme_ids', $2, true)`,
    [TENANT_B, `{${PROGRAMME_B1}}`],
  );
  return tx.query('SELECT display_name FROM contact');
});
// -> [ 'Grace Mwangi', 'Hassan Abdi', 'Irene Chebet' ]  — all tenant B
```

`tx.session.tenantId` still reads `TENANT_A` throughout. The object a reviewer
looks at and the scope the database enforces have diverged, which is precisely
what would make this hard to catch in review.

Why it matters beyond the obvious: ADR-0002 says "the last line of defence is
Postgres rather than application code, so it holds even if a controller is
wrong", and `packages/testing/src/isolation.ts` says the question the suite
answers is "if the application layer were completely compromised and set any
session variables it liked, what could still leak?". The honest answer is
**everything in the cell**, for any code holding a `TenantTx`. The guarantee is
real but narrower than either sentence: it holds against code that is wrong *by
accident*, not against code that is wrong *deliberately*. Every other tenancy
control — repository predicates, resolved scope, the guard that rejects scope
headers — sits above this line and is bypassed along with it.

**Not a live exploit.** Nothing in the repository does this, no endpoint injects
SQL, and every write path is parameterised. It is a missing control, and the
mitigation is a decision rather than a patch: a `TenantTx` whose `query` refuses
`set_config`, a `SECURITY DEFINER` setter that can only narrow a scope, or an
explicit paragraph in ADR-0002 accepting it so the next reader is not misled. I
deliberately did not choose between those.

### FINDING-2 — keyset pagination silently drops rows below millisecond resolution (HIGH)

**Owner:** whoever owns `packages/domain/core/src/cursor.ts` (M3 / Agent 3).
**Test:** `CHARACTERISES FINDING-2: keyset pagination drops rows below millisecond resolution`.

Two independent truncations compose into data loss:

1. `pg` parses `timestamptz` into a JavaScript `Date`, which is millisecond
   precision. `2026-01-01 00:00:00.000500+00` arrives as `…T00:00:00.000Z`.
2. `encodeCursor` writes `position.createdAt.toISOString()` — millisecond
   precision again.

The cursor therefore names a position **earlier** than the row it was built
from. Under `ORDER BY created_at DESC, id DESC` with the predicate
`(created_at, id) < (cursor)`, every row whose `created_at` lies between the
truncated cursor and the true value is skipped **permanently**. Nothing errors,
no page looks short, and the rows are simply absent from the listing.

Reproduction (in the test): insert three contacts into programme A2 at
`12:00:00.000900Z`, `.000500Z` and `.000100Z`; six rows now exist in that
programme. Page through with `limit: 1` until `nextCursor` is null.

```
rows in programme A2:            6
rows returned by the full walk:  4
```

The two rows at `.000500` and `.000100` are never returned. No duplicates —
that half of the invariant holds.

Reachable in production, not just in a contrived fixture: `created_at` defaults
to `now()`, which has microsecond resolution, so any two contacts created within
the same millisecond can do it. A bulk import does it continuously. The existing
`cursor-tampering` suite does not see it because every seeded `created_at` is a
whole minute.

The fix is not mine to choose, but for the record the cheap options are to carry
the position as a Postgres-formatted string rather than a `Date` (`created_at::text`
round-tripped verbatim), or to compare on a value the transport cannot truncate
such as `extract(epoch …)::numeric`. A paired control test
(`paginates every row when timestamps are millisecond-aligned`) sits next to it
so the diagnosis is "loses sub-millisecond rows", not "pagination is broken".

### FINDING-3 — `auth_rate_limit` is readable and deletable by every session in the cell (MEDIUM)

**Owner:** Agent 1 (M2 / auth), ADR-0009.
**Test:** `CHARACTERISES FINDING-3: any session reads and clears every auth_rate_limit row in the cell`.

ADR-0009 argues the missing `tenant_id` is harmless because "the only thing a
session could do with unrestricted access is increment or clear a counter for a
key it already knows — which it can do anyway by making sign-in requests". Both
halves of that sentence are wrong against the policy as written
(`USING (true) WITH CHECK (true)`):

- **SELECT is unrestricted**, so a session enumerates every key in the cell.
  ADR-0009's own text says the digest is unkeyed over a low-entropy input and a
  row is therefore "evidence that a named person attempted to sign in at a named
  workspace". Reading the table is reading that evidence for every *other*
  tenant — the exact pseudonymised personal data the ADR puts in NDPA scope.
  "A key it already knows" does not describe a full table scan.
- **DELETE is unrestricted and unbounded.** One statement clears every lockout
  in the cell, for every tenant. No sign-in request can do that, and lockout is
  the only bound on password guessing in the system.

The exemption itself is right — a counter that must answer identically for a
workspace that does not exist cannot be scoped to a tenant. What is wrong is the
argument that `USING (true)` follows from it. A policy that admits a row only to
a session presenting that row's `key_hash` would keep the property ADR-0009
needs and remove both of the above. The HMAC the ADR already wants (blocked on
D-L13) would remove the enumeration value separately.

Same standing as FINDING-1: reachable only by code that can issue arbitrary SQL,
so it is a missing second layer rather than a live exploit — which is exactly
what makes it notable, because this is the one table the repo itself describes
as having a single layer of defence.

### FINDING-4 — a unique-constraint violation is a cross-tenant existence oracle (LOW, unreachable)

**Test:** `never puts another tenant's row values into a constraint or planner error`
plus `keeps the contact id server-generated, which is what closes the uniqueness oracle`.

RLS cannot filter a uniqueness check. Inserting a contact whose `id` collides
with a row in **another tenant** raises `23505 duplicate key value violates
unique constraint "contact_pkey"` — which discloses that the row exists. The
good news, and it is genuinely good: Postgres gives the app role no `DETAIL`, so
**nothing about the row leaks** — not the display name, not the family name, not
the phone number, not the owning tenant or programme. I asserted all five.

The oracle has no path to it today because no write path accepts a client-chosen
id. That is the entire compensating control, so it is now asserted rather than
assumed: a test fails if `contact.repository.ts` grows an `INSERT`. Worth
remembering at the moment an import or upsert API is designed.

### FINDING-5 — the rate-limit key and the account lookup normalise differently (LOW, latent)

**Test:** `keeps the rate-limit key's normalisation identical to the account lookup's`.

`hashRateLimitKey` normalises with JavaScript `String.prototype.toLowerCase()`.
`AuthService.findAccount` matches with Postgres `lower()`. These are different
functions: JavaScript applies Unicode *full* case mapping, Postgres applies the
collation's *simple* mapping. U+0130 (LATIN CAPITAL LETTER I WITH DOT ABOVE)
lowers to `i` in Postgres under `en_US.utf8` and to `i` + U+0307 in JavaScript
— verified against the real container, not assumed:

```
postgres:  lower('WANJİRU') = 'wanjiru'
javascript: 'WANJİRU'.toLowerCase() = 'wanji̇ru'
```

So `wanjİru.agent@tenant-b.test` would find the **same account** while producing
a **different** `auth_rate_limit` key — a fresh five-attempt budget per spelling,
against the only bound on password guessing in the system. With one such
character per `i` in an address the budget multiplies.

**It does not work today**, and the only reason is that `SignInBody.email` is
`z.string().email()`, whose regex is ASCII-only. That is one relaxation away
from being untrue, and IDN email is a plausible ask for an Africa-first product.
The test asserts the disagreement is real *and* that the schema rejects the
input, so widening the schema fails the test rather than quietly opening the
bypass.

## Attacks tried that did NOT break anything

Recorded because "did anyone check?" should have an answer that is not a guess.

- **Interleaved transactions on a pool of one.** Three transactions across two
  tenants forced onto a single physical connection. Each saw exactly its own
  programmes. `set_config(..., is_local => true)` plus the transaction boundary
  holds.
- **`statement_timeout` firing between `set_config` and the query.** The
  statement is cancelled (`57014`), the transaction aborts, and after `ROLLBACK`
  the connection reports `app.tenant_id = ''` — which `app.current_tenant_id()`
  turns into NULL, denying every row. The recycled connection then served the
  next tenant correctly. Fails closed.
- **Subtransaction rollback.** `ROLLBACK TO SAVEPOINT` reverts `set_config` to
  the *enclosing* transaction's value, i.e. back to the session's own scope. It
  cannot be used to carry a widened scope forward.
- **Membership changes mid-session.** Granting yourself a `user_programme` row
  inside a live transaction does not widen what that transaction can read — the
  GUC was set before the insert. Revoking one narrows scope on the very next
  transaction.
- **Timing: "no such contact" vs "contact in another tenant".** 81 interleaved
  pairs, medians compared. Within noise. The harness carries a positive control
  (a `pg_sleep(0.004)` arm that must show >3× separation), so the test cannot
  pass by being blind.
- **Reserved-word `"user"`.** Scanned every `.ts` and `.sql` file in `apps/` and
  `packages/` for `FROM|JOIN|INTO|UPDATE user` unquoted, excluding comment
  lines. Nothing. Detector proven to fire on `FROM user` and stay quiet on
  `FROM "user"` and `FROM user_programme`.
- **`formatProgrammeIds` fuzz.** 200 generated uuids accepted, 200 single-
  character mutations rejected, 16 hostile shapes rejected (array delimiters,
  `NULL`, embedded comma, quotes, whitespace, NUL byte, a SQL-injection
  payload). Nothing got through.
- **`decodeCursor` fuzz.** 500 seeded random strings over a base64/JSON-ish
  alphabet: all rejected with `InvalidCursorError`, none produced a position.
  200 legitimate positions round-tripped exactly. A cursor with `tenantId` and
  `programmeIds` smuggled in decodes to `{createdAt, id}` only.
- **Authentication transaction reach.** A session with a tenant and an empty
  programme list — what `withAuthTransaction` produces — reads zero contacts and
  zero programmes, while still reading the four `user` rows and one `tenant` row
  it needs. The claim in the `withAuthTransaction` header comment is true.
- **Rate-limit key delimiter ambiguity.** `hashRateLimitKey` joins its parts
  with `:` and does not length-prefix them, so `('signin','a:b','c@d')` and
  `('signin','a','b:c@d')` collide. I could not reach it: `email` is
  `z.string().email()` and a colon in the local part is rejected, and the slug
  is only ever the first part. Noted, not filed.
- **Forged scope from below** (the existing `rls-enforcement` ground): re-run
  and re-confirmed, no new angle found there. I did not restate its attacks.

## On "tests that cannot pass by accident"

Every assertion in the suite either has a positive control beside it or is
called out where it is legitimately vacuous:

- the timing test asserts its own resolving power before it asserts equality;
- the `"user"` scan asserts the detector fires on the string it hunts and stays
  quiet on the two near misses that make up almost every line it reads;
- the constraint-error test asserts one substring that IS present, so the
  `not.toContain` loop is demonstrably capable of failing;
- the concurrency test requires every result list to be non-empty, so "saw
  nothing" cannot pass as "leaked nothing";
- the fuzz tests assert their iteration counts, so an empty loop cannot pass as
  coverage;
- `buildAuthzMatrix({ roles: [], … })` returning `[]` is genuinely vacuous and
  says so in a comment next to it.
