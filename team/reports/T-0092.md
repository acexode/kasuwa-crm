## What changed

**`packages/storage-adapter`** (new; `@kasuwa/storage-adapter`, `scope:adapter`, mapped in `tsconfig.base.json` and
`vitest.workspace.ts`)
- `keys.ts`:
  - `StorageKey` and `StoragePrefix` are classes with private fields. That makes them nominal to TypeScript, and checkable
    at run time (`#text in value`), which R2 needs;
  - the constructor demands a module-private symbol, so nothing outside the module can build one;
  - `mintStorageKey(tx, { programmeId, purpose })` is synchronous. It takes the tenant from `tx.session` only. The
    programme must be in `tx.session.programmeIds`, the purpose in `STORAGE_PURPOSES` (`['import']`), and the fileId is
    a fresh `randomUUID()`. Extra input is ignored;
  - `tenantStoragePrefix` refuses anything but a canonical lower-case UUID;
  - keys and prefixes are redacted from `JSON.stringify` and `util.inspect`, so logging one by mistake prints no path.
- `port.ts`:
  - the `ObjectStore` port, with exactly the eight methods;
  - `planParts`: every part but the last is equal and at least 5 MiB, the last part holds the remainder, and the parts
    sum to the total. It refuses a length ≤ 0 or fractional, a part count < 1, and a count that cannot meet the 5 MiB
    minimum;
  - validation of part lists, upload ids and content types.
- `s3-store.ts`, `S3ObjectStore(storageEnv(env))`:
  - two `S3Client`s. `internal` calls S3_ENDPOINT. `public` only signs part URLs, on S3_PUBLIC_ENDPOINT;
  - every method refuses an unminted key or prefix before any request;
  - every SDK error is wrapped;
  - `requestChecksumCalculation` and `responseChecksumValidation` are both `WHEN_REQUIRED`;
  - SSE `AES256` is sent on every PutObject and CreateMultipartUpload, unless `S3_SSE_MODE=off`;
  - part URLs are `UploadPart` presigns with `expiresIn: 300` and `signableHeaders: {content-length}`;
  - `deletePrefix` aborts the prefix's multipart uploads first (R10). It then pages ListObjectsV2 at `MaxKeys` 10,000,
    deletes in batches of 1,000, fails on any per-key error (with a count, never a key), and sweeps the uploads once
    more;
  - `head` returns `null` on a 404, and `abortUpload` is idempotent on NoSuchUpload;
  - **beyond the suite (D-L146):** every PutObject and CreateMultipartUpload is tagged `kasuwa-purpose=<purpose>`, the
    tag the lifecycle backstop matches. A prefix filter cannot do it, because the purpose is not a leading prefix. I
    observed SeaweedFS 3.80 keep the tag on both paths, and keep the content type through a multipart upload.
- `errors.ts`:
  - `StorageError` carries a `code`, a fixed message, `providerCode` (the S3 error name, checked against
    `^[A-Za-z][A-Za-z0-9.]{0,63}$`) and `httpStatus`. Nothing else, and **no `cause`**: SeaweedFS's error XML, the
    SDK's `$response` and SignatureDoesNotMatch bodies all carry the key path or the access key id;
  - `StoredObjectNotFoundError` is one message and one code (`stored_object_not_found`), naming no id;
  - `StoredObjectStateError` and `StoredObjectInputError`.
- `repository.ts`, `StoredObjectRepository(store)`:
  - `create` mints the key with the row's own id (R1), inserts `pending`, uploaded by the session user, with
    `expires_at = now() + 24 hours` (the abandoned-upload window in ADR-0017), and returns a record with no key text
    (R4);
  - `get`, `presignUpload`, `completeUpload` and `markDeleted` read the row with an explicit
    `tenant_id = session.tenantId AND programme_id = ANY(session.programmeIds)` (R7), plus `FOR UPDATE` on the moves.
    A malformed id or an empty session is the not-found error before any query;
  - `presignUpload` signs the row's declared size, for a `pending` row only;
  - `completeUpload` completes, then calls `head`. If the size or content type differs, or the object is missing, it
    deletes the object and returns the `rejected` row rather than throwing, so the move commits. A failed
    CompleteMultipartUpload throws and leaves the row `pending`;
  - `markDeleted` deletes the object, then moves the row to `deleted`. It is idempotent, and `deleted` is terminal.
- `fake.ts`, `FakeObjectStore`:
  - keeps the same key rules and part planning;
  - records SSE and the tag per request;
  - `uploadPart` enforces the signed length;
  - an aborted upload cannot be completed;
  - exported for T-0094's unit tests and banned from apps and domains by lint.
- Unit tests: `keys`, `errors` (the wrapping drops every path, own property and `cause`), `fake` (with `planParts`),
  `s3-store` (refuses forgeries, with no network) and `repository` (against an in-memory table). 61 tests.

**`@kasuwa/config`**
- `storage-env.ts`, `storageEnv(env)`:
  - S3_REGION and S3_BUCKET are required;
  - S3_ENDPOINT and S3_PUBLIC_ENDPOINT are optional URLs, and the public one defaults to the internal one;
  - S3_FORCE_PATH_STYLE is `'true' | 'false'`;
  - the two keys are optional together;
  - S3_SSE_MODE is `AES256` (the default) or `off`. `off` is refused unless NODE_ENV is development or test, and an unset
    NODE_ENV counts as enforced. `aws:kms` is refused by the enum;
  - the result is frozen, and `credentials` is non-enumerable, so a spread or `JSON.stringify` leaves the secret out;
  - messages carry names only.
- `apiEnv` and `workerEnv` (`server-env.ts`) run `storageEncryptionProblems`. They refuse an invalid S3_SSE_MODE
  everywhere, and `off` outside development and test. They do not require the rest of the storage settings, so
  `SERVER_PROD_SAFE` still boots.
- `webEnv` accepts and returns `S3_PUBLIC_ENDPOINT`. `S3_ENDPOINT` joins `WEB_FORBIDDEN` (R9), and
  `tests/e2e/scripts/run-e2e.mjs` now blanks it for the web process.

**Migration `0040_stored_object.sql`**, in the 0027/0036 pattern, in one transaction with `lock_timeout 5s`
- The columns are exactly R3's. Constraints:
  - CHECKs: `key = 'tenant/' || tenant_id || '/programme/' || programme_id || '/' || purpose || '/' || id` (R1), purpose
    `import`, the four statuses, declared size > 0, verified size ≥ 0, content type 1–255 characters, sha256 of 32
    bytes;
  - `UNIQUE (key)`;
  - FKs, all ON UPDATE RESTRICT: tenant (CASCADE), `(tenant_id, programme_id)` to programme (CASCADE), and
    `(tenant_id, uploaded_by_user_id)` to "user" (RESTRICT);
  - one index: `(tenant_id, programme_id, created_at DESC, id DESC)`, which serves the FK lookups.
- RLS is ENABLED and FORCED:
  - `stored_object_isolation` is FOR ALL, with WITH CHECK identical to USING;
  - `stored_object_insert_as_session` is RESTRICTIVE FOR INSERT. kasuwa_app inserts only `pending`, unverified,
    unhashed rows, uploaded by `app.current_user_id()` (audit_event's actor rule, 0008).
- Grants:
  - `REVOKE ALL` from PUBLIC, kasuwa_app, kasuwa_auth, kasuwa_sweeper and kasuwa_test_admin;
  - kasuwa_app gets SELECT and INSERT, and UPDATE on `status`, `verified_size_bytes`, `sha256` and `expires_at` only.
    It gets **no DELETE**, so a DELETE is 42501;
  - the test admin gets full DML.
- `app.guard_stored_object_fixed()`, a SECURITY INVOKER trigger with a pinned search_path and EXECUTE revoked, uses
  D-L76's allow-list (the migrator only). It refuses changes to id, tenant_id, programme_id, purpose and key, and any
  move out of `deleted`.
- A self-check DO block. No SECURITY DEFINER.
- `schema.ts` mirror (`storedObject`), and `stored_object` in `TENANT_SCOPED_TABLES`.

## What was hard
- **Wrapping errors without losing the reason.** A wrapper that keeps the SDK error as `cause` fails the L scan,
  because the raw response holds `<Key>` and `<Resource>` with the full path. So the wrapper keeps only a status and an
  S3 error code that cannot contain a slash.
- **R1 against the planted rows.** The suite inserts `key` explicitly, so a generated column would be refused (428C9 is
  counted as a refusal, but the control insert would fail too). It is a CHECK, plus the guard trigger for immutability.
- **No DELETE, observably.** 0027 used a restrictive policy so a DELETE matches zero rows. This suite pins 42501, so it
  is a REVOKE here. The self-check covers kasuwa_app and every role it can enter, for DELETE, TRUNCATE and BYPASSRLS.
- **ESLint's one-rule-per-block override.** `no-restricted-imports` is replaced, not merged, by each later block, so
  the SDK pattern has to be restated in each block and deliberately left out of the adapter's own.

## Left out
- **The web CSP:** none exists. ADR-0019's build adds it, and the storage origin joins at T-0096 (D-L150).
- **Import endpoints, the job and the sweeper:** T-0094.
- **`presignDownload`:** not until the export centre (D-L146).
- **Bucket CORS methods and exposed headers:** not expressible on SeaweedFS (R11). Real cells: T-0005.
- `sha256` is never filled. Nothing computes it yet: `head` returns a checksum only if the uploader sent one, and
  presigned browser PUTs don't. The column and its 32-byte CHECK are ready for T-0094 if it hashes during the parse.
- `S3ObjectStore` takes a `StorageEnv` by type only. It does not check at run time that the object came from
  `storageEnv`.

## Open questions
1. **Tagging needs `s3:PutObjectTagging` in a real cell.** I added the D-L146 tag at write time. A cell whose IAM
   policy lacks the permission will refuse every upload. T-0005 should grant it, or the lead may prefer to drop the
   tag until the lifecycle rule exists.
2. **The content-type check at complete is strict equality.** SeaweedFS and S3 keep the type set at create. If a
   provider normalises it (adds `; charset=`), a good upload would be rejected. I saw no normalisation on SeaweedFS
   3.80.
3. **A failed CompleteMultipartUpload leaves the row `pending`,** so the client can retry inside the window. The
   lifecycle rule aborts the incomplete upload after a day. If the lead prefers a failed complete to reject the row,
   that is a one-line change.

## Review fixes (D-L155)
These were applied as new commits. Migration 0040 was edited in place, because it is unmerged.

**Applied**
- **Live transactions only.**
  - `@kasuwa/db`: `withTenantTransaction` registers each tx in a module-private WeakSet when its callback starts. It
    removes the tx before COMMIT, or in the rollback path.
  - `assertLiveTenantTx(tx)` and `TenantTxNotLiveError` (code `tenant_tx_not_live`) are exported.
  - The check is called in `mintKeyWithId`, and so in `mintStorageKey`, and in `create`, `presignUpload`,
    `completeUpload` and `markDeleted`.
  - Tests: forged, spread and prototype copies are refused (unit, `live-tenant-tx.test.ts`). The real tx passes while
    open, its copies are refused, and it is refused after COMMIT and after ROLLBACK (integration,
    `live-tenant-tx.integration.test.ts`).
  - The adapter's unit tests mock the check with a registry of stub txs, and assert that unregistered stubs are refused
    before any query or store call.
- **`tenantStoragePrefix` and `FakeObjectStore` are gated by lint.** `tenantStoragePrefix` is banned in apps and
  domains. `FakeObjectStore` is banned in every runtime package, in both the TS and JS blocks; tests are exempt.
- **No deep imports.** `package.json` has `"exports": { ".": "./src/index.ts" }`. `@kasuwa/storage-adapter/*` is banned
  everywhere. `keyForStoredRow` and `mintKeyWithId` are not exported from the entry.
- **Endpoint schemes.** `storageEnv` refuses any scheme but http and https everywhere, and requires https outside
  development and test.
- **Branded config.** `storageEnv` adds its result to a module-private WeakSet, `isStorageEnv` is exported, and
  `S3ObjectStore` refuses anything else, copies included.
- **0040 status rules.** These bind every role, the migrator included:
  - status moves forward only: `pending` to `uploaded`, `rejected` or `deleted`, and `uploaded` or `rejected` to
    `deleted`. Nothing moves into `pending`;
  - a deleted row cannot change at all;
  - `expires_at` cannot be cleared;
  - refusals are 23514.

  The key rule keeps D-L76's migrator exemption, and its refusal stays 42501.
- **Caps.** `PURPOSE_LIMITS.import` is 25 MiB and 4 parts. Both stores enforce it on put and presign, and the
  repository on create and on the part count.
- **One open upload per key.** I picked "abort the old one". Before CreateMultipartUpload, `S3ObjectStore.presignUpload`
  lists the open uploads on that exact key and aborts them. The fake store does the same, and the doc comments say so.
- **`deletePrefix` no-progress guard.** A truncated page with no token, a repeated token or no keys throws
  `storage_request_failed` rather than looping.
- **Lint and boundary verify.**
  - The SDK pattern now also covers `@smithy/*`, and applies to `.js`, `.mjs`, `.cjs` and `.jsx` through a new JS
    block.
  - `tools/verify-boundaries.mjs` now proves an `@aws-sdk` import in `apps/api` is reported. It also proves the same
    import in `packages/storage-adapter` is not.
- **Smaller fixes.**
  - `completeUpload` documents that it checks metadata only: a missing content type is accepted, because the server set
    the type at create.
  - Every docker-compose port binds `127.0.0.1`.
  - The three repository SQL statements carry `// tenancy-reviewed` markers.

**NOT applied: two rulings contradict the unmodified suite. Please rule.**
1. **`assertLiveTenantTx` in `StoredObjectRepository.get`.** The suite's R7 test ("filters explicitly too", around line
   2279) builds a TenantTx by hand: `{ session: <agent 1>, query: (t, v) => tx.query(t, v) }`. It calls
   `repo.get(narrowed, ROW_A1)` and expects the row back. The live check refuses that object, so the control fails.
   Applying the ruling to `get` would make the suite red. `get` is the one method left without the check. It is a read
   on the caller's own connection under RLS, with explicit session filters, so it cannot widen anything. Your options:
   - accept the exception (documented in `repository.ts`); or
   - edit R7 to narrow inside a real tx some other way, after which the one-line check can go into `get`.
2. **`CHECK (status <> 'uploaded' OR verified_size_bytes = declared_size_bytes)`.** The suite's test "an A1 session
   cannot update an A2 or tenant-B row…" (around line 2075) runs `UPDATE stored_object SET status = 'uploaded'` as
   kasuwa_app on a planted pending row with `verified_size_bytes` NULL. It pins that as accepted ("the control: an A1
   agent can move its own row"), and the CHECK refuses it. The repository always writes the verified size with
   `uploaded`, so the invariant holds in practice, but not in the database. The 0040 header records the omission. To
   add the CHECK, the suite's control would need to set `verified_size_bytes = declared_size_bytes`.
