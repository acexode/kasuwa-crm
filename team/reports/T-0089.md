## What changed

**Migration `packages/db/migrations/0039_custom_field_values.sql`** (expand only, one transaction, `lock_timeout 5s`)
- `custom jsonb NOT NULL DEFAULT '{}'::jsonb` on contact, account, activity and deal.
- Three CHECKs per table, all `NOT VALID`, none validated:
  - `<t>_custom_is_object`: `jsonb_typeof(custom) = 'object'`;
  - `<t>_custom_keys`: `NOT jsonb_path_exists(custom, 'strict $.keyvalue() ? (!(@.key like_regex "^[a-z][a-z0-9_]*__c$"))', '{}', true)`.
    `strict` plus `silent`: on a non-object it is NULL, so the is-object CHECK is what refuses it, as 23514;
  - `<t>_custom_size`: `octet_length(custom::text) <= 32768` (the backstop).
- `GRANT UPDATE (custom)` to kasuwa_app on activity and deal. INSERT and SELECT are already table-level on all four.
- `field_def.retired_at timestamptz NULL`, no default.
- One restrictive DELETE policy, `field_def_delete_not_standard_object`: kasuwa_app may delete a field_def only when
  its object is custom. It is ANDed with 0025's `field_def_delete_custom_only`.
- 0025's `app.guard_standard_field_def()` is replaced (same name, still INVOKER with a pinned search_path), and
  `field_def_standard_fixed` is dropped and re-created with a wider WHEN. A custom field's `type` is now frozen for
  kasuwa_app (42501). The migrator is not frozen (S4).
- A self-check DO block. No index, table, role, function, extension, LEAKPROOF mark or SECURITY DEFINER.
- Drizzle `schema.ts`: `custom` on the four tables, `retiredAt` on fieldDef.

**`packages/metadata-engine`**
- `custom-fields.ts`:
  - constants and limits;
  - `customValueProblem` (the six encodings; the number regex is the contract's, verbatim);
  - `customFieldsSchema(defs, 'create' | 'patch')`, the per-(tenant, object) Zod builder: `.strict()`, details from
    paths and `params.reason` only, a malformed key reported once at `custom` and never named;
  - `customIssueDetails`, `splitCustomPatch` and `jsonbTextOctets`;
  - `loadCustomFieldAccess`: one round trip for the live custom definitions plus the caller's level per programme,
    read on every request (V9);

- `custom-field-definitions.ts`: list, find, create, update and retire for the admin API. Create locks the object row
  by bumping its `field_security_version`, which serialises creates per object so the 100/500 limits cannot be
  raced. It refuses live and retired duplicates, and inserts `none` grants for every unlocked set when the field is
  `pii` or `sensitive`.

**`packages/permissions`**: `custom_field.write` joins `TENANT_ACTIONS`.

**`packages/domain/core/src/custom/custom-values.repository.ts`**
- **The projection.** `custom - ARRAY(keys NOT in the readable list for this row's programme)`. The list comes from a
  `$n::jsonb` map of programme to keys. This is ADR-0016's `custom - <withheld>` in its fail-closed form: withheld,
  retired and undefined keys are all removed, and a programme the map does not name reads `{}`.
- `readProjectedCustom` is one extra statement per page, keyed on (tenant, session programmes, ids). No record
  statement selects `custom` whole. The existing SELECT and RETURNING column lists never name it.
- `customMergeSet`: `custom = (custom || $set::jsonb) - $remove::text[]`.
- `measureCustomVisibleSize`: two integers, the before and after octets restricted to the readable keys.
- `customFilterClauses`: picklist `->>` equality, boolean `->` equality, and `NOT (custom ? $k)`. Every key and value
  is bound.
- The table name and column refs come from constants behind a guard (`CustomValuesSqlError`), as `dealProgrammeMember`
  does.
- Wired into the contact, account and activity repositories in core, and the deal repository in api (insert, update
  and list filters).

## Acceptance tests I think are wrong (not edited)
1. **`subject` on updateActivity** (values suite: "a retired key leaves custom AND withheldFields (V2)", "write
   answers: …updateActivity…", "(V3) the SQL projection"). Each sends `PATCH /activities/{id}` with
   `{ subject: 'T-0089 …' }` and expects 200. `UpdateActivityRequest` is closed and has no `subject`, and
   records-contract-activities pins the exact key set without it. The served answer is
   `400 unrecognized_keys at subject`. I did not widen the contract. Suggested fix: a body the contract admits, such
   as `{ dealId: null }`.
2. **Eager supertest requests.**
   - Admin suite: "no session is 401 on all four operations". It builds five `request(server())…` objects in an
     array before awaiting the first.
   - Values suite: "(V3)". `const calls = [read(...), get(...), …]` does the same.
   - supertest listens on the shared server for the first request and closes it when that request ends, so the later
     ones get `ECONNREFUSED`. That is a connection error, not an HTTP answer. Every other suite uses thunks
     (`() => request.Test`); so does the admin test right after this one.
   - So V3 hits both defects. Once both are fixed, I expect it to pass: no record statement selects `custom` whole,
     and the projection and the size check return only readable keys or integers. That is untested end to end.

## What was hard
- Projecting withheld values without letting them reach the process. Rather than add a per-programme projection to
  every record SELECT (four repositories, the board, RETURNING clauses), no record statement selects `custom` at all.
  One projected read per page does, and writes read back nothing. This kept the projection in one reviewed builder.
  It costs one extra statement per request; the budget shows about 26 ms at 120k rows.
- Measuring the size rule without reading values: the before and after visible sizes come back from SQL as two
  integers.
